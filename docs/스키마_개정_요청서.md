# DB 스키마 개정 요청서 (초안)

대상은 `PRJ_2026_002_DB스키마_설계안.md` v0.5다. 작성일 2026-10-31이며 발송은 사용자가 한다. 승인 전에는 새 테이블·코드를 쓰지 않는다.

## 1. 확정된 요청 (intent.md D8, D9)

권한 코드를 신설할지 기존 코드로 묶을지 기관과 설계 담당자의 판단이 필요하다.

## 3. 요청하지 않는 것 (확정)
- 전화번호 검색키 컬럼: 기존 D10의 제외 결정은 2026-11-19 A안 승인으로 대체했다(ADR-095, OTP_재전송제한_개정안.md). R26 환불 항목과 별개다.
- 환불 접수 채널 컬럼 (D11)

## 4. 별도 확인 (스키마 개정이 아님)
- 관리자 로그인 실패 제한 수치 (D12, PRD Q28). 기관 정책이 필요하다.
- 대시보드 확인할 업무별 필요 권한과 통계 집계자료 등록·승인 권한·위치 (PRD Q21, 화면설계서 S11). 스키마 개정이 아니라 기관 확인이다.

## 8. 콘텐츠 유형(CT) 코드 추가 요청서 (설계 담당자에게 발송)

> 발송용 단독 문서는 [글유형코드_추가_요청서.md](글유형코드_추가_요청서.md)이다. 이 장은 같은 내용의 내부 정리본이고, 그대로 설계 담당자에게 보낼 수 있게 정리했다. 근거는 기관 2차 회신(2026-11-17)이고 구현 쪽 작업은 승인 뒤에 시작한다. 승인 전에는 코드를 만들지 않는다.

**요청 한 줄.** 스키마 설계안(v0.5)의 CT 코드집합에 4종을 추가하고, 그중 2종을 기존 약관과 같은 버전 관리 규칙(R17)에 포함하는지 정해 달라.

### 8.1 추가할 코드

현재 CT는 `CT.INTRO`·`CT.HISTORY`·`CT.POPUP`·`CT.BANNER`·`CT.TERMS`·`CT.PRIVACY`·`CT.MARKET`·`CT.OPER_RULE` 8종이다(설계안 코드표, 마이그레이션 0001 시드).

| 순서 제안 | 코드 | 코드명 제안 | 쓰임 | 관련 요구 | 기관 답 |
|---|---|---|---|---|---|
| 9 | `CT.GUIDE` | 수강·환불 안내 | 수강신청·환불 안내 글 | RQ-FUN-FN-006 | 동의 |
| 10 | `CT.CONTACT` | 연락처 | 수강문의·센터 대표·행정복지센터 대표 전화, 운영시간, 주차, 주소 | RQ-FUN-FN-011, FN-072 | 동의 |
| 11 | `CT.PRIVACY_POLICY` | 개인정보처리방침 | 푸터와 방침 화면에 게시하는 문안 | RQ-FUN-FN-055, FN-072 | 동의, 버전 관리를 함 |
| 12 | `CT.EMAIL_REFUSAL` | 이메일 무단수집 거부 | 푸터 링크의 안내 문안 | RQ-FUN-FN-055, FN-072 | 동의, 버전 관리를 함 |

코드는 모두 `CT.`로 시작해 기존 CHECK(`CK_CD_SITE_CONTS_CONTS_TYPE_CD`)와 `FK_SITE_CONTS_03`을 통과한다. 다만 `CT.PRIVACY_POLICY`(17자)와 `CT.EMAIL_REFUSAL`(16자)은 코드 칸(CHAR(12))보다 길다. 아래 8.3의 1번을 먼저 정해야 한다.

### 8.2 추가하지 않는 것

| 코드 | 이유 |
|---|---|
| `CT.FACILITY`(시설안내) | 기관이 추가하지 않기로 답했다. 시설 정보는 기존 시설 테이블이 맡는다 |
| `CT.VISUAL`(홈 비주얼) | 기관 답이 없다. 홈 비주얼은 계속 비워 둔다(ADR-036) |

### 8.3 정해 주실 것

1. **코드 길이.** 코드 칸(`TB_COM_CD.COM_CD`, `TB_SITE_CONTS.CONTS_TYPE_CD`)은 CHAR(12)다. 기관과 합의한 이름 `CT.PRIVACY_POLICY`(17자)와 `CT.EMAIL_REFUSAL`(16자)은 들어가지 않는다. 후보는 두 가지다. (가) 12자 이내 이름으로 줄인다. (나) 코드 칸을 넓힌다(코드를 참조하는 모든 CHAR(12) 컬럼과 FK가 연쇄로 바뀌어 영향이 크다). 구현 쪽 추천은 (가)다.

   | 의미 | 줄임 제안 |
   |---|---|
   | 개인정보처리방침 | `CT.PRVPOLICY`(12자) |
   | 이메일 무단수집 거부 | `CT.EMAILREFU`(12자) |

   `CT.GUIDE`(8자)와 `CT.CONTACT`(10자)는 그대로 들어간다. 기관 회신과 요약 문서에 적힌 긴 이름은 줄임 이름이 승인되면 같은 뜻으로 읽는다.
2. **버전 관리 규칙(R17)에 포함하는지.** 두 문안은 기관이 버전 관리를 하겠다고 했다. 제안은 R17을 확장해 게시본 수정 금지, 새 버전 생성, SHA-256 문안 고정을 적용하는 것이다. 단, 동의 이력(`TB_MBR_AGRE_HSTRY`, R22)의 동의 대상에는 넣지 않는다. 두 문안은 회원이 동의하는 문서가 아니라 고지 문서이기 때문이다.
3. **묶음 공통인지.** 약관은 동 미지정(묶음 공통)이다. 두 문안과 `CT.GUIDE`·`CT.CONTACT`도 같은지 확인해 달라. 센터가 하나의 묶음이라 구현 쪽은 묶음 공통을 제안한다.
4. **연락처 구조 저장 위치.** 연락처는 항목 여럿(전화 3종, 운영시간, 주차, 주소)이다. 새 컬럼 없이 `CONTS_CN`(CLOB)에 항목 구조(JSON)를 저장하는 것을 제안한다. 이 경우 `CT.CONTACT`는 본문이 구조화 값이라는 규칙을 설계안에 한 줄 적어 주면 된다.
5. **게시 기간.** 4종은 게시 여부(`PSTG_YN`)와 게시 기간을 기존 규칙(`published_window`)대로 쓴다. 홈 배너만 기간을 보지 않는다(ADR-088).

### 8.4 승인 뒤 구현 쪽 작업

- 스키마 설계안 코드표와 마이그레이션 0001 시드에 코드 4종을 넣고(배포 전이라 0001에 포함), 5개 묶음의 코드집합 체크섬을 맞춘다(R24).
- 콘텐츠 API의 유형 목록과 `app/auth/join.py`와 같은 유형 매핑, 관리자 콘텐츠 화면의 유형 탭, 공개 화면(푸터·안내·연락처)을 서버 콘텐츠로 연결한다. 지금은 모의 서버 문서로만 둔다.
- 8.3의 2번이 승인되면 약관 서비스의 버전·해시 규칙을 두 유형에도 적용한다.
- 각 단계는 기존 방식대로 실제 DB 시험과 변이 검사로 확인한다.
