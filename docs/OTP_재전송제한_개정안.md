# 전화번호 기준 OTP 재전송 제한 적용 보고

2026-11-19 사용자가 권고안 A를 승인했다. D10·PRD Q27·DV82의 이전 결정을 ADR-095로 대체하고 소스와 설계안 v0.7에 반영했다. 실제 DB는 아직 이행하지 않았다. 기존 요청서 R26은 환불 항목이며 이번 건과 별개다.

| 항목 | 반영 내용 |
|---|---|
| 컬럼 | TB_CERT_DMND.TELNO_SRCH_HASH_VL CHAR(64) NULL. 기존 행은 NULL, 신규 발급은 항상 기록 |
| 검색키 | 숫자 전화번호와 otp-phone-search 파생키의 HMAC-SHA-256. 원문·단순 해시 제외 |
| 인덱스 | IX_CERT_DMND_03(OPER_BNDL_SN, TELNO_SRCH_HASH_VL, REG_DT) |
| 정책 | 운영묶음·전화번호 기준 60초. 목적·회원 존재·인증 소비 여부와 무관. 정확히 60초부터 허용 |
| 경합 | 발급·가입·복구 소비·인증기록 파기 모두 공통 운영묶음 → 인증 행 순서. DB 커밋 뒤 SMS 호출 |
| 가짜 요청 | 회원이 없어도 인증 행을 커밋해 같은 429 정책 적용 |
| 호환 | 서명 쿠키 보조 제한, OTP 5분 유효·오입력 5회 유지. HTTP API 형식 변경 없음 |
| 이행 | 0001·0002 보존, 0003으로 REG_DT DATETIME(6) 추가 확장. 새 테이블·기존 데이터 삭제 없음 |

## 배포 절차

1. DB 백업과 실행 대상을 확인한다. OTP 발급을 중지하고 **5분 이상 기다려 기존 OTP를 만료**시킨다. 기존 행에는 검색키가 없거나 소수초가 유실되어 이 대기 없이 전환하면 번호별 60초 제한에 공백이 생긴다.
2. apps/api에서 `uv run alembic upgrade 0001:head --sql`로 기존 0001 DB에 대한 추가 SQL을 검토한다. 이미 0002인 DB는 `uv run alembic upgrade 0002:head --sql`로 0003만 검토한다. 새 DB는 별도 0001부터 시작한다.
3. 올바른 JORI_DATABASE_URL이 설정된 환경에서 `uv run alembic upgrade head`를 실행한다. 실제 DB 적용은 이 작업에서 수행하지 않았다.
4. 변경된 API를 배포·재시작하고 스키마 버전 0003과 검색키·인덱스·REG_DT의 소수초 6자리 정밀도를 확인한다. 모든 API 인스턴스를 같은 버전·비밀키로 맞춘 뒤 발급을 재개한다. 구버전 인스턴스가 신규 검색키 없이 발급하게 두지 않는다.
5. 전용 jori_test DB에서 쿠키 삭제·새 세션·목적 변경·회원 없음·60초 경계와 동시성 시험을 실행한다. 실제 번호로 부하 시험하지 않는다.

비밀키 변경도 발급 중지 → 5분 만료 대기 → 모든 인스턴스의 키 교체 → 재개 순서로 진행한다. 기존 행 역채움·다중 키 조회는 제공하지 않으며 KEY_VER_ID는 v1이다. 롤백 때는 발급 중지 상태에서 구버전 앱과 DB의 순서를 맞춰야 하며 검색키를 제거하면 번호별 제한도 제거된다.

## 검증과 남은 확인

로컬 단위 시험으로 HMAC, 입력 형식, 60초 경계, 목적 통합, 회원 없는 요청, 다른 번호·운영묶음, 인증 소비 이후 제한을 검증한다. SQLite 시험은 MariaDB 제약·행 잠금을 증명하지 않는다. 오프라인 Alembic 시험은 0001 SQL 원본 보존과 0002 추가·되돌림 SQL과 0003 정밀도 확장·되돌림 SQL을 확인한다.

MariaDB 동시성 시험은 별도 코드로 제공한다. 현재 환경은 소켓 연결이 제한돼 실제 DB 이행·MariaDB 경합·브라우저 E2E를 검증하지 못했다. 이 범위는 배포 환경에서 확인해야 한다.

실행 결과: 관련 Python 56건 통과·실DB 필요 130건 건너뜀, 주민 화면 전체 34파일·401건 통과, mypy 334파일과 주민 화면 TypeScript·변경 파일 ESLint 검사 통과. 기존 보완 회귀 Python 30건 통과·20건 건너뜀.

최종 확인: API 전체 Ruff 통과, 변경 Python 서식 검사 통과, 주민 화면 운영 빌드 통과, git diff --check 통과.

## 코드 리뷰 후속 적용 (2026-11-19)

| 항목 | 수정 |
|---|---|
| P1 잠금 역전 | 발급·업무 소비·인증기록 파기 모두 공통 운영묶음 → 인증 행. 다른 묶음 인증은 잠금 대상에서 제외 |
| P2 격리 수준 | READ COMMITTED·REPEATABLE READ를 명시하고 연결에서 실제 격리 수준을 확인. 발급과 가입·아이디 찾기·비밀번호 재설정·실제 인증기록 파기의 혼합 경합 추가 |
| P3 60초 정밀도 | REG_DT를 DATETIME(6)로 확장하는 0003, 스키마 v0.7·생성기·Core 정의 동기화. 59.1초·59.999999초 차단과 정확히 60초 허용 시험 |

0003은 기존 행을 삭제하지 않으며 기존 초 단위 시각에 소수초를 새로 복원하지 않는다. 다운그레이드는 소수초가 유실되므로 발급을 중지한 상태에서만 실행한다. HTTP 계약과 기존 0001·0002는 변경하지 않았다. 실제 DB 이행은 이번 작업에서도 수행하지 않았다.

### 후속 검증 결과

- 관련 Python 시험 72건 통과·140건 건너뜀. 건너뛴 시험은 실제 MariaDB 연결이 필요하며 이를 통과로 계산하지 않았다.
- API 전체 Ruff 통과, 변경 Python 13파일 서식 검사 통과, mypy 338파일 통과.
- 독립 후속 리뷰에서 발급·소비·파기의 잠금 순서와 두 격리 수준 시험, DATETIME(6) 변경을 재검토했으며 추가 수정이 필요한 문제는 발견하지 못했다.
- 실제 DB 이행과 MariaDB 동시성 검증은 미완료다. 운영 배포 전 0003 이행·소수초 왕복 저장·RC/RR 혼합 경합 검증이 필요하다.

인증기록 파기 중에는 같은 운영묶음의 발급이 부모 행 잠금을 기다릴 수 있다. 다량 파기의 처리 시간은 배포 환경에서 확인한다.
