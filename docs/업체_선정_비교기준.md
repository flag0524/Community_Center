# 결제대행(PG)·문자(SMS) 업체 선정 비교 기준

- 대상: 조리읍 주민자치회(업체 선정·계약 주체)와 개발팀
- 관련: PRD Q1·Q2, TRD 6장, RQ-FUN-FN-040~042·063(결제), FN-028·029·059·061·062(문자), NF-SER-008
- 상태: 2026-11-20 작성. **업체와 가격 정보는 아직 없다.** 이 문서는 값을 지어내지 않고 무엇을 어떤 기준으로 비교할지만 정한다. 비교표의 빈칸은 업체의 공식 답변과 문서로 채운다.

## 1. 쓰는 방법

1. 후보 업체 2~3곳에 3·4장의 「업체에 확인할 것」을 그대로 보내 서면으로 답을 받는다(2장의 「필수 조건」을 하나라도 못 채우면 탈락).
2. 답을 7장의 비교표에 적고, 필수 조건을 통과한 업체만 5장의 평가표로 점수를 낸다.
3. 고른 업체와 계약하면 8장의 자료를 받아 개발팀이 어댑터를 만든다.

PRD·TRD의 후보(PG: 토스페이먼츠, KG이니시스, NHN KCP / 문자: NHN Cloud SMS, 알리고, 솔라피)는 개발 문서에 적어 둔 예시일 뿐 추천이 아니다. 후보를 늘리거나 바꿔도 된다.

## 2. 이미 정해져 있어 업체가 맞춰야 하는 것

시스템이 이미 정한 규칙이다. 업체가 이 규칙을 지원하지 못하면 후보가 될 수 없다.

| 구분 | 정해진 규칙 | 근거 |
|---|---|---|
| 결제수단 | 신용·체크카드와 실시간 계좌이체만 쓴다. 가상계좌는 쓰지 않는다 | FN-040, TRD 6장 |
| 결제 기한 | 자리를 배정받은 뒤 10분(600초). 새로고침·결제수단 변경으로 늘릴 수 없다 | FN-036 |
| 결과 검증 | 브라우저가 알려 준 값을 믿지 않고 서버가 업체 승인 API로 금액·통화·가맹점·주문번호를 대조한 뒤 반영한다 | FN-040 |
| 응답이 사라졌을 때 | 같은 주문번호로 다시 조회한다. 그래도 모르면 「결과 확인 중」으로 두고 자리를 지키며 재결제·만료를 막는다 | ADR-006 |
| 통보(웹훅) | 서명을 확인하고 원문 해시와 함께 저장하며 같은 사건이 다시 와도 한 번만 처리한다 | TRD 6장 |
| 취소(환불) | 원결제를 금액만큼 취소하고, 같은 키로 다시 불러도 한 번만 취소된다. 응답이 사라지면 키로 조회한다 | TDD 5.6 |
| 외부 호출 시간 | 연결 3초, 읽기 10초 안에 답이 없으면 「결과를 모름」으로 처리한다 | ADR-007 |
| 문자 인증번호 | 6자리, 5분 유효, 같은 번호로 60초 안에 다시 보내지 않는다 | PRD OTP 규칙 |
| 문자 문안 | 인증번호·승격 알림만 보낸다. 개인정보·결제수단은 넣지 않는다 | FN-028 |
| 문자 결과 | 「접수」와 「최종 전달」을 구분한다. 결과를 모르면 새로 보내지 않고 조회한다 | SMS-04 |

## 3. 결제대행(PG) 업체에 확인할 것

### 3.1 필수 조건(하나라도 안 되면 탈락)

| 번호 | 확인할 것 | 시스템에서 쓰는 곳 |
|---|---|---|
| P1 | 신용·체크카드와 실시간 계좌이체를 지원하는가 | 결제창 |
| P2 | 결제창을 연 뒤 서버가 승인을 요청하는 방식(서버 대 서버)이 있는가. 승인 응답에 **주문번호·금액·통화·가맹점 식별자·승인번호·승인 시각**이 모두 들어 있는가 | `approve` |
| P3 | 주문번호만으로 거래 상태를 조회하는 API가 있는가 | `lookup` |
| P4 | 웹훅 서명을 검증하는 방법이 문서로 공개되어 있는가. 같은 사건에 고유 번호를 주고, 우리가 응답하지 못하면 재전송하는가(횟수·간격) | `parse_webhook` |
| P5 | 전체 취소와 부분 취소를 모두 지원하는가. 같은 취소 요청을 다시 보내도 중복 취소되지 않게 하는 식별자(멱등키)를 받는가 | `cancel` |
| P6 | 취소 요청의 결과를 그 식별자로 조회할 수 있는가(응답이 사라진 경우) | `lookup_cancel` |
| P7 | 결제창의 유효 시간을 정할 수 있거나, 10분 안에 결제하지 않은 주문을 우리가 만료시켜도 문제가 없는가(만료 뒤 늦게 결제된 건을 어떻게 알려 주는가) | 결제 기한 |
| P8 | 실제 돈이 오가지 않는 시험 환경(샌드박스)과 시험 카드·계좌가 있는가 | 시험 |
| P9 | 실시간 계좌이체 결제를 환불할 때 PG 취소로 되돌려 주는가, 아니면 별도 계좌 환불이 필요한가 | 환불 |

### 3.2 비교할 것(점수로 평가)

| 번호 | 항목 | 확인할 것 |
|---|---|---|
| P10 | 수수료 | 카드·계좌이체별 수수료율(부가세 포함 여부), 최소 수수료, 취소 시 수수료 환급 여부, 가입비·월 이용료·보증보험 |
| P11 | 정산 | 정산 주기, 정산 입금 계좌, 거래 대조에 쓸 수 있는 정산 파일 또는 조회 API, 취소·부분취소가 정산에 반영되는 시점 |
| P12 | 신뢰 | 운영 실적(공공·지방자치단체 사례), 장애 이력과 공지 방식, 서비스 수준(가용률) 약속, 보안 인증 |
| P13 | 문서·지원 | API 문서의 완성도와 예제, 개발자 지원 창구와 응답 시간, 운영 중 장애 연락 체계(야간·휴일) |
| P14 | 가맹 절차 | 가맹 신청에 필요한 서류(주민자치회 명의로 가능한지), 심사 기간, 서버 주소 사전 등록 여부 |
| P15 | 영수증 | 승인번호·승인 시각·결제수단을 영수증에 보일 수 있는 값이 응답에 들어 있는가(FN-063) |
| P16 | 개인정보 | 위탁 계약 조항, 카드번호가 우리 서버를 거치지 않는 구조인가, 보관 기간 |

## 4. 문자(SMS) 업체에 확인할 것

### 4.1 필수 조건(하나라도 안 되면 탈락)

| 번호 | 확인할 것 | 시스템에서 쓰는 곳 |
|---|---|---|
| S1 | 센터 명의의 발신번호를 사전 등록해 쓸 수 있는가. 등록에 필요한 서류와 걸리는 기간은 | 발신번호 |
| S2 | 단건 발송과 다건(관리자 일괄) 발송을 모두 지원하는가 | `send`, 관리자 문자 |
| S3 | 보낸 문자의 **접수 결과와 최종 전달 결과**를 따로 조회하는 API가 있는가 | `lookup` |
| S4 | 요청 식별자(멱등키)를 받아 같은 요청을 한 번만 보내는가. 없다면 우리가 보낸 요청을 식별자로 다시 찾을 방법이 있는가 | 중복 발송 방지 |
| S5 | 응답이 사라진 경우(시간 초과)에 실제로 발송되었는지 조회할 수 있는가 | 결과 불명 처리 |
| S6 | 인증번호 문자가 몇 초 안에 도착하는지 약속하거나 통계를 제공하는가(인증번호는 5분만 유효) | OTP |
| S7 | 인증·안내 같은 정보성 문자는 광고 표시나 수신거부 번호 없이 보낼 수 있는가 | 문안 규칙 |
| S8 | 시험 발송이 가능한가(시험 번호, 무료 시험 건수) | 시험 |

### 4.2 비교할 것(점수로 평가)

| 번호 | 항목 | 확인할 것 |
|---|---|---|
| S9 | 요금 | 건당 단가(단문·장문), 충전 방식(선불·후불), 최소 충전액, 유효 기간, 실패 건 과금 여부 |
| S10 | 글자 수 | 단문 길이 한도와 넘으면 장문으로 바뀌는 방식, 단가 차이(문안 길이 제한은 90바이트로 둠) |
| S11 | 발송 속도 | 초당 발송 한도, 관리자 일괄 발송(수백 건) 처리 방식 |
| S12 | 도달률·품질 | 통신사별 도달률 자료, 스팸 차단 대응, 실패 사유 코드의 상세함 |
| S13 | **공급자 쪽 보관** | 보낸 문안과 수신번호를 업체가 얼마나 보관하는지, 보관을 줄이거나 삭제 요청할 수 있는지. 우리 시스템은 발송 결과가 확정되면 문안과 수신번호를 바로 파기하므로(ADR-087) 업체에 오래 남으면 이 원칙이 무의미해진다 |
| S14 | 접속 방식 | 서버 주소 사전 등록, 인증 방식, 장애 때 안내 방식, 지원 시간 |
| S15 | 개인정보 | 위탁 계약 조항, 재위탁 여부, 국외 이전 여부 |

## 5. 평가표(필수 조건을 통과한 업체만)

가중치는 개발팀의 제안값이다. 기관이 더 중요하게 보는 항목이 있으면 바꾼다. 점수는 항목마다 1~5점이고 합계는 `가중치 × 점수`의 합이다.

| 분야 | 항목 | PG 가중치 | SMS 가중치 |
|---|---|---|---|
| 기술 적합 | 2장 규칙을 얼마나 자연스럽게 지원하는가(PG: P7·P9, SMS: S4·S6), API 문서 | 30 | 30 |
| 신뢰·운영 | 공공 실적, 가용률, 장애 대응, 지원 시간 | 20 | 20 |
| 비용 | 수수료·단가, 부대 비용, 총비용 추정(연간 거래·발송량 가정으로) | 20 | 25 |
| 정산·계약 | 정산 주기, 대조 용이성, 계약 조건과 해지(PG), 발송 품질(SMS) | 20 | 15 |
| 개인정보 | 위탁 조항, 보관 기간(특히 SMS의 S13) | 10 | 10 |

총비용 추정에는 기관이 정한 이용량 가정이 필요하다(연간 수강 결제 건수·금액, 연간 문자 발송 건수). 이 값은 지금 문서에 없으므로 기관에 받아서 채운다.

## 6. 계약 전에 기관이 정할 것

- 계약 당사자와 가맹점·발신번호의 명의(조리읍 주민자치회 또는 센터)
- 결제 정산을 받을 계좌와 정산 주기
- 연간 예상 결제 건수·금액, 연간 문자 발송 건수(5장의 비용 추정용)
- 개인정보 처리 위탁 계약서의 책임자와 담당부서(PRD Q12와 같이 확인)
- 장애 때 연락할 담당자와 시간대

## 8. 업체를 고른 뒤 개발팀이 받아야 할 자료

| 자료 | 쓰는 곳 |
|---|---|
| API 규격서(승인·조회·취소·취소 조회, 문자 발송·조회)와 응답 예시, 오류 코드표 | 어댑터 구현(`PaymentGateway` 6개, `SmsSender` 2개 기능) |
| 웹훅 서명 규격과 시험용 서명 예시 | 통보 검증 시험 |
| 시험 환경 접속 정보와 시험 카드·계좌·번호 | 연동 시험(비밀값은 저장소에 넣지 않고 서버 설정으로만 둔다) |
| 서버 주소 사전 등록 절차 | 가비아 클라우드 서버 주소 확정 후 |
| 발신번호 등록 결과 | 문자 운영 |
| 정산 파일 형식 | 거래 대조 화면의 수동 대사 |

개발 순서는 업체 확정 → 어댑터 구현(모의 어댑터와 같은 계약 시험을 통과시킴) → 시험 환경 통합 시험 → 운영 전환 점검이다. 업체가 정해지기 전에는 운영 서버가 모의 어댑터를 쓰는 설정으로는 기동하지 않는다(의도된 차단).

## 9. 주의

- 이 문서의 가중치와 기준은 제안이다. 법령(전자금융거래법, 개인정보 보호법, 정보통신망법 등)에 따른 의무는 기관이 계약 전에 법무 담당자와 확인한다.
- 업체 비교는 답변서와 공식 문서로 한다. 광고 자료나 구두 설명만으로 필수 조건을 통과시키지 않는다.
