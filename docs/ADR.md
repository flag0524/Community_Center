### ADR-001
**조리읍 시범은 단일 서버·단일 DB에서 운영묶음 ID로 격리** — 대체됨(→ADR-002)

- **맥락**: 추가 결정안(RQ-DAR-NF-001)은 시범 1개소를 1서버·1 MariaDB에서 운영묶음 식별자와 서버 권한 검증으로 격리하고, 확대 시에만 기관별 DB를 두기로 했다.
- **대체 사유**: 2차 기관 회신이 "주민자치회별 독립 WAS·DB·전용 계정, 시범에도 동일 원칙 적용"으로 바꿨다.

### ADR-002
**주민자치회별 독립 WAS·DB·DB 계정** — 승인

- **맥락**: RQ-DAR-NF-001, RQ-QUR-NF-010, RQ-SER-NF-009 2차 회신. 여러 자치회의 회원·결제 데이터를 공용 DB의 센터 코드로만 나누면 안 된다.
- **결정**: 자치회 1곳 = Nginx 사이트 + API 프로세스 + 워커 + MariaDB 스키마 + 전용 DB 계정 1세트. 코드베이스는 하나이고 배포 설정만 다르다. 자치회 내부에서는 `OPER_BNDL_SN`으로 운영묶음 접근을 제어한다.
- **결과**: 센터 간 통합 조회·통계는 구조적으로 불가능하다(요구사항상 금지). 자치회 추가 시 배포 자동화(IaC 스크립트)가 필요하다. 시범 단계에서도 `OPER_BNDL_SN`은 모든 업무 테이블에 둔다.

### ADR-003
**정원 동시성은 강좌 행 비관적 잠금으로 제어** — 대체됨(→ADR-028)

- **대체 사유**: DB 스키마 설계안 v0.5의 TB_CORS에 `OCPY_CNT`·`WAIT_CNT` 카운터 컬럼이 없고, 무결성규칙 R11이 "강좌 행 잠금 후 HELD+CONFIRMED 점유수를 계산"으로 정했다. 강좌 행 잠금은 ADR-028에 그대로 남는다.

- **맥락**: FN-034. 정원 100에 500건이 동시에 들어와도 결제대기+수강확정 ≤ 정원이어야 하고, 대기자가 있으면 신규가 빈자리를 먼저 얻으면 안 된다.
- **결정**: 신청 생성·취소·만료·승격은 모두 같은 트랜잭션 패턴을 쓴다.
  1. `SELECT … FROM TB_CORS WHERE CORS_SN=? FOR UPDATE`
  2. 강좌 행의 `OCPY_CNT`(점유 수), `WAIT_CNT`(대기 수)를 읽고 판정
  3. 신청 행 INSERT/UPDATE, 카운터 갱신
  4. COMMIT
- **대안**: (a) 낙관적 잠금 + 재시도는 경합이 심한 오픈 순간에 재시도 폭주가 생긴다. (b) Redis 분산락은 ADR-004 결정(추가 인프라 없음)과 충돌한다.
- **결과**: 강좌 단위로 직렬화되므로 한 강좌에 몰리는 오픈 순간 처리량이 잠금 보유 시간에 묶인다. 잠금 구간에서 외부 호출(PG·SMS) 금지, 목표 50ms 이하. 카운터와 실제 행 수의 불일치는 야간 정합성 점검 작업이 감지한다.

### ADR-004
**백그라운드 처리는 APScheduler 단일 워커 + DB 작업 테이블** — 승인 (사용자 확정)

- **맥락**: 결제기한 만료, 대기자 승격, SMS 발송·재조회, PG 결과 재조회, 첨부 검사, 탈퇴 파기 처리가 필요하다. Redis/Celery는 자치회마다 운영 컴포넌트를 늘린다.
- **결정**: `worker` 프로세스 1개(자치회당)에서 APScheduler가 주기 작업을 돌린다. 처리 대상은 DB 상태로 찾는다(예: `PAY_DDLN_DT <= NOW()`인 결제대기). 다건 처리 시 `FOR UPDATE SKIP LOCKED`로 집어 중복 실행을 막는다. 작업 실행·결과는 TB_JOB_HSTRY에 남긴다.
- **결과**: 만료 반영 지연은 폴링 주기(10초)만큼 생긴다. 그래서 **결제 요청 API는 기한을 직접 다시 검사**해 워커 지연과 무관하게 기한 이후 결제를 막는다. 워커는 단일 인스턴스로만 띄운다(하트비트로 감시).

### ADR-005
**결제기한은 DB 시각 기준 배정시각 + 600초** — 승인

- **맥락**: FN-036. 새로고침·재접속·결제수단 변경·클라이언트 시계 조작으로 기한이 바뀌면 안 된다.
- **결정**: 자리 배정 트랜잭션에서 `ASGN_DT = NOW(6)`, `PAY_DDLN_DT = ASGN_DT + INTERVAL 600 SECOND`를 저장한다. 화면 카운트다운은 API가 내려준 `PAY_DDLN_DT`와 `server_now`의 차이로 계산한다. 판정은 항상 DB 시각과 비교한다.
- **결과**: 재신청·재배정은 새 행/새 배정시각으로만 기한을 얻는다. 감면 승인 지연은 기한을 늘리지 않는다(ADR-012).
- **보정(ADR-027)**: 컬럼명은 `TB_ATNLC_APLY.SEAT_ALTMNT_DT`(자리배정일시)·`STLM_DDLN_DT`(결제기한일시)다. 시각은 UTC로 저장한다(SEAT-01).

### ADR-006
**결제 결과 불명 시 `결과 확인 중` 상태로 자리 동결** — 승인

- **맥락**: FN-042. 응답 유실·통신 실패만으로 성공·실패를 단정하면 이중 결제나 잘못된 자리 반환이 생긴다.
- **결정**: PG 승인 요청 후 응답을 못 받으면 결제를 `확인중(CHKNG)`으로 두고 원주문번호로 즉시 재조회 최대 3회. 그래도 미확정이면 `확인중` 유지. 이 상태에서는 재결제·만료·다음 순번 배정을 모두 막는다. 익영업일까지 운영자가 PG 관리자에서 수동 대사한다. 기한 이후 승인된 거래는 중복 배정 여부를 확인한 뒤 같은 거래를 취소·환불한다.
- **결과**: 만료 워커는 `확인중` 결제가 걸린 신청을 건너뛴다. 대시보드에 "승인 결과 확인" 업무로 노출한다(FN-066).

### ADR-007
**SQLAlchemy 동기 세션과 명시적 트랜잭션** — 승인 (2026-10-31 사용자 확정)

- **맥락**: 핵심 로직이 `FOR UPDATE` 잠금 순서와 트랜잭션 경계에 의존한다. 동시 500명은 동기 워커 다수로 충분하다.
- **결정**: FastAPI 경로 함수는 `def`(동기)로 쓰고 Gunicorn 워커 × 스레드로 동시성을 얻는다. 서비스 계층은 `with session.begin():` 블록으로 트랜잭션을 명시한다. PG·SMS 호출은 트랜잭션 밖에서 한다.
- **대안**: async SQLAlchemy + aiomysql은 잠금·세션 수명 디버깅 비용이 크고 이득이 적다.
- **결과**: 외부 HTTP 호출은 `httpx` 동기 클라이언트 + 타임아웃(연결 3초, 읽기 10초)을 쓴다.

### ADR-008
**서버 저장 세션 + HttpOnly 쿠키 (JWT 미사용)** — 승인 (2026-10-31 사용자 확정)

- **맥락**: FN-024, FN-062, RQ-SER-NF-008. 로그아웃·비밀번호 재설정·탈퇴 시 즉시 세션을 무효화해야 하고, 회원 30분·관리자 15분 유휴 만료가 있다.
- **결정**: 로그인 시 무작위 256비트 토큰을 발급하고 해시를 TB_LGN_SSN에 저장한다. 쿠키는 `HttpOnly; Secure; SameSite=Lax`. 요청마다 `LAST_ACCES_DT`를 갱신하고 유휴 시간을 넘으면 거부한다. 상태 변경 요청은 CSRF 토큰(더블 서브밋)을 요구한다. 주민·관리자 쿠키 이름과 도메인을 분리한다.
- **결과**: 요청마다 세션 조회 1회가 추가된다(PK 조회라 비용 작음).

### ADR-009
**외부 연동은 어댑터 인터페이스** — 승인 (사용자 확정: TBD + 후보 병기)

- **결정**: `PaymentGateway`, `SmsSender`, `FileScanner` 프로토콜을 정의하고 `MockPaymentGateway`, `MockSmsSender`를 dev/stg 기본으로 둔다. 공급자 계약 후 구현체를 추가하고 설정(`PG_PROVIDER=toss` 등)으로 고른다.
- **결과**: 도메인 로직은 공급자 SDK를 직접 import하지 않는다. 웹훅 경로는 `/api/pg/webhook/{provider}`.

### ADR-010
**결제수단은 카드·실시간 계좌이체, 가상계좌 제외** — 승인

- **근거**: FN-016, FN-040. 가상계좌는 입금 시점이 10분 안에 확정되지 않는다.

### ADR-011
**본인확인은 SMS 6자리 OTP로 통일** — 승인

- **근거**: FN-029, FN-061, FN-062. 5분 유효, 5회 오류 무효, 재전송 60초. PASS·이메일·카카오 인증은 1차 제외.
- **결과**: 실명 확인 수준은 "휴대전화 소지 확인"이다. 이름은 자기 신고값이므로 이름 변경은 관리자 검토로 처리한다(FN-031).

### ADR-012
**감면은 접수 전 증빙 제출·관리자 심사** — 승인

- **근거**: FN-038, FN-039. 행정정보 자동조회 연계는 1차 제외.
- **결정**: 회원이 기수별로 사전 감면 심사(TB_RDCT_BFHD_SRNG)를 신청하고 증빙을 올린다. 담당자 승인 결과는 판정 이력(TB_RDCT_HSTRY)으로 남는다. 신청 생성 시점에 유효한 승인 판정이 있으면 서버가 50%를 적용한다. 판정과 증빙 연결은 불변이며 재판정은 새 행이다.
- **결과**: 접수 중 심사를 기다리며 10분 기한이 흐르는 상황을 원천 차단한다.
- **보정(ADR-027)**: 사전 승인은 TB_RDCT_BFHD_SRNG(`DS.APPROVED`)에, 신청별 적용 판정·금액은 TB_RDCT_HSTRY(`ATNLC_APLY_SN` 필수)에 남는다. 적용 시 회원 행을 잠가 기수당 1강좌를 확보하고, 취소·환불만으로 감면권을 자동 복구하지 않는다(RDCT-BFHD-02).

### ADR-014
**멱등키 적용** — 승인

- **근거**: FN-033, FN-041, FN-046, FN-059.
- **결정**: 클라이언트는 신청·결제요청·환불신청·문자발송 요청에 `Idempotency-Key`(UUID) 헤더를 보낸다. 서버는 `(행위자, 키)`로 요청 본문 해시와 결과를 저장한다. 같은 키·같은 해시면 저장된 결과를 반환하고, 같은 키·다른 해시면 409 충돌을 반환한다. PG 웹훅은 공급자 통보 ID + 본문 해시로 같은 방식을 적용한다.

### ADR-027
**논리 데이터 모델은 DB 스키마 설계안 v0.5(45테이블)를 기준으로 한다** — 승인 (사용자 제공 문서)

- **맥락**: 원천 추적표에는 테이블 이름만 있어 TDD 0.1의 6장 컬럼은 개발팀이 만든 초안이었다. 이후 테이블명세 xlsm v0.4에서 생성한 [PRJ_2026_002_DB스키마_설계안.md](PRJ_2026_002_DB스키마_설계안.md) v0.5(2026-10-28)가 45테이블·610컬럼·184FK·코드 40집합·무결성규칙 135개를 정의했다.
- **결정**
  1. 테이블·컬럼·타입·키·FK·공통코드·무결성규칙은 스키마 설계안을 따른다. TDD는 컬럼을 복사하지 않고 스키마 설계안 절 번호를 참조한다.
  2. 일련번호는 `NUMERIC(22,0)`(TB_STLM.STLM_SN만 `NUMERIC(10,0)`)이며 API에는 문자열로 전달한다. BIGINT 축소는 하지 않는다(N08). 자동증가·조건부 UNIQUE·CLOB 매핑 등 물리 DDL은 MariaDB 버전 확인 후 정한다(N10).
  3. 코드 컬럼은 `CHAR(12)`에 `그룹.값`(예: `ES.HOLD`)을 저장하고 TB_COM_CD FK와 접두부 CHECK를 함께 건다(N06, R01). TDD 0.1의 "코드는 DB FK 없이 애플리케이션 검증" 방침을 바꾼다.
  4. 날짜는 `CHAR(8)` YYYYMMDD, 시각은 `CHAR(6)` HHMMSS, 시스템 사건시각은 UTC 저장·한국시간 표시다(N07).
  5. 공통 컬럼은 `REG_DT`, `MDFCN_DT`, `RCRD_VER`(낙관적 잠금)다.
  6. TDD 0.1의 `[보완]` 테이블 TB_CORS_PLAN·TB_WRKR_HRTBT는 철회한다. 강의계획은 `TB_CORS.LCTR_PLAN_CN` + 계획서 파일(`FP.PLAN`), 워커 생존 감시는 DB 밖(systemd watchdog + 상태 파일)에서 한다.
  7. 결제 결과 불명(ADR-006)은 신청 `ES.HOLD` + 결제 `PS.PENDING`으로 표현한다. 별도 신청 상태는 두지 않는다(SEAT-02).
  8. 코드가 있다는 사실만으로 기능을 켜지 않는다. `AU.MBR_W`(회원수정), `PM.VIRTUAL`(가상계좌), `AP.ADMIN`·`TB_LGN_SSN.ADD_CERT_DT`(관리자 추가인증)는 현재 수행방안상 비활성이다.
- **결과**: 테이블은 45개로 고정한다. 새 테이블·코드값이 필요하면 스키마 설계안을 먼저 개정한다. 스키마에 근거가 없는 권한·코드 매핑(감면 심사·공통코드 관리·보존관리 권한, 연락처 콘텐츠 유형 등)은 PRD 6장 확인 항목으로 둔다.

### ADR-028
**정원 점유는 카운터 없이 강좌 행 잠금 아래 신청 행을 집계** — 승인 (스키마 R11·SEAT-01·SEAT-02)

- **맥락**: FN-034. ADR-003의 강좌 행 잠금은 유지하되, 스키마 설계안에 점유·대기 카운터 컬럼이 없다.
- **결정**: 신청 생성·취소·만료·승격·폐강은 모두 같은 패턴을 쓴다.
  1. `SELECT … FROM TB_CORS WHERE OPER_BNDL_SN=? AND CORS_SN=? FOR UPDATE`
  2. 같은 트랜잭션에서 `APLY_STTS_CD IN ('ES.HOLD','ES.CONFIRM')` 행 수(점유)와 `'ES.WAIT'` 행 수(대기)를 센다. 인덱스는 `IX_ATNLC_APLY_01`을 쓴다.
  3. 신청 행 INSERT/UPDATE
  4. COMMIT
- **대안**: 카운터 컬럼은 집계 비용이 없지만 스키마에 없고 실제 행 수와 어긋날 수 있다.
- **결과**: 강좌당 신청 행은 정원+대기정원 수준이라 집계 비용이 작다. 잠금 구간 외부 호출 금지와 목표 50ms 이하는 그대로다. 야간 카운터 정합성 점검은 필요 없어진다.

### ADR-029
**물리 DDL은 설계안에서 생성하고 시퀀스·생성 컬럼·고정 문자셋으로 구현** — 승인 (스키마 1.2·9.1, TDD 6.1)

- **맥락**: 스키마 설계안은 일련번호 생성 방식, 조건부 UNIQUE 구현, 문자셋·정렬규칙을 "물리 DDL에서 정한다"고 미뤘다. 610개 컬럼을 손으로 옮기면 틀리기 쉽다.
- **결정**: 아래 다섯 가지를 따른다.
  1. **생성**: 설계안 4절의 표를 읽어 마이그레이션 SQL을 생성한다(`app.tools.generate_ddl`). 생성기가 문서의 숫자(45 테이블·610 컬럼·184 외래키·코드 40집합 182값)와 내부 참조·타입 일치를 검사하고 어긋나면 만들지 않는다. 만든 SQL은 Alembic `0001`이 실행한다. 배포한 뒤에는 이 파일을 고치지 않고 새 버전을 더한다.
  2. **일련번호**: 단일 숫자 기본키마다 `SEQUENCE SQ_<테이블>`을 두고 컬럼 기본값을 `NEXTVAL`로 한다(41개). 컬럼 타입은 `DECIMAL(22,0)`을 유지하고 BIGINT로 줄이지 않는다. 연결 테이블의 복합키와 코드 기본키에는 시퀀스가 없다. 시퀀스는 `CACHE 1000`이라 재시작 뒤 번호에 구멍이 생길 수 있고 번호가 연속임을 가정하지 않는다.
  3. **조건부 UNIQUE**(`UQ_FILTER_ATNLC_APLY_01`, `UQ_FILTER_STLM_01`): MariaDB에는 부분 인덱스가 없어 `PERSISTENT` 생성 컬럼 `ZF_*`(조건이 참이면 1, 아니면 NULL)를 UNIQUE 키에 더한다. NULL은 중복으로 보지 않아 취소 건은 몇 개든 쌓이고 유효 건만 하나로 제한된다. 생성 컬럼의 식은 `IN` 목록을 쓸 수 없어(오류 1901) `OR`로 푼다. 이 컬럼 2개는 설계안의 610개에 더해진다.
  4. **문자셋·시각**: `utf8mb4` / `utf8mb4_unicode_ci`, 서버 시간대는 UTC, 시각 컬럼 기본값은 `CURRENT_TIMESTAMP`다.
  5. **제약**: 문서의 `YN`(18건)과 `CD`(36건) 규칙을 `CHECK`로 만든다(코드 접두부 검사 + `TB_COM_CD` 외래키). 서술형 규칙 중 문서가 DB 제약으로 분명히 적은 것(R01·R04·R05·R06·R08·R09·R10·R13·R14·R16·R18·R19·R21, SEAT-01·RFND-01·RCRT-01·STAT-04·SMS-02·SMS-03·AUTH-01) 33건과, R27(일련번호 양수, 정렬순서·횟수 0 이상)을 컬럼 도메인으로 자동 만든 81건을 더해 `CHECK`는 모두 168건이다. 문서가 서비스 계층 규칙으로 분류한 것(예 R15 환불 요청자)은 옮기지 않는다. 외래키는 모두 `RESTRICT`다(생성 컬럼의 기반 컬럼에는 `CASCADE`를 쓸 수 없기도 하다).
- **개발 환경 주의**: Windows용 MariaDB의 기본은 테이블 이름을 소문자로 저장한다(`lower_case_table_names=1`). 개발 DB는 `2`로 두어 이름을 보존하지만 비교는 여전히 대소문자를 구분하지 않아, Ubuntu 운영에서만 나는 대소문자 오류를 숨길 수 있다. 배포 전에 Ubuntu에서 DB 시험을 한 번 더 돌린다.
- **대안**: 손으로 쓰는 DDL은 문서와 어긋나도 모른다. 부분 인덱스 대신 서비스 계층 검사만 쓰면 동시 신청에서 중복이 생긴다.
- **결과**: 문서와 DB의 일치를 시험이 자동으로 확인한다. 문서를 고치면 생성기를 다시 돌리고 배포 전이면 파일을 갱신, 배포 후면 새 마이그레이션을 더한다.

### ADR-030
**백엔드 DB 접근은 SQLAlchemy Core와 생성된 테이블 정의, 운영묶음은 배포 설정의 사이트 식별자** — 승인 (ADR-001·002, 스키마 C03·C04, TDD 2.3·4.5)

- **맥락**: 스택은 SQLAlchemy 2 동기 세션이다. 테이블이 45개·컬럼이 610개이고 문서가 컬럼명 명시·`SELECT *` 금지·잠금 순서를 요구한다. 운영묶음은 요청이 아니라 서버가 정해야 한다(R26).
- **결정**: 아래 다섯 가지를 따른다.
  1. **ORM 클래스를 만들지 않는다.** SQLAlchemy Core의 `Table` 정의를 설계안에서 생성한다(`app/db/tables.py`). 서비스는 `select`·`insert`·`update`로 컬럼을 명시해 쓴다. 생성 파일은 서식 도구에서 제외하고 생성기가 서식을 책임져 항상 같은 출력이 나온다.
  2. **요청 하나가 트랜잭션 하나다.** `get_db` 의존성이 응답 전에 커밋하고 예외가 나면 되돌린다. 세션은 `autoflush`를 끄고 접속마다 시간대를 UTC로 고정한다.
  3. **운영묶음은 배포 설정이 정한다.** ADR-002대로 배포 1곳은 사이트 1개를 맡으므로 환경변수 `JORI_SITE_ID`로 `TB_OPER_BNDL`에서 묶음을 한 번 찾아 기억한다. 요청의 호스트·헤더·경로·본문은 쓰지 않는다. 사이트가 없거나 사용 중지면 사용자 잘못이 아니라 배포 오류(500)다.
  4. **낙관적 잠금**: 갱신은 키(기본키+묶음)와 화면이 읽은 `RCRD_VER`가 모두 맞을 때만 하고 버전을 1 올리며 수정 시각을 남긴다. 행이 없으면 404, 버전이 다르면 409(`VERSION_CONFLICT`)다.
  5. **멱등 삽입**: 삽입이 (묶음, 멱등키) 유일키 때문에 실패하면 기존 행을 읽어, 같은 요청이면 그 행을 돌려주고 다른 요청이면 409(`IDEMPOTENCY_CONFLICT`)다. 다른 유일키(예 유효 신청 중복)가 막은 것이면 그대로 올려 호출자가 업무 오류로 바꾼다. InnoDB는 실패한 문장만 되돌리므로 저장점을 쓰지 않는다.
- **오류와 로그**: 예상하지 못한 오류는 응답에 내용을 싣지 않고, 로그에도 예외 메시지(SQL·개인정보가 들어 있을 수 있다) 없이 예외 종류와 요청 ID만 남긴다(C10).
- **대안**: ORM은 매핑 클래스 610개 분량을 따로 관리해야 하고 잠금·묶음 조건이 숨는다. 요청 호스트로 묶음을 정하면 클라이언트가 조작할 수 있다.
- **결과**: 새 테이블 정의는 마이그레이션과 같은 생성기에서 함께 나와 어긋나지 않는다. 한 배포에서 여러 묶음을 서비스해야 하는 요구가 생기면 묶음 판정만 바꾼다.

### ADR-031
**로그인·세션 구현은 서버 세션과 로그인 전 CSRF 시드 쿠키, 관리자 잠금은 정책 확정 전까지 설정값** — 승인 (ADR-008, DV17, 스키마 AUTH-03~05, PRD Q28)

- **맥락**: ADR-008과 DV17이 서버 세션·HttpOnly 쿠키·세션 토큰 해시 파생 CSRF를 정했다. 그러나 세션 테이블에는 CSRF 컬럼이 없고, 로그인 요청도 CSRF 토큰이 필요한데 그때는 세션이 없다. 관리자 로그인 실패 제한 수치는 기관 정책(Q28)이 없다.
- **결정**: 아래 여섯 가지를 따른다.
  1. **세션 토큰**은 256비트 무작위 값이고 서버에는 SHA-256 해시(`TKN_HASH_VL`)만 둔다. 세션은 회원 또는 관리자 중 정확히 한 대상이고 회원은 운영묶음이 필요하다. 요청마다 폐기·만료·계정 상태(회원 `MS.ACTIVE`, 관리자 `USE_YN=Y`)를 다시 확인한다.
  2. **CSRF 토큰**은 저장하지 않고 파생한다. 로그인 뒤에는 `HMAC(비밀키에서 파생한 키, "session:" + 세션 토큰 해시)`이고, 로그인 전에는 `GET /auth/session`이 무작위 시드를 HttpOnly 쿠키로 내리고 `HMAC(..., "anon:" + 시드)`를 토큰으로 준다(더블 서브밋). 회원·관리자는 시드 쿠키 이름이 다르다.
  3. **쿠키**는 `HttpOnly; Secure; SameSite=Lax; Path=/`이고 회원 `jori_session`, 관리자 `jori_admin_session`으로 이름이 다르다. 로그아웃은 쿠키를 지우고 몇 번 불러도 같은 결과다.
  4. **유휴 만료**는 회원 30분, 관리자 15분이다. `EXPRY_DT`가 현재 유휴 마감이고 사용자 조작(관리자 `extend`)이 있을 때만 뒤로 민다. `GET /auth/session`은 연장하지 않는다.
  5. **회원 잠금**은 직전 10분의 실패 5회에 15분이다(AUTH-04). 계정 행을 잠근 채 실패 이력으로 센다. 없는 아이디·탈퇴 계정은 같은 응답과 같은 계산(더미 해시 검증)을 하고 이력은 남기지 않는다. 실패 이력과 잠금은 오류 응답을 내기 전에 커밋한다(`get_db`는 예외가 나면 되돌린다).
  6. **관리자 잠금 수치는 지어내지 않는다.** `JORI_ADMIN_LOCK_FAILURES`와 `JORI_ADMIN_LOCK_MINUTES`를 함께 설정하면 그대로 적용하고, 없으면 실패 이력만 남기고 잠그지 않는다. 정책이 정해지면 값만 설정한다.
- **비밀값**: `JORI_SECRET_KEY`는 32자 이상이고 CSRF·OTP 등 용도별로 파생해 쓴다. 비밀번호는 PBKDF2-HMAC-SHA-256이고 반복 횟수를 해시와 함께 저장해 설정을 올려도 옛 해시를 검증한다(기본 600,000).
- **적용 순서**: 이번에는 인증 엔드포인트가 스스로 CSRF를 검증한다. 나머지 엔드포인트의 세션·CSRF 검증은 각각 구현할 때 붙이고, 모두 끝난 뒤 전역 검증으로 바꾼다.
- **대안**: 세션 테이블에 CSRF 컬럼을 더하려면 스키마 개정이 필요하다. 로그인 전 CSRF를 생략하면 로그인 CSRF 공격이 가능하다.
- **결과**: 새 테이블·컬럼 없이 문서의 결정을 모두 지킨다. 관리자 잠금 정책이 없는 동안 관리자 로그인은 무차별 대입에 약하므로 운영 전에 Q28을 확정해야 한다.

### ADR-032
**OTP는 계정 존재를 숨기는 가짜 인증 행과 앱 시계 기준 시각, 문자 발송은 커밋 뒤 어댑터 호출** — 승인 (TDD 8.1·8.2, 스키마 AUTH-01~03·OTP-SMS-01, ADR-009)

- **맥락**: OTP 응답은 대상 회원이 있든 없든 같아야 하고(FN-061), 인증번호 원문은 DB·로그에 남지 않으며, 문자 공급자는 아직 정해지지 않았다(Q2~Q4).
- **결정**: 아래 여섯 가지를 따른다.
  1. **가짜 인증 행.** 아이디 찾기·비밀번호 재설정에서 일치하는 정상 회원이 없으면 문자는 보내지 않고 대상 회원이 없는 인증 행만 만든다. 확인 단계도 실제와 같은 모양(틀린 코드는 200 `verified:false`와 남은 횟수)으로 응답해 회원 존재를 알 수 없다. 스키마 AUTH-01은 "다른 목적은 정확한 대상 계정이 필수"라고 하지만 가짜 행은 어떤 업무 API도 통과하지 못하므로 이 규칙을 해치지 않는다.
  2. **코드와 암호화.** 인증번호는 6자리 난수이고 DB에는 `HMAC(비밀키에서 파생한 키, 요청 번호 + 코드)`만 둔다. 전화번호는 AES-256-GCM이다. 가입 단계의 이름은 인증 테이블에 이름 컬럼이 없고 가입 요청에도 이름이 없어서 전화번호와 함께 같은 암호문 안에 넣는다(`{"p": 전화, "n": 이름}`). 암호문은 용도별 연관 데이터로 묶어 다른 용도의 값을 옮겨 붙여도 열리지 않는다.
  3. **제한.** 유효 5분, 입력 오류 5회 무효, 재전송 60초다. 재전송은 서명 쿠키(모든 요청)와 같은 회원·목적의 직전 요청 시각(회원 대상)으로 이중 제한한다. 쿠키만 지워도 피해자에게 문자가 쏟아지지 않는다. 전화번호 단위 제한은 HMAC 검색키 컬럼이 필요해 스키마 개정 요청 대상이다.
  4. **시각은 앱 시계 하나로 통일한다.** `REG_DT`·`EXPRY_DT`·`FAIL_DT`·`LAST_ACT_DT` 같이 판정에 쓰는 시각은 모두 앱이 넣는다. DB 기본값(`CURRENT_TIMESTAMP`)과 섞으면 앱 서버와 DB 서버의 시계가 어긋날 때 재전송 제한이 풀린다(시험에서 실제로 발생). 기록용인 `MDFCN_DT`는 DB 시계를 쓰지만 판정에는 쓰지 않는다.
  5. **문자 발송.** 인증 요청·문자 요청·수신 대상을 한 트랜잭션으로 커밋한 뒤에 어댑터를 호출한다. 공급자 호출은 DB 잠금·트랜잭션 밖이다. 결과는 접수(`SS.SENDING`), 거절(`SS.FAIL`), 알 수 없음(`SS.UNKNOWN`)으로 이력에 남기고 최종 성공(`SS.SENT`)은 워커가 조회로 확정한다. 거절이면 기록을 먼저 커밋하고 500으로 답하며 자동으로 다시 보내지 않는다.
  6. **어댑터.** 문자는 `SmsSender` 규약 뒤에 두고 공급자가 정해질 때까지 모의 구현만 둔다. 발신번호도 미정이라 값을 지어내지 않고 `TBD`로 표시한다. 설정으로 모의가 아닌 공급자를 고르면 시작하지 못한다.
- **남은 위험**: 회원 대상은 DB 직전 요청으로, 가짜 행은 쿠키로만 재전송을 제한하므로 쿠키를 지우고 두 번 요청하면 429 여부로 회원 존재를 추측할 수 있다. 전화번호 검색키 없이는 막을 수 없고 문서가 이를 감수했다. 인증 요청 번호는 순차라 추측할 수 있지만 요청마다 5회까지만 시도할 수 있어 위험이 작다.
- **결과**: 새 테이블·컬럼 없이 문서를 지킨다. 가입·아이디 찾기·비밀번호 재설정(다음 단계)은 이 인증 행을 같은 검사로 소비하고 사용 완료 표시를 업무 확정과 같은 트랜잭션에서 한다.

### ADR-033
**가입·아이디 찾기·비밀번호 재설정은 인증 소비와 업무 확정을 한 트랜잭션으로, 필수 약관이 하나도 없으면 가입을 거절** — 승인 (TDD 8.1, 스키마 4.16·AUTH-01·AUTH-05, R17·R22, ADR-032)

- **맥락**: 이 세 기능은 OTP 인증 행을 소비하며 업무를 확정한다. 어떤 약관이 필수인지는 문안마다 `ESNTL_YN`이 정하는데, 필수 문안이 하나도 게시되지 않은 때의 동작은 문서에 없다.
- **결정**
  1. **소비 규칙.** `consume_otp`가 인증 행을 잠그고 목적·운영묶음·만료·실패 횟수·코드를 검사한다. 목적이나 운영묶음이 다르면 없는 인증과 같이 `OTP_INVALID`다. 틀린 코드의 실패 횟수는 오류 응답 전에 커밋한다. 사용 완료 표시(`mark_used`)는 업무 변경과 같은 트랜잭션이다.
  2. **가입.** 이름·전화번호는 암호문에서 꺼낸다. 약관은 같은 운영묶음에서 지금 게시 중(게시 여부·시작·종료)인 문안만 인정하고, 게시 중인 버전과 문안 해시(R17)가 맞아야 동의를 받는다. 필수 유형(게시된 문안의 `ESNTL_YN`)에 동의가 없으면 거절한다. 아이디 중복(MariaDB 1062)은 `JOIN_LOGIN_ID_TAKEN`이며 인증은 소비되지 않아 다른 아이디로 다시 시도할 수 있다. 가입 성공은 회원·동의 이력·사용 완료·감사 기록을 한 번에 확정하고 로그인시키지는 않는다.
  3. **필수 약관이 하나도 게시되지 않으면 가입을 거절한다(문서에 없는 보수적 규칙).** 그대로 두면 약관 동의 없이 가입이 되기 때문이다. 약관을 게시하기 전에는 가입이 열리지 않는다. 운영에서 다르게 하려면 이 결정을 새 ADR로 대체한다.
  4. **아이디 찾기.** 앞 2글자만 보이고 나머지는 `*`이며 마지막 한 글자는 항상 가린다(짧은 아이디가 통째로 드러나지 않게). 가짜 인증은 실제와 같은 모양으로 "없음"만 답한다.
  5. **비밀번호 재설정.** 인증된 회원의 아이디와 입력한 아이디가 다르면 틀린 코드처럼 실패 횟수를 올리고 거절한다. 성공하면 비밀번호 해시를 바꾸고 그 회원의 살아 있는 세션을 모두 폐기한다(다른 회원 세션은 그대로).
  6. **감사.** `TB_JOB_HSTRY`에 INSERT만 한다. 비밀번호·인증번호·전체 아이디는 기록하지 않는다.
- **남은 위험**: 같은 유형에 게시된 버전이 여럿이면 가입자가 고른 버전을 인정한다. 같은 인증 번호를 두 요청이 동시에 소비하는 경쟁은 행 잠금으로 막히지만 단일 연결 시험 환경에서는 검증하지 못했다(Ubuntu DB 시험에서 확인).
- **결과**: 새 테이블·컬럼 없이 구현했다. 변이 검사 25건 중 4건이 처음에 살아남아 시험 3건을 보강했고(미게시 약관, 필수 문안 부재, 다른 운영묶음 인증) 모두 잡힌다.

### ADR-034
**공개 조회는 게시 중인 것만 보여 주고, 저장 위치가 없는 안내 글·연락처 필드는 지어내지 않고 비운다** — 승인 (TDD 5절 GET /terms·/contents·/site/contact, RQ-FUN-FN-006·011·055·072, R9, Q23·Q24)

- **맥락**: 로그인 없이 읽는 약관·안내 글·연락처의 저장 위치를 문서가 일부만 정했다. 연락처는 저장 위치가 없고(Q23), 안내 글은 CT 코드가 소개·연혁뿐이다(R9 미반영).
- **결정**
  1. **게시 판정.** 약관·안내 글은 같은 운영묶음에서 게시 여부(`PSTG_YN`)가 Y이고 게시 시작 이상·종료 미만인 문안만 보인다. 앱 시계를 기준으로 하며 시작 시각 정각은 보이고 종료 시각 정각은 보이지 않는다. 후보가 여럿이면 가장 늦게 만든 문안이다. 버전을 지정해도 게시 중이 아니면 404다(초안·종료된 문안을 드러내지 않는다).
  2. **약관 시행일.** 게시 시작 시각을 한국 날짜로 바꿔 준다. 시작 시각이 비어 있으면 null이다.
  3. **안내 글.** 사용자가 정한 대로 `center-history`만 `CT.HISTORY`에서 `CONTS_ID`가 같은 문안으로 제공한다. `guide-apply`·`guide-refund`·`center-facility`는 R9가 반영될 때까지 어떤 유형으로 저장돼 있어도 404다. 본문(`CONTS_CN`)은 `{"subtitle", "sections"}` 모양의 JSON이고 응답과 같은 camelCase다. 모양이 틀리면 500이다. 수정일은 수정 시각(없으면 등록 시각)의 한국 날짜다.
  4. **연락처.** 운영묶음의 `TELNO`·`ADDR`만 채우고 나머지 필드(관리실 전화, 우편번호, 층, 운영시간, 주차)는 null이다. 화면은 null이면 '확인 필요'로 표시한다. Q23이 닫히면 채운다.
  5. **홈**은 강좌·게시판 조회가 있어야 만들 수 있어 B4-2c에서 한다.
- **대안**: 연락처를 콘텐츠 행(JSON)으로 임시 저장하거나 안내 글 4종을 소개·연혁 유형에 나누어 저장하는 방법이 있었으나, 스키마 개정 때 이관이 필요하고 R9 요청서의 "임시 저장하지 않는다" 결정을 뒤집어서 택하지 않았다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 변이 검사 18건 중 처음 3건이 살아남아 시험을 보강했고 모두 잡힌다.

### ADR-035
**강좌 공개 조회는 기준 기수 안의 공개·마감·운영중 강좌만 보여 주고, 접수·교육 상태는 서버가 판정한다** — 승인 (TDD 5.2·6절 GET /courses, RQ-FUN-FN-012~015, RQ-QUR-NF-008, ADR-028)

- **맥락**: 목록 응답은 "기준 분기"를 담아야 하는데(FN-012) 어떤 기수를 기준으로 삼는지, 어떤 상태의 강좌가 주민에게 보이는지, 강사 이름을 어디까지 내보내는지를 문서가 정하지 않았다.
- **결정**
  1. **기준 기수.** 사용 중(`USE_YN=Y`)인 기수 가운데 교육이 끝나지 않은(종료일 ≥ 한국 오늘) 것 중 교육 시작이 가장 이른 기수다. 모두 끝났으면 가장 최근에 끝난 기수다. 기수가 없으면 목록은 비고 기준 기수도 null이다. 상세와 강의계획은 기준 기수와 무관하게 공개된 강좌면 보인다.
  2. **공개 범위.** 강좌 상태가 `CS.OPEN`·`CS.CLOSE`·`CS.RUN`인 강좌만 보인다. `CS.DRAFT`·`CS.END`·`CS.CANCEL`은 목록·상세·강의계획 모두 404다. 폐강은 회원 본인의 신청 화면에서 알린다(TDD 5.1).
  3. **접수 상태.** `CS.OPEN`이고 접수 시작 시각 이상·종료 시각 미만이면 접수중, 시작 전이면 접수예정, 그 밖(수동 마감·운영중·종료 시각 이후)은 접수마감이다. 종료 시각 정각은 마감이며 신청 생성(TDD 5.2)이 같은 규칙을 쓴다. 상태 거름은 같은 판정을 SQL로 써서 쪽 나누기와 전체 건수가 맞는다. 교육 상태는 교육 시작·종료일을 한국 날짜와 견주며 종료일 당일까지 교육중이다.
  4. **잔여석과 대기.** 잔여석은 모집 인원에서 `ES.HOLD`·`ES.CONFIRM` 신청 수를 뺀 값이고 0 밑으로 내려가지 않는다(ADR-028). 대기 수는 `ES.WAIT`만 센다. 조회는 잠금 없이 읽으므로 같은 순간의 신청과 약간 어긋날 수 있고, 정원 판정은 신청 생성이 잠금 아래에서 다시 한다.
  5. **강사 이름.** 승인(`IS.APPROVE`)이고 공개(`RLS_YN=Y`)로 둔 강사만 이름이 나가고 검색에도 걸린다. 그렇지 않으면 이름은 null이고 검색으로도 찾을 수 없다.
  6. **분류.** 사용 중이고 삭제되지 않은 센터별 분류만 나간다. 연결되지 않았거나 중지·삭제된 분류는 null이다(자동 매핑하지 않는다, 스키마 1.2).
  7. **일정.** 적용 종료일이 한국 오늘 이상인 일정 행만 모아, 같은 시작·종료 시각의 요일을 한 줄로 묶고 월~일 순으로 준다. 반 구분(`label`)은 저장 위치가 없어 null이다. 강의실은 일정에 걸린 시설 이름을 중복 없이 쉼표로 잇는다.
  8. **계획서 파일.** 용도 `FP.PLAN`이고 검사 상태 `FS.SAFE`인 첨부 중 정렬 순서가 앞선 하나만 알린다. 계획이 있다는 표시(`hasPlan`)는 공백 아닌 계획 본문이나 이런 파일이 있을 때 참이다.
  9. **검색·페이지.** 검색어는 앞뒤 공백을 자르고 `%`·`_`를 글자로 취급한다. 목록은 강좌 번호 순이다.
- **남은 위험**: 기준 기수 규칙은 운영 경험으로 바꿀 수 있다(여러 기수가 동시에 접수 중이면 가장 이른 기수만 보인다). 이 경우 기수 선택 파라미터가 필요하며 계약 개정이 따른다. 잔여석은 잠금 없는 읽기라 목록을 본 뒤 신청하면 대기가 될 수 있다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 일정 행의 시작·종료 시각 사이 겹침과 휴보강(`TB_CORS_SCHDL_CHG`)은 상세에 아직 반영하지 않았다(계약에 필드가 없다).

### ADR-036
**게시판·홈·파일 내려받기는 소유 업무의 지금 공개 상태로 판정하고, 저장 위치가 없는 홈 비주얼은 비운다** — 승인 (TDD 5·6절, TRD 4.4·4.5, RQ-FUN-FN-006·054, RQ-SER-NF-002, R14·R24)

- **맥락**: 게시물 목록·상세·첨부·홈 콘텐츠를 로그인 없이 읽게 한다. 공개 판정이 목록과 파일 내려받기에서 달라지면 비공개가 된 글의 첨부가 새어 나간다(TRD 4.4는 같은 판정을 쓰라고 한다).
- **결정**
  1. **공개 글 판정은 한 곳에 둔다.** 게시판이 사용 중이고, 글이 원글이며, 삭제·비공개가 아니고, 게시 시작 이상·종료 미만이다. 목록·상세·홈 공지·파일 내려받기가 모두 `public_post_conditions`를 쓴다. 게시일은 게시 시작 시각이 있으면 그것, 없으면 등록 시각이다. 순서는 상단공지, 게시일 내림차순, 번호 내림차순이다.
  2. **이 엔드포인트가 여는 게시판은 `notice`·`news`·`resources`·`gallery`·`faq` 다섯이다.** 질문과 답변·수강후기는 작성자와 비공개 판정이 달라 전용 엔드포인트가 맡으므로 이 경로에서는 404다(글과 첨부 모두). 화면이 쓰는 읽기 게시판이 이 다섯이다.
  3. **목록 요약.** 자주하는 질문만 본문을, 자료실만 첫 첨부를, 갤러리만 첫 이미지를 담는다. 게시판이 첨부를 끄면 파일은 목록·상세·내려받기에서 모두 사라진다. 이미지의 대체 문구는 저장 위치가 없어 글 제목을 쓴다. 공고의 핵심 항목(`facts`)은 저장 위치가 없어 비어 있다.
  4. **파일 내려받기.** 검사를 통과한 파일(`FS.SAFE`)이 아래 소유자일 때만 내려준다. 게시물은 위의 공개 글이면서 첨부 사용 중인 게시판이고 용도가 첨부·이미지일 때, 홈 콘텐츠는 게시 중인 배너·팝업의 이미지일 때, 강좌는 공개 강좌의 강의계획서(`FP.PLAN`)일 때다. 그 밖의 소유자(감면 증빙, 강사 지원서, 만족도 자료 등)는 모두 404다. 강의계획서는 B4-2b가 파일 주소를 알려 주므로 라우터의 원래 설명에 더했다.
  5. **응답 머리글.** 이미지는 `inline`, 그 밖은 `attachment`로 내려주고 이미지로 표시한 파일도 실제 미디어 유형이 `image/`가 아니면 `attachment`다. `X-Content-Type-Options: nosniff`와 `Cache-Control: no-store`를 붙인다(비공개가 되면 바로 막혀야 하므로).
  6. **저장소.** 로컬 디스크의 `JORI_FILE_ROOT`(기본 `/data/files`) 아래 객체키로 읽는다. 키가 저장소 밖을 가리키거나 파일이 없으면 500이며 응답에 경로를 싣지 않는다. 쓰기(업로드·검사)는 B4-7이다.
  7. **홈.** 기준 기수는 강좌 목록과 같다. 분야 카드는 그 기수의 공개 강좌 중 사용 중 분류가 있는 강좌만 모으고, 접수 상태는 접수중 > 접수예정 > 마감 순으로 우선하며 기간은 가장 이른 시작과 가장 늦은 끝이다. 강좌명은 앞 세 개다. 공지는 공지사항 게시판의 상단공지 먼저 최근 5건이다. 배너·팝업은 게시 중인 것만 정렬 순서대로 주되 같은 콘텐츠 아이디의 여러 버전 중에는 가장 늦게 만든 것 하나다. 링크는 사이트 안 경로(`/`로 시작, `//` 제외)나 `https://` 주소만 내보내고 나머지(`javascript:`, `http:`, `data:` 등)는 null로 버린다. 이미지는 검사를 통과한 첫 이미지 하나이고 대체 문구는 콘텐츠 제목이다.
  8. **홈 비주얼은 항상 null이다.** 저장 위치가 없다(스키마 개정 R14의 `CT.VISUAL`). 사용자가 확인했다. 임시로 `CT.INTRO`를 빌리지 않는다.
- **남은 일**: TRD 4.5는 파일 내려받기마다 요청·행위자·IP·파일·시각·허용/거절을 감사 기록하라고 하나 이번에는 하지 않았다. 로그인 없는 공개 조회마다 작업이력을 INSERT하면 양이 크고 행위자 구분이 없다. 파일 단계(B4-7)에서 대상(비공개 파일, 거절)을 정해 같이 한다. 게시물 본문은 저장 시 정화된 HTML일 수 있는데(스키마) 응답 계약은 문단을 빈 줄로 나눈 글이라 서버는 저장된 본문을 그대로 준다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 변이 검사 62건 중 동등 변이 셋을 빼고 모두 잡힌다(첨부·이미지의 같은 정렬 순서 시험은 검사 도중 공백으로 드러나 보강했다).
