# ADR — 아키텍처 결정 기록

| 항목 | 내용 |
|---|---|
| 문서 | Architecture Decision Records |
| 버전 | 0.2 · 2026-10-30 (DB 스키마 설계안 v0.5 반영, ADR-027·028 추가) |
| 독자 | 내부 개발팀 |
| 규칙 | 결정은 삭제하지 않는다. 뒤집을 때는 새 ADR을 추가하고 기존 ADR 상태를 `대체됨(→ADR-NNN)`으로 바꾼다 |

상태 값은 다음과 같다. **승인**: 원천 요구사항 또는 기관 회신에 근거가 있다. **제안**: 개발팀 설계 판단이며 리뷰가 필요하다. **대체됨**: 이후 결정으로 무효가 됐다.

### ADR-001
**조리읍 시범은 단일 서버·단일 DB에서 운영묶음 ID로 격리** — 대체됨(→ADR-002)

- **맥락**: 추가 결정안(RQ-DAR-NF-001)은 시범 1개소를 1서버·1 MariaDB에서 운영묶음 식별자와 서버 권한 검증으로 격리하고, 확대 시에만 기관별 DB를 두기로 했다.
- **대체 사유**: 2차 기관 회신이 "주민자치회별 독립 WAS·DB·전용 계정, 시범에도 동일 원칙 적용"으로 바꿨다.

### ADR-002
**주민자치회별 독립 WAS·DB·DB 계정** — 승인

- **맥락**: RQ-DAR-NF-001, RQ-QUR-NF-010, RQ-SER-NF-009 2차 회신. 여러 자치회의 회원·결제 데이터를 공용 DB의 센터 코드로만 나누면 안 된다.
- **결정**: 자치회 1곳 = Nginx 사이트 + API 프로세스 + 워커 + MariaDB 스키마 + 전용 DB 계정 1세트. 코드베이스는 하나이고 배포 설정만 다르다. 자치회 내부에서는 `OPER_BNDL_SN`으로 운영묶음 접근을 제어한다.
- **결과**: 센터 간 통합 조회·통계는 구조적으로 불가능하다(요구사항상 금지). 자치회 추가 시 배포 자동화(IaC 스크립트)가 필요하다. 시범 단계에서도 `OPER_BNDL_SN`은 모든 업무 테이블에 둔다.

### ADR-003
**정원 동시성은 강좌 행 비관적 잠금으로 제어** — 대체됨(→ADR-028)

- **대체 사유**: DB 스키마 설계안 v0.5의 TB_CORS에 `OCPY_CNT`·`WAIT_CNT` 카운터 컬럼이 없고, 무결성규칙 R11이 "강좌 행 잠금 후 HELD+CONFIRMED 점유수를 계산"으로 정했다. 강좌 행 잠금은 ADR-028에 그대로 남는다.

- **맥락**: FN-034. 정원 100에 500건이 동시에 들어와도 결제대기+수강확정 ≤ 정원이어야 하고, 대기자가 있으면 신규가 빈자리를 먼저 얻으면 안 된다.
- **결정**: 신청 생성·취소·만료·승격은 모두 같은 트랜잭션 패턴을 쓴다.
  1. `SELECT … FROM TB_CORS WHERE CORS_SN=? FOR UPDATE`
  2. 강좌 행의 `OCPY_CNT`(점유 수), `WAIT_CNT`(대기 수)를 읽고 판정
  3. 신청 행 INSERT/UPDATE, 카운터 갱신
  4. COMMIT
- **대안**: (a) 낙관적 잠금 + 재시도는 경합이 심한 오픈 순간에 재시도 폭주가 생긴다. (b) Redis 분산락은 ADR-004 결정(추가 인프라 없음)과 충돌한다.
- **결과**: 강좌 단위로 직렬화되므로 한 강좌에 몰리는 오픈 순간 처리량이 잠금 보유 시간에 묶인다. 잠금 구간에서 외부 호출(PG·SMS) 금지, 목표 50ms 이하. 카운터와 실제 행 수의 불일치는 야간 정합성 점검 작업이 감지한다.

### ADR-004
**백그라운드 처리는 APScheduler 단일 워커 + DB 작업 테이블** — 승인 (사용자 확정)

- **맥락**: 결제기한 만료, 대기자 승격, SMS 발송·재조회, PG 결과 재조회, 첨부 검사, 탈퇴 파기 처리가 필요하다. Redis/Celery는 자치회마다 운영 컴포넌트를 늘린다.
- **결정**: `worker` 프로세스 1개(자치회당)에서 APScheduler가 주기 작업을 돌린다. 처리 대상은 DB 상태로 찾는다(예: `PAY_DDLN_DT <= NOW()`인 결제대기). 다건 처리 시 `FOR UPDATE SKIP LOCKED`로 집어 중복 실행을 막는다. 작업 실행·결과는 TB_JOB_HSTRY에 남긴다.
- **결과**: 만료 반영 지연은 폴링 주기(10초)만큼 생긴다. 그래서 **결제 요청 API는 기한을 직접 다시 검사**해 워커 지연과 무관하게 기한 이후 결제를 막는다. 워커는 단일 인스턴스로만 띄운다(하트비트로 감시).

### ADR-005
**결제기한은 DB 시각 기준 배정시각 + 600초** — 승인

- **맥락**: FN-036. 새로고침·재접속·결제수단 변경·클라이언트 시계 조작으로 기한이 바뀌면 안 된다.
- **결정**: 자리 배정 트랜잭션에서 `ASGN_DT = NOW(6)`, `PAY_DDLN_DT = ASGN_DT + INTERVAL 600 SECOND`를 저장한다. 화면 카운트다운은 API가 내려준 `PAY_DDLN_DT`와 `server_now`의 차이로 계산한다. 판정은 항상 DB 시각과 비교한다.
- **결과**: 재신청·재배정은 새 행/새 배정시각으로만 기한을 얻는다. 감면 승인 지연은 기한을 늘리지 않는다(ADR-012).
- **보정(ADR-027)**: 컬럼명은 `TB_ATNLC_APLY.SEAT_ALTMNT_DT`(자리배정일시)·`STLM_DDLN_DT`(결제기한일시)다. 시각은 UTC로 저장한다(SEAT-01).

### ADR-006
**결제 결과 불명 시 `결과 확인 중` 상태로 자리 동결** — 승인

- **맥락**: FN-042. 응답 유실·통신 실패만으로 성공·실패를 단정하면 이중 결제나 잘못된 자리 반환이 생긴다.
- **결정**: PG 승인 요청 후 응답을 못 받으면 결제를 `확인중(CHKNG)`으로 두고 원주문번호로 즉시 재조회 최대 3회. 그래도 미확정이면 `확인중` 유지. 이 상태에서는 재결제·만료·다음 순번 배정을 모두 막는다. 익영업일까지 운영자가 PG 관리자에서 수동 대사한다. 기한 이후 승인된 거래는 중복 배정 여부를 확인한 뒤 같은 거래를 취소·환불한다.
- **결과**: 만료 워커는 `확인중` 결제가 걸린 신청을 건너뛴다. 대시보드에 "승인 결과 확인" 업무로 노출한다(FN-066).

### ADR-007
**SQLAlchemy 동기 세션과 명시적 트랜잭션** — 승인 (2026-10-31 사용자 확정)

- **맥락**: 핵심 로직이 `FOR UPDATE` 잠금 순서와 트랜잭션 경계에 의존한다. 동시 500명은 동기 워커 다수로 충분하다.
- **결정**: FastAPI 경로 함수는 `def`(동기)로 쓰고 Gunicorn 워커 × 스레드로 동시성을 얻는다. 서비스 계층은 `with session.begin():` 블록으로 트랜잭션을 명시한다. PG·SMS 호출은 트랜잭션 밖에서 한다.
- **대안**: async SQLAlchemy + aiomysql은 잠금·세션 수명 디버깅 비용이 크고 이득이 적다.
- **결과**: 외부 HTTP 호출은 `httpx` 동기 클라이언트 + 타임아웃(연결 3초, 읽기 10초)을 쓴다.

### ADR-008
**서버 저장 세션 + HttpOnly 쿠키 (JWT 미사용)** — 승인 (2026-10-31 사용자 확정)

- **맥락**: FN-024, FN-062, RQ-SER-NF-008. 로그아웃·비밀번호 재설정·탈퇴 시 즉시 세션을 무효화해야 하고, 회원 30분·관리자 15분 유휴 만료가 있다.
- **결정**: 로그인 시 무작위 256비트 토큰을 발급하고 해시를 TB_LGN_SSN에 저장한다. 쿠키는 `HttpOnly; Secure; SameSite=Lax`. 요청마다 `LAST_ACCES_DT`를 갱신하고 유휴 시간을 넘으면 거부한다. 상태 변경 요청은 CSRF 토큰(더블 서브밋)을 요구한다. 주민·관리자 쿠키 이름과 도메인을 분리한다.
- **결과**: 요청마다 세션 조회 1회가 추가된다(PK 조회라 비용 작음).

### ADR-009
**외부 연동은 어댑터 인터페이스** — 승인 (사용자 확정: TBD + 후보 병기)

**본인확인은 SMS 6자리 OTP로 통일** — 승인

### ADR-012
**감면은 접수 전 증빙 제출·관리자 심사** — 승인

- **근거**: FN-038, FN-039. 행정정보 자동조회 연계는 1차 제외.
- **결정**: 회원이 기수별로 사전 감면 심사(TB_RDCT_BFHD_SRNG)를 신청하고 증빙을 올린다. 담당자 승인 결과는 판정 이력(TB_RDCT_HSTRY)으로 남는다. 신청 생성 시점에 유효한 승인 판정이 있으면 서버가 50%를 적용한다. 판정과 증빙 연결은 불변이며 재판정은 새 행이다.
- **결과**: 접수 중 심사를 기다리며 10분 기한이 흐르는 상황을 원천 차단한다.
- **보정(ADR-027)**: 사전 승인은 TB_RDCT_BFHD_SRNG(`DS.APPROVED`)에, 신청별 적용 판정·금액은 TB_RDCT_HSTRY(`ATNLC_APLY_SN` 필수)에 남는다. 적용 시 회원 행을 잠가 기수당 1강좌를 확보하고, 취소·환불만으로 감면권을 자동 복구하지 않는다(RDCT-BFHD-02).

### ADR-013
**신청·결제·환불을 별도 원장으로 분리** — 승인

- **근거**: FN-026, FN-045. 부분환불이 원결제액을 덮으면 안 되고, 세 상태를 독립 표시해야 한다.
- **결정**: TB_ATNLC_APLY(신청) 1 : N TB_STLM(결제 시도) 1 : N TB_RFND(환불). 한 신청에 `성공` 결제는 최대 1건(부분 유니크 제약을 생성 컬럼으로 구현). 환불 합계는 원결제액 이하.
- **보정(ADR-027)**: 성공 결제 1건은 `UQ_FILTER_STLM_01`(`STLM_STTS_CD='PS.PAID'`)이다. 생성 컬럼 등 MariaDB 구현 방식은 물리 DDL에서 정한다.

### ADR-014
**멱등키 적용** — 승인

- **근거**: FN-033, FN-041, FN-046, FN-059.
- **결정**: 클라이언트는 신청·결제요청·환불신청·문자발송 요청에 `Idempotency-Key`(UUID) 헤더를 보낸다. 서버는 `(행위자, 키)`로 요청 본문 해시와 결과를 저장한다. 같은 키·같은 해시면 저장된 결과를 반환하고, 같은 키·다른 해시면 409 충돌을 반환한다. PG 웹훅은 공급자 통보 ID + 본문 해시로 같은 방식을 적용한다.
- **보정(ADR-027)**: 키는 업무 테이블의 `IDEM_KEY VARCHAR(128)`에 두고 `(OPER_BNDL_SN, IDEM_KEY)` 유니크로 막는다. 요청 해시 컬럼은 문자 요청(`DMND_HASH_VL`)에만 있으므로, 나머지는 저장된 회원·대상·금액 등 의미 있는 내용을 비교해 충돌을 판정한다(R31). 웹훅은 `(OPER_BNDL_SN, STLM_SN, EVENT_ID)` 유니크와 `EVENT_HASH_VL`로 판정한다(R30).

### ADR-021
**주민·관리자 프런트엔드 2개 앱 + 공유 패키지 모노레포** — 승인

- **근거**: RQ-QUR-NF-010(소스·빌드 분리), RQ-QUR-NF-007(중복 화면 단일화).
- **결정**
  ```
  /apps/api          FastAPI
  ```

### ADR-027
**논리 데이터 모델은 DB 스키마 설계안 v0.5(45테이블)를 기준으로 한다** — 승인 (사용자 제공 문서)

- **맥락**: 원천 추적표에는 테이블 이름만 있어 TDD 0.1의 6장 컬럼은 개발팀이 만든 초안이었다. 이후 테이블명세 xlsm v0.4에서 생성한 [PRJ_2026_002_DB스키마_설계안.md](PRJ_2026_002_DB스키마_설계안.md) v0.5(2026-10-28)가 45테이블·610컬럼·184FK·코드 40집합·무결성규칙 135개를 정의했다.
- **결정**
  1. 테이블·컬럼·타입·키·FK·공통코드·무결성규칙은 스키마 설계안을 따른다. TDD는 컬럼을 복사하지 않고 스키마 설계안 절 번호를 참조한다.
  2. 일련번호는 `NUMERIC(22,0)`(TB_STLM.STLM_SN만 `NUMERIC(10,0)`)이며 API에는 문자열로 전달한다. BIGINT 축소는 하지 않는다(N08). 자동증가·조건부 UNIQUE·CLOB 매핑 등 물리 DDL은 MariaDB 버전 확인 후 정한다(N10).
  3. 코드 컬럼은 `CHAR(12)`에 `그룹.값`(예: `ES.HOLD`)을 저장하고 TB_COM_CD FK와 접두부 CHECK를 함께 건다(N06, R01). TDD 0.1의 "코드는 DB FK 없이 애플리케이션 검증" 방침을 바꾼다.
  4. 날짜는 `CHAR(8)` YYYYMMDD, 시각은 `CHAR(6)` HHMMSS, 시스템 사건시각은 UTC 저장·한국시간 표시다(N07).
  5. 공통 컬럼은 `REG_DT`, `MDFCN_DT`, `RCRD_VER`(낙관적 잠금)다.
  6. TDD 0.1의 `[보완]` 테이블 TB_CORS_PLAN·TB_WRKR_HRTBT는 철회한다. 강의계획은 `TB_CORS.LCTR_PLAN_CN` + 계획서 파일(`FP.PLAN`), 워커 생존 감시는 DB 밖(systemd watchdog + 상태 파일)에서 한다.
  7. 결제 결과 불명(ADR-006)은 신청 `ES.HOLD` + 결제 `PS.PENDING`으로 표현한다. 별도 신청 상태는 두지 않는다(SEAT-02).
  8. 코드가 있다는 사실만으로 기능을 켜지 않는다. `AU.MBR_W`(회원수정), `PM.VIRTUAL`(가상계좌), `AP.ADMIN`·`TB_LGN_SSN.ADD_CERT_DT`(관리자 추가인증)는 현재 수행방안상 비활성이다.
- **결과**: 테이블은 45개로 고정한다. 새 테이블·코드값이 필요하면 스키마 설계안을 먼저 개정한다. 스키마에 근거가 없는 권한·코드 매핑(감면 심사·공통코드 관리·보존관리 권한, 연락처 콘텐츠 유형 등)은 PRD 6장 확인 항목으로 둔다.

### ADR-028
**정원 점유는 카운터 없이 강좌 행 잠금 아래 신청 행을 집계** — 승인 (스키마 R11·SEAT-01·SEAT-02)

- **맥락**: FN-034. ADR-003의 강좌 행 잠금은 유지하되, 스키마 설계안에 점유·대기 카운터 컬럼이 없다.
- **결정**: 신청 생성·취소·만료·승격·폐강은 모두 같은 패턴을 쓴다.
  1. `SELECT … FROM TB_CORS WHERE OPER_BNDL_SN=? AND CORS_SN=? FOR UPDATE`
  2. 같은 트랜잭션에서 `APLY_STTS_CD IN ('ES.HOLD','ES.CONFIRM')` 행 수(점유)와 `'ES.WAIT'` 행 수(대기)를 센다. 인덱스는 `IX_ATNLC_APLY_01`을 쓴다.
  3. 신청 행 INSERT/UPDATE
  4. COMMIT
- **대안**: 카운터 컬럼은 집계 비용이 없지만 스키마에 없고 실제 행 수와 어긋날 수 있다.
- **결과**: 강좌당 신청 행은 정원+대기정원 수준이라 집계 비용이 작다. 잠금 구간 외부 호출 금지와 목표 50ms 이하는 그대로다. 야간 카운터 정합성 점검은 필요 없어진다.

### ADR-029
**물리 DDL은 설계안에서 생성하고 시퀀스·생성 컬럼·고정 문자셋으로 구현** — 승인 (스키마 1.2·9.1, TDD 6.1)

- **맥락**: 스키마 설계안은 일련번호 생성 방식, 조건부 UNIQUE 구현, 문자셋·정렬규칙을 "물리 DDL에서 정한다"고 미뤘다. 610개 컬럼을 손으로 옮기면 틀리기 쉽다.
- **결정**: 아래 다섯 가지를 따른다.
  1. **생성**: 설계안 4절의 표를 읽어 마이그레이션 SQL을 생성한다(`app.tools.generate_ddl`). 생성기가 문서의 숫자(45 테이블·610 컬럼·184 외래키·코드 40집합 182값)와 내부 참조·타입 일치를 검사하고 어긋나면 만들지 않는다. 만든 SQL은 Alembic `0001`이 실행한다. 배포한 뒤에는 이 파일을 고치지 않고 새 버전을 더한다.
  2. **일련번호**: 단일 숫자 기본키마다 `SEQUENCE SQ_<테이블>`을 두고 컬럼 기본값을 `NEXTVAL`로 한다(41개). 컬럼 타입은 `DECIMAL(22,0)`을 유지하고 BIGINT로 줄이지 않는다. 연결 테이블의 복합키와 코드 기본키에는 시퀀스가 없다. 시퀀스는 `CACHE 1000`이라 재시작 뒤 번호에 구멍이 생길 수 있고 번호가 연속임을 가정하지 않는다.
  3. **조건부 UNIQUE**(`UQ_FILTER_ATNLC_APLY_01`, `UQ_FILTER_STLM_01`): MariaDB에는 부분 인덱스가 없어 `PERSISTENT` 생성 컬럼 `ZF_*`(조건이 참이면 1, 아니면 NULL)를 UNIQUE 키에 더한다. NULL은 중복으로 보지 않아 취소 건은 몇 개든 쌓이고 유효 건만 하나로 제한된다. 생성 컬럼의 식은 `IN` 목록을 쓸 수 없어(오류 1901) `OR`로 푼다. 이 컬럼 2개는 설계안의 610개에 더해진다.
  4. **문자셋·시각**: `utf8mb4` / `utf8mb4_unicode_ci`, 서버 시간대는 UTC, 시각 컬럼 기본값은 `CURRENT_TIMESTAMP`다.
  5. **제약**: 문서의 `YN`(18건)과 `CD`(36건) 규칙을 `CHECK`로 만든다(코드 접두부 검사 + `TB_COM_CD` 외래키). 서술형 규칙 중 문서가 DB 제약으로 분명히 적은 것(R01·R04·R05·R06·R08·R09·R10·R13·R14·R16·R18·R19·R21, SEAT-01·RFND-01·RCRT-01·STAT-04·SMS-02·SMS-03·AUTH-01) 33건과, R27(일련번호 양수, 정렬순서·횟수 0 이상)을 컬럼 도메인으로 자동 만든 81건을 더해 `CHECK`는 모두 168건이다. 문서가 서비스 계층 규칙으로 분류한 것(예 R15 환불 요청자)은 옮기지 않는다. 외래키는 모두 `RESTRICT`다(생성 컬럼의 기반 컬럼에는 `CASCADE`를 쓸 수 없기도 하다).
- **개발 환경 주의**: Windows용 MariaDB의 기본은 테이블 이름을 소문자로 저장한다(`lower_case_table_names=1`). 개발 DB는 `2`로 두어 이름을 보존하지만 비교는 여전히 대소문자를 구분하지 않아, Ubuntu 운영에서만 나는 대소문자 오류를 숨길 수 있다. 배포 전에 Ubuntu에서 DB 시험을 한 번 더 돌린다.
- **대안**: 손으로 쓰는 DDL은 문서와 어긋나도 모른다. 부분 인덱스 대신 서비스 계층 검사만 쓰면 동시 신청에서 중복이 생긴다.
- **결과**: 문서와 DB의 일치를 시험이 자동으로 확인한다. 문서를 고치면 생성기를 다시 돌리고 배포 전이면 파일을 갱신, 배포 후면 새 마이그레이션을 더한다.

### ADR-030
**백엔드 DB 접근은 SQLAlchemy Core와 생성된 테이블 정의, 운영묶음은 배포 설정의 사이트 식별자** — 승인 (ADR-001·002, 스키마 C03·C04, TDD 2.3·4.5)

- **맥락**: 스택은 SQLAlchemy 2 동기 세션이다. 테이블이 45개·컬럼이 610개이고 문서가 컬럼명 명시·`SELECT *` 금지·잠금 순서를 요구한다. 운영묶음은 요청이 아니라 서버가 정해야 한다(R26).
- **결정**: 아래 다섯 가지를 따른다.
  1. **ORM 클래스를 만들지 않는다.** SQLAlchemy Core의 `Table` 정의를 설계안에서 생성한다(`app/db/tables.py`). 서비스는 `select`·`insert`·`update`로 컬럼을 명시해 쓴다. 생성 파일은 서식 도구에서 제외하고 생성기가 서식을 책임져 항상 같은 출력이 나온다.
  2. **요청 하나가 트랜잭션 하나다.** `get_db` 의존성이 응답 전에 커밋하고 예외가 나면 되돌린다. 세션은 `autoflush`를 끄고 접속마다 시간대를 UTC로 고정한다.
  3. **운영묶음은 배포 설정이 정한다.** ADR-002대로 배포 1곳은 사이트 1개를 맡으므로 환경변수 `JORI_SITE_ID`로 `TB_OPER_BNDL`에서 묶음을 한 번 찾아 기억한다. 요청의 호스트·헤더·경로·본문은 쓰지 않는다. 사이트가 없거나 사용 중지면 사용자 잘못이 아니라 배포 오류(500)다.
  4. **낙관적 잠금**: 갱신은 키(기본키+묶음)와 화면이 읽은 `RCRD_VER`가 모두 맞을 때만 하고 버전을 1 올리며 수정 시각을 남긴다. 행이 없으면 404, 버전이 다르면 409(`VERSION_CONFLICT`)다.
  5. **멱등 삽입**: 삽입이 (묶음, 멱등키) 유일키 때문에 실패하면 기존 행을 읽어, 같은 요청이면 그 행을 돌려주고 다른 요청이면 409(`IDEMPOTENCY_CONFLICT`)다. 다른 유일키(예 유효 신청 중복)가 막은 것이면 그대로 올려 호출자가 업무 오류로 바꾼다. InnoDB는 실패한 문장만 되돌리므로 저장점을 쓰지 않는다.
- **오류와 로그**: 예상하지 못한 오류는 응답에 내용을 싣지 않고, 로그에도 예외 메시지(SQL·개인정보가 들어 있을 수 있다) 없이 예외 종류와 요청 ID만 남긴다(C10).
- **대안**: ORM은 매핑 클래스 610개 분량을 따로 관리해야 하고 잠금·묶음 조건이 숨는다. 요청 호스트로 묶음을 정하면 클라이언트가 조작할 수 있다.
- **결과**: 새 테이블 정의는 마이그레이션과 같은 생성기에서 함께 나와 어긋나지 않는다. 한 배포에서 여러 묶음을 서비스해야 하는 요구가 생기면 묶음 판정만 바꾼다.

### ADR-031
**로그인·세션 구현은 서버 세션과 로그인 전 CSRF 시드 쿠키, 관리자 잠금은 정책 확정 전까지 설정값** — 승인 (ADR-008, DV17, 스키마 AUTH-03~05, PRD Q28)

- **맥락**: ADR-008과 DV17이 서버 세션·HttpOnly 쿠키·세션 토큰 해시 파생 CSRF를 정했다. 그러나 세션 테이블에는 CSRF 컬럼이 없고, 로그인 요청도 CSRF 토큰이 필요한데 그때는 세션이 없다. 관리자 로그인 실패 제한 수치는 기관 정책(Q28)이 없다.
- **결정**: 아래 여섯 가지를 따른다.
  1. **세션 토큰**은 256비트 무작위 값이고 서버에는 SHA-256 해시(`TKN_HASH_VL`)만 둔다. 세션은 회원 또는 관리자 중 정확히 한 대상이고 회원은 운영묶음이 필요하다. 요청마다 폐기·만료·계정 상태(회원 `MS.ACTIVE`, 관리자 `USE_YN=Y`)를 다시 확인한다.
  2. **CSRF 토큰**은 저장하지 않고 파생한다. 로그인 뒤에는 `HMAC(비밀키에서 파생한 키, "session:" + 세션 토큰 해시)`이고, 로그인 전에는 `GET /auth/session`이 무작위 시드를 HttpOnly 쿠키로 내리고 `HMAC(..., "anon:" + 시드)`를 토큰으로 준다(더블 서브밋). 회원·관리자는 시드 쿠키 이름이 다르다.
  3. **쿠키**는 `HttpOnly; Secure; SameSite=Lax; Path=/`이고 회원 `jori_session`, 관리자 `jori_admin_session`으로 이름이 다르다. 로그아웃은 쿠키를 지우고 몇 번 불러도 같은 결과다.
  4. **유휴 만료**는 회원 30분, 관리자 15분이다. `EXPRY_DT`가 현재 유휴 마감이고 사용자 조작(관리자 `extend`)이 있을 때만 뒤로 민다. `GET /auth/session`은 연장하지 않는다.
  5. **회원 잠금**은 직전 10분의 실패 5회에 15분이다(AUTH-04). 계정 행을 잠근 채 실패 이력으로 센다. 없는 아이디·탈퇴 계정은 같은 응답과 같은 계산(더미 해시 검증)을 하고 이력은 남기지 않는다. 실패 이력과 잠금은 오류 응답을 내기 전에 커밋한다(`get_db`는 예외가 나면 되돌린다).
  6. **관리자 잠금 수치는 지어내지 않는다.** `JORI_ADMIN_LOCK_FAILURES`와 `JORI_ADMIN_LOCK_MINUTES`를 함께 설정하면 그대로 적용하고, 없으면 실패 이력만 남기고 잠그지 않는다. 정책이 정해지면 값만 설정한다.
- **비밀값**: `JORI_SECRET_KEY`는 32자 이상이고 CSRF·OTP 등 용도별로 파생해 쓴다. 비밀번호는 PBKDF2-HMAC-SHA-256이고 반복 횟수를 해시와 함께 저장해 설정을 올려도 옛 해시를 검증한다(기본 600,000).
- **적용 순서**: 이번에는 인증 엔드포인트가 스스로 CSRF를 검증한다. 나머지 엔드포인트의 세션·CSRF 검증은 각각 구현할 때 붙이고, 모두 끝난 뒤 전역 검증으로 바꾼다.
- **대안**: 세션 테이블에 CSRF 컬럼을 더하려면 스키마 개정이 필요하다. 로그인 전 CSRF를 생략하면 로그인 CSRF 공격이 가능하다.
- **결과**: 새 테이블·컬럼 없이 문서의 결정을 모두 지킨다. 관리자 잠금 정책이 없는 동안 관리자 로그인은 무차별 대입에 약하므로 운영 전에 Q28을 확정해야 한다.

### ADR-032
**OTP는 계정 존재를 숨기는 가짜 인증 행과 앱 시계 기준 시각, 문자 발송은 커밋 뒤 어댑터 호출** — 승인 (TDD 8.1·8.2, 스키마 AUTH-01~03·OTP-SMS-01, ADR-009)

- **맥락**: OTP 응답은 대상 회원이 있든 없든 같아야 하고(FN-061), 인증번호 원문은 DB·로그에 남지 않으며, 문자 공급자는 아직 정해지지 않았다(Q2~Q4).
- **결정**: 아래 여섯 가지를 따른다.
  1. **가짜 인증 행.** 아이디 찾기·비밀번호 재설정에서 일치하는 정상 회원이 없으면 문자는 보내지 않고 대상 회원이 없는 인증 행만 만든다. 확인 단계도 실제와 같은 모양(틀린 코드는 200 `verified:false`와 남은 횟수)으로 응답해 회원 존재를 알 수 없다. 스키마 AUTH-01은 "다른 목적은 정확한 대상 계정이 필수"라고 하지만 가짜 행은 어떤 업무 API도 통과하지 못하므로 이 규칙을 해치지 않는다.
  2. **코드와 암호화.** 인증번호는 6자리 난수이고 DB에는 `HMAC(비밀키에서 파생한 키, 요청 번호 + 코드)`만 둔다. 전화번호는 AES-256-GCM이다. 가입 단계의 이름은 인증 테이블에 이름 컬럼이 없고 가입 요청에도 이름이 없어서 전화번호와 함께 같은 암호문 안에 넣는다(`{"p": 전화, "n": 이름}`). 암호문은 용도별 연관 데이터로 묶어 다른 용도의 값을 옮겨 붙여도 열리지 않는다.
  3. **제한.** 유효 5분, 입력 오류 5회 무효, 재전송 60초다. 재전송은 서명 쿠키(모든 요청)와 같은 회원·목적의 직전 요청 시각(회원 대상)으로 이중 제한한다. 쿠키만 지워도 피해자에게 문자가 쏟아지지 않는다. 전화번호 단위 제한은 HMAC 검색키 컬럼이 필요해 스키마 개정 요청 대상이다.
  4. **시각은 앱 시계 하나로 통일한다.** `REG_DT`·`EXPRY_DT`·`FAIL_DT`·`LAST_ACT_DT` 같이 판정에 쓰는 시각은 모두 앱이 넣는다. DB 기본값(`CURRENT_TIMESTAMP`)과 섞으면 앱 서버와 DB 서버의 시계가 어긋날 때 재전송 제한이 풀린다(시험에서 실제로 발생). 기록용인 `MDFCN_DT`는 DB 시계를 쓰지만 판정에는 쓰지 않는다.
  5. **문자 발송.** 인증 요청·문자 요청·수신 대상을 한 트랜잭션으로 커밋한 뒤에 어댑터를 호출한다. 공급자 호출은 DB 잠금·트랜잭션 밖이다. 결과는 접수(`SS.SENDING`), 거절(`SS.FAIL`), 알 수 없음(`SS.UNKNOWN`)으로 이력에 남기고 최종 성공(`SS.SENT`)은 워커가 조회로 확정한다. 거절이면 기록을 먼저 커밋하고 500으로 답하며 자동으로 다시 보내지 않는다.
  6. **어댑터.** 문자는 `SmsSender` 규약 뒤에 두고 공급자가 정해질 때까지 모의 구현만 둔다. 발신번호도 미정이라 값을 지어내지 않고 `TBD`로 표시한다. 설정으로 모의가 아닌 공급자를 고르면 시작하지 못한다.
- **남은 위험**: 회원 대상은 DB 직전 요청으로, 가짜 행은 쿠키로만 재전송을 제한하므로 쿠키를 지우고 두 번 요청하면 429 여부로 회원 존재를 추측할 수 있다. 전화번호 검색키 없이는 막을 수 없고 문서가 이를 감수했다. 인증 요청 번호는 순차라 추측할 수 있지만 요청마다 5회까지만 시도할 수 있어 위험이 작다.
- **결과**: 새 테이블·컬럼 없이 문서를 지킨다. 가입·아이디 찾기·비밀번호 재설정(다음 단계)은 이 인증 행을 같은 검사로 소비하고 사용 완료 표시를 업무 확정과 같은 트랜잭션에서 한다.

### ADR-033
**가입·아이디 찾기·비밀번호 재설정은 인증 소비와 업무 확정을 한 트랜잭션으로, 필수 약관이 하나도 없으면 가입을 거절** — 승인 (TDD 8.1, 스키마 4.16·AUTH-01·AUTH-05, R17·R22, ADR-032)

- **맥락**: 이 세 기능은 OTP 인증 행을 소비하며 업무를 확정한다. 어떤 약관이 필수인지는 문안마다 `ESNTL_YN`이 정하는데, 필수 문안이 하나도 게시되지 않은 때의 동작은 문서에 없다.
- **결정**
  1. **소비 규칙.** `consume_otp`가 인증 행을 잠그고 목적·운영묶음·만료·실패 횟수·코드를 검사한다. 목적이나 운영묶음이 다르면 없는 인증과 같이 `OTP_INVALID`다. 틀린 코드의 실패 횟수는 오류 응답 전에 커밋한다. 사용 완료 표시(`mark_used`)는 업무 변경과 같은 트랜잭션이다.
  2. **가입.** 이름·전화번호는 암호문에서 꺼낸다. 약관은 같은 운영묶음에서 지금 게시 중(게시 여부·시작·종료)인 문안만 인정하고, 게시 중인 버전과 문안 해시(R17)가 맞아야 동의를 받는다. 필수 유형(게시된 문안의 `ESNTL_YN`)에 동의가 없으면 거절한다. 아이디 중복(MariaDB 1062)은 `JOIN_LOGIN_ID_TAKEN`이며 인증은 소비되지 않아 다른 아이디로 다시 시도할 수 있다. 가입 성공은 회원·동의 이력·사용 완료·감사 기록을 한 번에 확정하고 로그인시키지는 않는다.
  3. **필수 약관이 하나도 게시되지 않으면 가입을 거절한다(문서에 없는 보수적 규칙).** 그대로 두면 약관 동의 없이 가입이 되기 때문이다. 약관을 게시하기 전에는 가입이 열리지 않는다. 운영에서 다르게 하려면 이 결정을 새 ADR로 대체한다.
  4. **아이디 찾기.** 앞 2글자만 보이고 나머지는 `*`이며 마지막 한 글자는 항상 가린다(짧은 아이디가 통째로 드러나지 않게). 가짜 인증은 실제와 같은 모양으로 "없음"만 답한다.
  5. **비밀번호 재설정.** 인증된 회원의 아이디와 입력한 아이디가 다르면 틀린 코드처럼 실패 횟수를 올리고 거절한다. 성공하면 비밀번호 해시를 바꾸고 그 회원의 살아 있는 세션을 모두 폐기한다(다른 회원 세션은 그대로).
  6. **감사.** `TB_JOB_HSTRY`에 INSERT만 한다. 비밀번호·인증번호·전체 아이디는 기록하지 않는다.
- **남은 위험**: 같은 유형에 게시된 버전이 여럿이면 가입자가 고른 버전을 인정한다. 같은 인증 번호를 두 요청이 동시에 소비하는 경쟁은 행 잠금으로 막히지만 단일 연결 시험 환경에서는 검증하지 못했다(Ubuntu DB 시험에서 확인).
- **결과**: 새 테이블·컬럼 없이 구현했다. 변이 검사 25건 중 4건이 처음에 살아남아 시험 3건을 보강했고(미게시 약관, 필수 문안 부재, 다른 운영묶음 인증) 모두 잡힌다.

### ADR-034
**공개 조회는 게시 중인 것만 보여 주고, 저장 위치가 없는 안내 글·연락처 필드는 지어내지 않고 비운다** — 승인 (TDD 5절 GET /terms·/contents·/site/contact, RQ-FUN-FN-006·011·055·072, R9, Q23·Q24)

- **맥락**: 로그인 없이 읽는 약관·안내 글·연락처의 저장 위치를 문서가 일부만 정했다. 연락처는 저장 위치가 없고(Q23), 안내 글은 CT 코드가 소개·연혁뿐이다(R9 미반영).
- **결정**
  1. **게시 판정.** 약관·안내 글은 같은 운영묶음에서 게시 여부(`PSTG_YN`)가 Y이고 게시 시작 이상·종료 미만인 문안만 보인다. 앱 시계를 기준으로 하며 시작 시각 정각은 보이고 종료 시각 정각은 보이지 않는다. 후보가 여럿이면 가장 늦게 만든 문안이다. 버전을 지정해도 게시 중이 아니면 404다(초안·종료된 문안을 드러내지 않는다).
  2. **약관 시행일.** 게시 시작 시각을 한국 날짜로 바꿔 준다. 시작 시각이 비어 있으면 null이다.
  3. **안내 글.** 사용자가 정한 대로 `center-history`만 `CT.HISTORY`에서 `CONTS_ID`가 같은 문안으로 제공한다. `guide-apply`·`guide-refund`·`center-facility`는 R9가 반영될 때까지 어떤 유형으로 저장돼 있어도 404다. 본문(`CONTS_CN`)은 `{"subtitle", "sections"}` 모양의 JSON이고 응답과 같은 camelCase다. 모양이 틀리면 500이다. 수정일은 수정 시각(없으면 등록 시각)의 한국 날짜다.
  4. **연락처.** 운영묶음의 `TELNO`·`ADDR`만 채우고 나머지 필드(관리실 전화, 우편번호, 층, 운영시간, 주차)는 null이다. 화면은 null이면 '확인 필요'로 표시한다. Q23이 닫히면 채운다.
  5. **홈**은 강좌·게시판 조회가 있어야 만들 수 있어 B4-2c에서 한다.
- **대안**: 연락처를 콘텐츠 행(JSON)으로 임시 저장하거나 안내 글 4종을 소개·연혁 유형에 나누어 저장하는 방법이 있었으나, 스키마 개정 때 이관이 필요하고 R9 요청서의 "임시 저장하지 않는다" 결정을 뒤집어서 택하지 않았다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 변이 검사 18건 중 처음 3건이 살아남아 시험을 보강했고 모두 잡힌다.

### ADR-035
**강좌 공개 조회는 기준 기수 안의 공개·마감·운영중 강좌만 보여 주고, 접수·교육 상태는 서버가 판정한다** — 승인 (TDD 5.2·6절 GET /courses, RQ-FUN-FN-012~015, RQ-QUR-NF-008, ADR-028)

- **맥락**: 목록 응답은 "기준 분기"를 담아야 하는데(FN-012) 어떤 기수를 기준으로 삼는지, 어떤 상태의 강좌가 주민에게 보이는지, 강사 이름을 어디까지 내보내는지를 문서가 정하지 않았다.
- **결정**
  1. **기준 기수.** 사용 중(`USE_YN=Y`)인 기수 가운데 교육이 끝나지 않은(종료일 ≥ 한국 오늘) 것 중 교육 시작이 가장 이른 기수다. 모두 끝났으면 가장 최근에 끝난 기수다. 기수가 없으면 목록은 비고 기준 기수도 null이다. 상세와 강의계획은 기준 기수와 무관하게 공개된 강좌면 보인다.
  2. **공개 범위.** 강좌 상태가 `CS.OPEN`·`CS.CLOSE`·`CS.RUN`인 강좌만 보인다. `CS.DRAFT`·`CS.END`·`CS.CANCEL`은 목록·상세·강의계획 모두 404다. 폐강은 회원 본인의 신청 화면에서 알린다(TDD 5.1).
  3. **접수 상태.** `CS.OPEN`이고 접수 시작 시각 이상·종료 시각 미만이면 접수중, 시작 전이면 접수예정, 그 밖(수동 마감·운영중·종료 시각 이후)은 접수마감이다. 종료 시각 정각은 마감이며 신청 생성(TDD 5.2)이 같은 규칙을 쓴다. 상태 거름은 같은 판정을 SQL로 써서 쪽 나누기와 전체 건수가 맞는다. 교육 상태는 교육 시작·종료일을 한국 날짜와 견주며 종료일 당일까지 교육중이다.
  4. **잔여석과 대기.** 잔여석은 모집 인원에서 `ES.HOLD`·`ES.CONFIRM` 신청 수를 뺀 값이고 0 밑으로 내려가지 않는다(ADR-028). 대기 수는 `ES.WAIT`만 센다. 조회는 잠금 없이 읽으므로 같은 순간의 신청과 약간 어긋날 수 있고, 정원 판정은 신청 생성이 잠금 아래에서 다시 한다.
  5. **강사 이름.** 승인(`IS.APPROVE`)이고 공개(`RLS_YN=Y`)로 둔 강사만 이름이 나가고 검색에도 걸린다. 그렇지 않으면 이름은 null이고 검색으로도 찾을 수 없다.
  6. **분류.** 사용 중이고 삭제되지 않은 센터별 분류만 나간다. 연결되지 않았거나 중지·삭제된 분류는 null이다(자동 매핑하지 않는다, 스키마 1.2).
  7. **일정.** 적용 종료일이 한국 오늘 이상인 일정 행만 모아, 같은 시작·종료 시각의 요일을 한 줄로 묶고 월~일 순으로 준다. 반 구분(`label`)은 저장 위치가 없어 null이다. 강의실은 일정에 걸린 시설 이름을 중복 없이 쉼표로 잇는다.
  8. **계획서 파일.** 용도 `FP.PLAN`이고 검사 상태 `FS.SAFE`인 첨부 중 정렬 순서가 앞선 하나만 알린다. 계획이 있다는 표시(`hasPlan`)는 공백 아닌 계획 본문이나 이런 파일이 있을 때 참이다.
  9. **검색·페이지.** 검색어는 앞뒤 공백을 자르고 `%`·`_`를 글자로 취급한다. 목록은 강좌 번호 순이다.
- **남은 위험**: 기준 기수 규칙은 운영 경험으로 바꿀 수 있다(여러 기수가 동시에 접수 중이면 가장 이른 기수만 보인다). 이 경우 기수 선택 파라미터가 필요하며 계약 개정이 따른다. 잔여석은 잠금 없는 읽기라 목록을 본 뒤 신청하면 대기가 될 수 있다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 일정 행의 시작·종료 시각 사이 겹침과 휴보강(`TB_CORS_SCHDL_CHG`)은 상세에 아직 반영하지 않았다(계약에 필드가 없다).

### ADR-036
**게시판·홈·파일 내려받기는 소유 업무의 지금 공개 상태로 판정하고, 저장 위치가 없는 홈 비주얼은 비운다** — 승인 (TDD 5·6절, TRD 4.4·4.5, RQ-FUN-FN-006·054, RQ-SER-NF-002, R14·R24)

- **맥락**: 게시물 목록·상세·첨부·홈 콘텐츠를 로그인 없이 읽게 한다. 공개 판정이 목록과 파일 내려받기에서 달라지면 비공개가 된 글의 첨부가 새어 나간다(TRD 4.4는 같은 판정을 쓰라고 한다).
- **결정**
  1. **공개 글 판정은 한 곳에 둔다.** 게시판이 사용 중이고, 글이 원글이며, 삭제·비공개가 아니고, 게시 시작 이상·종료 미만이다. 목록·상세·홈 공지·파일 내려받기가 모두 `public_post_conditions`를 쓴다. 게시일은 게시 시작 시각이 있으면 그것, 없으면 등록 시각이다. 순서는 상단공지, 게시일 내림차순, 번호 내림차순이다.
  2. **이 엔드포인트가 여는 게시판은 `notice`·`news`·`resources`·`gallery`·`faq` 다섯이다.** 질문과 답변·수강후기는 작성자와 비공개 판정이 달라 전용 엔드포인트가 맡으므로 이 경로에서는 404다(글과 첨부 모두). 화면이 쓰는 읽기 게시판이 이 다섯이다.
  3. **목록 요약.** 자주하는 질문만 본문을, 자료실만 첫 첨부를, 갤러리만 첫 이미지를 담는다. 게시판이 첨부를 끄면 파일은 목록·상세·내려받기에서 모두 사라진다. 이미지의 대체 문구는 저장 위치가 없어 글 제목을 쓴다. 공고의 핵심 항목(`facts`)은 저장 위치가 없어 비어 있다.
  4. **파일 내려받기.** 검사를 통과한 파일(`FS.SAFE`)이 아래 소유자일 때만 내려준다. 게시물은 위의 공개 글이면서 첨부 사용 중인 게시판이고 용도가 첨부·이미지일 때, 홈 콘텐츠는 게시 중인 배너·팝업의 이미지일 때, 강좌는 공개 강좌의 강의계획서(`FP.PLAN`)일 때다. 그 밖의 소유자(감면 증빙, 강사 지원서, 만족도 자료 등)는 모두 404다. 강의계획서는 B4-2b가 파일 주소를 알려 주므로 라우터의 원래 설명에 더했다.
  5. **응답 머리글.** 이미지는 `inline`, 그 밖은 `attachment`로 내려주고 이미지로 표시한 파일도 실제 미디어 유형이 `image/`가 아니면 `attachment`다. `X-Content-Type-Options: nosniff`와 `Cache-Control: no-store`를 붙인다(비공개가 되면 바로 막혀야 하므로).
  6. **저장소.** 로컬 디스크의 `JORI_FILE_ROOT`(기본 `/data/files`) 아래 객체키로 읽는다. 키가 저장소 밖을 가리키거나 파일이 없으면 500이며 응답에 경로를 싣지 않는다. 쓰기(업로드·검사)는 B4-7이다.
  7. **홈.** 기준 기수는 강좌 목록과 같다. 분야 카드는 그 기수의 공개 강좌 중 사용 중 분류가 있는 강좌만 모으고, 접수 상태는 접수중 > 접수예정 > 마감 순으로 우선하며 기간은 가장 이른 시작과 가장 늦은 끝이다. 강좌명은 앞 세 개다. 공지는 공지사항 게시판의 상단공지 먼저 최근 5건이다. 배너·팝업은 게시 중인 것만 정렬 순서대로 주되 같은 콘텐츠 아이디의 여러 버전 중에는 가장 늦게 만든 것 하나다. 링크는 사이트 안 경로(`/`로 시작, `//` 제외)나 `https://` 주소만 내보내고 나머지(`javascript:`, `http:`, `data:` 등)는 null로 버린다. 이미지는 검사를 통과한 첫 이미지 하나이고 대체 문구는 콘텐츠 제목이다.
  8. **홈 비주얼은 항상 null이다.** 저장 위치가 없다(스키마 개정 R14의 `CT.VISUAL`). 사용자가 확인했다. 임시로 `CT.INTRO`를 빌리지 않는다.
- **남은 일**: TRD 4.5는 파일 내려받기마다 요청·행위자·IP·파일·시각·허용/거절을 감사 기록하라고 하나 이번에는 하지 않았다. 로그인 없는 공개 조회마다 작업이력을 INSERT하면 양이 크고 행위자 구분이 없다. 파일 단계(B4-7)에서 대상(비공개 파일, 거절)을 정해 같이 한다. 게시물 본문은 저장 시 정화된 HTML일 수 있는데(스키마) 응답 계약은 문단을 빈 줄로 나눈 글이라 서버는 저장된 본문을 그대로 준다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 변이 검사 62건 중 동등 변이 셋을 빼고 모두 잡힌다(첨부·이미지의 같은 정렬 순서 시험은 검사 도중 공백으로 드러나 보강했다).

### ADR-037
**회원 전용 요청은 세션 확인과 활동 연장 규칙을 한 의존성이 맡고, 신청 가능 판정·금액·화면 상태는 서버가 정한다** — 승인 (TDD 5.1·5.2·5.5, AUTH-05, RQ-FUN-FN-012·014·025·037·038, RQ-QUR-NF-008)

- **맥락**: `/me/*`와 신청 미리보기는 그동안 인증이 문서에만 있었다. 또 "화면의 백그라운드 폴링이 유휴 시간을 늘리면 안 된다"(AUTH-05)는 구분 방법이 없어 체크리스트에 미결이었다. 신청 가능 여부, 금액, 화면 상태를 화면이 날짜로 비교하면 판정이 어긋난다.
- **결정**
  1. **`require_member` 하나가 회원 세션을 확인한다.** 세션이 살아 있고 운영묶음이 이 배포의 것이며 계정이 `MS.ACTIVE`일 때만 통과하고 아니면 401이다. 회원 번호는 세션에서만 온다. 관리자 쿠키로는 통과하지 못한다.
  2. **활동 연장.** 사용자가 정한 대로 모든 `/me` 요청이 유휴 30분을 처음부터 다시 센다. 화면이 저절로 부르는 조회는 `X-Background: 1` 헤더를 붙이면 연장하지 않는다. 값이 `1`이 아니면 활동으로 본다. 세션 조회(`GET /auth/session`)는 지금처럼 연장하지 않는다(ADR-031). 프런트의 자동 조회에 이 헤더를 붙이는 일이 남았다.
  3. **신청 가능 판정**은 접수기간, 회원 상태, 우선접수, 중복, 정원 순으로 첫 이유 하나를 알린다. 접수 상태는 강좌 조회와 같은 함수다(ADR-035). 우선접수 대상은 센터가 거주를 확인한 조리읍·파주시 주민이고, 그 밖은 강좌의 관외 개방 시각 이후에만 신청한다(개방 시각이 비어 있으면 열리지 않는다). 대기자가 있으면 빈자리가 있어도 새 신청이 가로채지 못한다.
  4. **관외 신청자는 잔여 정원이 없으면 대기도 받지 않는다.** TDD가 "기본값은 대기 불가"로 두고 PRD Q5가 열려 있어 그 기본값을 따랐다.
  5. **금액**은 수강료 스냅샷, 감면(수강료의 50% 내림), 결제예정액이다. 감면은 조리읍 거주가 확인된 회원이 같은 기수에 `DS.APPROVED` 사전심사(생계·유공·장애 3유형, 유효기간 안)를 갖고, 같은 기수에 감면을 적용한 신청이 없거나 담당자가 해제(더 나중의 `DR.REJECT`)한 경우에만 준다. 취소·환불로는 복구하지 않는다. 이번 단계는 읽기만 하고 적용 이력 기록은 B4-3d다.
  6. **화면 상태와 가능한 행동**은 신청 상태와 최근 결제·환불 상태를 합쳐 서버가 정한다. 결제 승인 결과 확인 중(`PS.PENDING`)이면 결제·취소·환불을 모두 막는다. 결제는 결제대기이고 기한 안일 때만 가능하다. 취소는 대기와 (결과 확인 중이 아닌) 결제대기, 그리고 결제 없는 확정의 개강 전이다. 환불 요청은 결제를 마친 확정이고 환불이 없거나 반려된 경우다.
  7. **결제 없는 확정의 취소는 개강 전까지만 허용한다**(TDD 5.7 "ES.CONFIRM (0원) 가능 (개강 전)"). 개강일 당일부터는 막는다. 개강 후 정원 반환은 PRD Q18의 기본값(개강 전에만)을 따른다.
  8. **내 신청**은 회원 조건을 걸어 남의 신청은 없는 것과 같이 404다. 대기 순번은 같은 강좌 대기 신청 중 (대기순서, 신청번호)가 내 앞인 수 + 1이다.
- **남은 일**: 신청 생성·취소(B4-3b·c)에서 같은 판정을 강좌 행 잠금 아래에서 다시 한다. 미리보기의 잔여석은 잠금 없는 읽기라 신청 시점과 어긋날 수 있다. 환불 요청 가능 여부는 환불 단계(B4-5)에서 정책(반환액·기한)을 더해 다시 정한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 변이 검사 70여 건 중 동등 변이(제약이 막는 데이터) 셋을 빼고 모두 잡힌다. 시험 공백 4건(감면 유형, 가장 최근 승인, 다른 신청의 반려, 수강료 있는 0원 결제)은 보강했다.

### ADR-038
**신청 생성은 강좌 → 회원 행 잠금 아래에서 판정하고, DB 엔진은 READ COMMITTED로 고정한다** — 승인 (TDD 5.2, ADR-028·006, RQ-FUN-FN-033·034·036·038·039, C07·C08)

- **맥락**: 정원 초과와 이중 배정 0건이 목표(G2)다. 판정 단계마다 행 잠금 아래에서 세어야 하는데, InnoDB 기본 격리 수준(REPEATABLE READ)에서는 잠금을 기다린 뒤에도 일반 SELECT가 트랜잭션 처음의 스냅샷을 본다. 시험에서 이 때문에 정원 초과, 같은 키 중복 신청, 감면 이중 사용이 실제로 일어났다(READ COMMITTED를 빼면 동시성 시험 4건이 실패한다).
- **결정**
  1. **엔진은 READ COMMITTED다.** 모든 요청이 문장마다 최신 커밋 값을 읽는다. 바이너리 로그를 켠 운영 DB에서 `binlog_format`이 STATEMENT이면 READ COMMITTED 쓰기가 거절된다고 MariaDB 문서가 설명한다. 개발 DB는 바이너리 로그가 꺼져 있고(`log_bin=0`, 기본 형식 MIXED) 앱 계정에 형식을 바꿀 권한이 없어 이 충돌은 재현하지 못했다. 운영 DB는 MIXED(MariaDB 기본값) 또는 ROW로 두고 Ubuntu DB 시험에서 바이너리 로그를 켠 상태로 쓰기를 확인한다.
  2. **잠금 순서는 강좌 → 회원이다**(C07). 강좌 행을 `FOR UPDATE`로 잠가 같은 강좌의 신청을 직렬화하고, 회원 행을 잠가 같은 회원의 다른 강좌 신청(기수당 감면 1회)을 직렬화한다. 둘 다 빠지면 각각 정원 초과와 감면 이중 사용이 시험에서 재현된다.
  3. **판정은 잠금 뒤에 다시 한다.** 멱등키 조회, 접수 상태, 회원 상태, 우선접수, 중복, 정원·대기 집계를 모두 잠금 아래에서 한다. 미리보기와 같은 `first_blocker`를 쓴다. 보이지 않는 강좌(작성중·종료·폐강)는 404다.
  4. **멱등.** 같은 키라도 회원·강좌가 같으면 이전 결과를 201로 다시 주고(그 사이 접수가 끝나거나 정원이 차도 같다), 다르면 409다. 회원도 강좌도 달라 잠금이 겹치지 않는 요청이 같은 키를 쓰는 경우는 (묶음, 멱등키) 유일키가 막고 이 오류를 409로 바꾼다.
  5. **배정.** 대기자가 없고 자리가 있을 때만 바로 배정한다. 결제예정액이 0원이면 수강확정(결제기한 없음, 결제 행도 만들지 않는다), 아니면 결제대기로 자리배정일시와 그 10분 뒤 결제기한을 저장한다. 그 밖에는 주민이고 대기정원이 남았을 때 대기 순번 `max+1`로 대기한다. 시각은 앱 시계 하나다(ADR-032).
  6. **금액과 감면.** 수강료·감면·결제예정액을 신청 행에 스냅샷으로 저장한다. 감면 적용 때는 신청 행에 사유(대상 유형만)와 심사자를 남기고 같은 트랜잭션에서 `TB_RDCT_HSTRY(DR.APPROVE)`를 추가한다. 이 이력이 있어야 같은 기수에 다시 쓰지 못하므로 감면 이력 기록(옛 B4-3d)을 이 단계에 합쳤다.
  7. **CSRF.** 신청 생성은 로그인에 더해 `X-CSRF-Token`이 맞아야 한다(`require_member_write`). 인증이 본문 검증보다 먼저라 로그인하지 않은 요청은 어떤 본문이든 401이다.
  8. **감사.** `APLY_CREATE`를 작업이력에 남긴다. 멱등키는 남기지 않는다.
- **남은 위험**: 같은 세션의 동시 요청은 `touch`의 세션 행 갱신 때문에 시작부터 직렬화된다. 이것이 정원 판정을 대신하지는 않으며 시험은 기기(세션)를 따로 써서 이를 배제했다. 실패(`APLY_FULL` 등)한 요청은 기록이 남지 않아 같은 키로 다시 보내면 처음부터 판정한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 동시성 시험은 서로 다른 DB 연결 7건(정원 경쟁 12명×4강좌, 연타, 같은 키 재전송, 같은 키 다른 강좌, 다른 회원이 같은 키, 감면 한 번만)이며 3회 반복에서 안정적이다. 변이 검사 50여 건 중 동등 변이(다른 보호 장치가 같은 일을 하는 것)를 빼고 모두 잡힌다.

### ADR-039
**신청 취소는 강좌 → 신청 잠금 아래에서 판정·반환하고, 같은 트랜잭션에서 대기자를 승격하며, 안내 문자는 아웃박스에만 쌓는다** — 승인 (TDD 5.3·5.7, ADR-028·038, RQ-FUN-FN-028·035·036·037, PRD Q16·Q18)

- **맥락**: 자리가 나면 운영자 개입 없이 다음 대기자에게 즉시 넘어가야 하고(FN-035), 같은 순간의 취소·신규 신청·다른 취소와 겹쳐도 정원 초과나 이중 승격이 없어야 한다. 문자 발송 실패가 기한에 영향을 주면 안 된다(FN-028).
- **결정**
  1. **취소 대상.** 대기, 결제 결과 확인 중이 아닌 결제대기, 개강 전의 결제 없는 확정이다(TDD 5.7). 승인 결과를 기다리는 결제(`PS.PENDING`)가 있으면 `PAY_RESULT_PENDING`, 결제한 확정·만료·종료는 `APLY_CANCEL_NOT_ALLOWED`다(결제한 확정은 환불로 안내). 남의 신청은 404다. 이미 취소한 신청을 다시 취소하면 같은 결과를 돌려주고 다시 반환·승격하지 않는다.
  2. **잠금과 판정.** 강좌 행 → 신청 행 순서로 잠근 뒤 최신 상태로 가능 여부를 다시 판정한다(C07). 결제창만 발급된(`PS.READY`) 이 신청의 결제는 함께 `PS.CANCEL`로 바꾼다.
  3. **자리 반환.** 보류나 확정이던 신청을 취소할 때만 자리가 난 것으로 보고 승격한다. 대기 신청 취소는 승격을 일으키지 않는다.
  4. **승격.** 같은 잠금 아래에서 정원이 찰 때까지 `(대기순서, 신청번호)`가 앞선 대기 신청을 하나씩 승격한다. 결제할 금액이 있으면 결제대기로 새 배정 시각과 그 10분 뒤 기한, 없으면 수강확정(기한 없음)이며 대기순서는 비운다. 순서가 된 회원이 탈퇴·제한이면 '자격 상실'로 취소하고 다음 대기자로 넘어간다. 취소된 신청의 이전 배정 시각은 지우지 않는다(SEAT-02).
  5. **승격 허용 범위.** 강좌가 공개 상태(공개·마감·운영중)이고 한국 날짜가 교육 시작일보다 앞일 때만 한다. 접수가 끝나도 이어지고(Q16), 교육 시작일부터는 하지 않는다(Q18). 작성중·종료·폐강 강좌에서는 하지 않는다.
  6. **안내 문자.** `TB_SMS_DMND`(`SM.AUTO`·`SG.EVENT`)와 `TB_SMS_TRGT`에 쌓기만 하고 발송은 하지 않는다. 문안은 센터명·강좌명·한국 시각의 기한·내역 링크(사이트 주소 + `/me/applications/{신청번호}`)만 담고 회원 이름·전화번호는 담지 않는다. 결제가 없으면 확정 안내다. 수신번호는 암호화해 저장한다. 번호가 없는 회원은 승격하되 문자는 쌓지 않고 작업이력에 그 사실을 적는다. 사건 식별자는 `PROMO:{신청번호}:{배정시각}`이라 (묶음, 유형, 식별자) 유일키가 중복을 막는다. 문안 해시는 문안의 SHA-256이다.
  7. **감사.** 취소는 `APLY_CANCEL`(회원), 승격은 `APLY_PROMOTE`(시스템)로 남긴다. 스키마 R21에 따라 시스템 작업은 회원·관리자를 비우고 대상은 신청 번호로 추적한다.
- **남은 일**: 문자의 실제 발송과 재조회는 B5 워커가 한다. 환불로 정원을 돌려주는 경로(B4-5)와 결제기한 만료(B5)도 이 승격 함수(`promote_waiters`)를 같은 방식으로 부른다. 문자에 쓰는 사이트 주소는 운영묶음의 `URL_ADDR`이며 값 확정은 계약 후다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 동시성 시험은 두 보유자의 동시 취소, 같은 신청의 8개 기기 동시 취소, 취소와 신규 신청 경쟁을 서로 다른 DB 연결로 확인하고 8회 연속 안정적이었다. 변이 검사 약 55건 중 다른 보호 장치가 같은 일을 하는 동등 변이(남의 신청·묶음 조건은 이후 조회가 한 번 더 막고, 대기자 행 잠금은 강좌 잠금이 이미 직렬화) 셋을 빼고 모두 잡힌다. 공백 5건은 시험을 보강했다.

### ADR-040
**결제 승인은 PG 호출 전에 결과 대기를 커밋하고 트랜잭션 밖에서 호출하며, 결과를 모르면 자리를 지킨다** — 승인 (TDD 5.4, ADR-006·010, RQ-FUN-FN-036·039·040·042, R12·R13)

- **맥락**: 결제는 외부 시스템이라 응답이 늦거나 사라질 수 있고, 같은 주문을 여러 기기가 동시에 확인할 수 있다. 결과를 모르는데 자리를 돌려주면 돈은 나갔는데 자리가 없다. 잠금을 쥔 채 외부를 부르면 같은 강좌의 모든 신청이 멈춘다.
- **결정**
  1. **PG 포트.** `PaymentGateway`는 결제창 값 준비(`prepare`)와 서버 대 서버 승인(`approve`)을 가진다. 승인 결과는 승인·거절·결과 불명으로 구분한다. 결제대행사와 가맹점 아이디는 계약 후 정해지므로 모의 어댑터만 있고 가맹점 아이디는 `TBD`다(`JORI_PG_PROVIDER`, `JORI_PG_MERCHANT_ID`).
  2. **결제 요청.** 강좌 → 신청 순서로 잠근 뒤, 결제 확인 중인 결제가 없고 신청이 결제대기이며 결제할 금액이 있고 기한 안일 때만 `PS.READY`를 만든다. 금액은 신청에 저장한 결제예정액이다. 같은 멱등키는 같은 신청·수단이면 이전 결과(기한은 신청의 값 그대로)를, 다르면 409다. 새로 요청하면 이전 결제창은 `PS.CANCEL`로 바꿔 하나만 쓰게 한다. 기한이 지났으면 그 자리에서 신청을 만료시키고 자리를 돌려 대기자를 승격한 뒤 알린다.
  3. **승인 확인은 세 단계다.** (1) 잠금 아래에서 금액(브라우저가 보낸 값은 대조에만), 결제 상태, 기한을 확인하고 `PS.PENDING`과 결제창이 준 `paymentKey`를 커밋한다. (2) 트랜잭션과 잠금 밖에서 PG를 부른다. 예외·시간 초과는 결과 불명으로 본다. (3) PG 응답 뒤 **시각을 새로 읽고** 다시 잠가 결과를 반영한다.
  4. **결과 반영.** 승인이고 PG가 알려 준 주문번호·금액·가맹점·통화가 우리 값과 같으면 결제완료·수강확정이다. 결과를 기다리는 동안 자리를 지켰으므로 기한이 그 사이 지났어도 확정한다. 거절이면 결제실패이고, 기한이 남았으면 신청을 결제대기로 두어 다시 결제하게 하고 지났으면 만료시켜 자리를 돌려준다. 결과 불명이면 `PS.PENDING`을 유지하고 자리를 지킨다. 승인이라는데 주문번호나 금액이 다르면 확정하지 않고 같은 확인 중 상태로 둔 채 실패 사건을 남겨 대사로 올린다. 그 사이 다른 경로(통보·대사)가 먼저 끝낸 결제는 덮어쓰지 않는다.
  5. **거래 아이디.** `PG_DLNG_ID`는 결제창이 준 `paymentKey` 그대로 둔다. (대행사, 가맹점, 거래 아이디) 유일키가 같은 거래를 두 결제에 연결하지 못하게 막고 환불에도 이 값을 쓴다. PG 응답의 거래 번호는 사건 기록에만 남긴다.
  6. **재확인.** 결제가 끝난 주문을 다시 확인하면 PG를 부르지 않고 같은 결과를 준다. 확인 중인 주문은 `PAY_RESULT_PENDING`, 실패·취소된 주문은 `PAY_NOT_PAYABLE`이다. 동시에 같은 주문을 확인해도 PG 승인 요청은 한 번이다.
  7. **기한 만료 공용 함수.** `expire_application`(결제창 취소, 신청 만료, 배정 시각·기한은 지우지 않음, 대기자 승격)을 결제 요청·확인이 쓰고 B5 워커도 같은 함수를 쓴다.
  8. **기록.** 요청·응답 사건은 정규화한 허용 항목과 내용 해시만 `TB_STLM_EVENT`에 남기고 PG 전문과 `paymentKey`는 남기지 않는다. 요청과 승인 결과는 `PAY_REQUEST`·`PAY_CONFIRM`으로 작업이력에 남긴다.
  9. **영수증.** 결제가 끝난 본인 건만 조회되고 아니면 404다.
- **남은 일**: PG 통보(웹훅)의 서명 검증과 멱등 수신(B4-4c), 결제기한 만료 워커와 `PS.PENDING` 재조회·대사(B5)가 남았다. 실제 대행사 어댑터는 ADR-007의 시간 초과(연결 3초, 읽기 10초, 포트의 상수)를 쓰고 시간 초과를 예외가 아니라 결과 불명으로 돌려줘야 한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 동시성 시험은 같은 주문의 8개 기기 동시 확인, 승인과 취소의 경쟁, 같은 신청의 동시 결제 요청, 같은 키의 동시 요청을 서로 다른 DB 연결로 확인하고 6회 연속 안정적이었다. 변이 검사 약 70건이 모두 잡히거나 동등 변이로 분류됐다.

### ADR-041
**PG 통보는 서명 확인 후 사건을 먼저 저장하고, 통보 내용이 아니라 거래 조회 결과로 반영한다** — 승인 (TDD 5.4.2, ADR-006·009·040, RQ-FUN-FN-041, R12·R13·R23)

- **맥락**: PG 통보는 같은 사건이 여러 번 오거나(재전송), 같은 사건 번호에 다른 내용이 오거나, 위조될 수 있다. 통보 본문이 말하는 상태를 믿으면 위조 한 번으로 결제가 확정된다.
- **결정**
  1. **경로와 노출.** `POST /api/pg/webhook/{provider}`(ADR-009)이며 이 배포가 쓰는 대행사(`JORI_PG_PROVIDER`)가 아니면 404다. 세션·CSRF 대신 서명으로 인증하고 프런트 계약(OpenAPI)에는 넣지 않는다.
  2. **서명.** 포트의 `parse_webhook`이 서명을 확인하고 사건 번호·주문번호·원문 해시만 돌려준다. 서명이 틀리거나 형식을 읽을 수 없으면 401이고 아무것도 저장하지 않는다. 보안 로그에는 요청 번호만 남기고 본문·서명 값은 남기지 않는다. 모의 어댑터는 HMAC-SHA256이며 실제 대행사의 방식은 계약 후 어댑터가 맡는다.
  3. **식별.** 같은 운영묶음에서 주문번호로 결제를 찾는다. 서명은 맞는데 우리 주문이 아니면 저장하지 않고 보안 로그에 격리하며 200으로 받았음을 알린다(재전송 폭주를 막는다, R23). **응답 코드의 근거.** 문서(TDD 5.4.2)가 정한 것은 서명 실패 401과 중복 200뿐이다. 격리·충돌·재시도를 200으로 받는 것은 문서에 없는 구현 판단이며, 대행사가 비2xx에 재전송 폭주를 일으키는 것을 막으려는 것이다. 실제 대행사의 재전송 정책이 정해지면 어댑터 계약과 함께 다시 확인한다.
  4. **멱등 저장.** 사건을 `ET.WEBHOOK`·`EP.RECEIVED`로 (결제, 사건 번호) 유일키 아래 저장하고 **PG를 부르기 전에 커밋한다.** 같은 사건이 다시 오면 업무를 바꾸지 않고 조회도 하지 않으며 `duplicate`로 응답한다. 같은 사건 번호에 해시가 다른 내용이 오면 업무에 반영하지 않고 작업이력(`JR.DENY`, 시스템)과 보안 로그에 남기며 `conflict`로 응답한다. 사건에는 사건 번호와 주문번호만 담고 원문은 복사하지 않는다.
  5. **거래 조회로 반영.** PG에 주문번호로 거래를 다시 조회해(트랜잭션·잠금 밖) 그 결과를 승인 확인과 같은 규칙(`_settle`)으로 반영한다. 조회에 실패하거나 결과를 모르면 사건을 `EP.FAIL`, 재시도 횟수 1로 남기고 업무는 바꾸지 않으며 `retry`로 응답한다(워커가 다시 시도, B5).
  6. **반영 규칙.** 결제가 `PS.READY`(결제창만 발급)이거나 `PS.PENDING`(확인 중)이고, 조회한 주문번호·금액·가맹점·통화가 우리 값과 같고, 신청이 결제대기면 결제완료·수강확정이다(사용자 확정: 금액이 맞으면 `READY`도 확정, 승인 확인을 보내지 못한 회원과 한 번에 승인하는 PG를 지원). 거절이면 `PS.FAIL`이고 기한이 지났으면 신청을 만료시킨다. 이미 결제완료인 주문은 바꾸지 않는다.
  7. **돈은 나갔는데 확정할 수 없는 경우.** 우리 결제가 이미 취소·실패로 닫혔거나 신청이 만료·취소됐는데 PG가 승인했다면 결제를 되살리지 않고, 이어받은 사람의 자리도 건드리지 않는다. 사건을 `EP.FAIL`로 하고 사유에 "보상환불 필요"를 적어 대사 화면에 올린다(R12). 환불 자체는 B4-5의 환불 기능이 한다. 승인 응답이 어긋날 때(주문번호·금액·가맹점·통화)도 같다.
  8. **기록.** 처리 결과는 `PAY_WEBHOOK`(시스템, 회원·관리자 비움, R21)으로 작업이력에 남긴다.
- **남은 일**: 재시도 대상 사건(`EP.FAIL`)과 `PS.PENDING` 재조회·대사는 B5 워커가 한다. 환불 접수 시 PG 취소(B4-5). 실제 대행사의 서명 방식·사건 번호 규칙·응답 형식은 계약 후 어댑터에서 구현한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 웹훅 기능 시험 35건과 동시성 시험(같은 통보 8회 동시 수신, 통보와 승인 확인의 경쟁, 조회 중 같은 통보)으로 확인했고 변이 검사 약 35건이 모두 잡히거나 동등 변이로 분류됐다.
### ADR-042
**환불 접수는 서버가 반환 기준액을 정하고, 접수 즉시 신청을 취소해 자리를 돌려준다** — 승인 (TDD 5.6·5.7, ADR-028·038·040, RQ-FUN-FN-043·045, 스키마 R14·R15)

- **맥락**: 결제한 수강확정은 취소가 아니라 환불로만 나간다(ADR-039). 환불 금액을 회원이 입력하면 조작할 수 있고, 환불을 접수하고도 신청이 남으면 자리를 잡은 채 환불이 길어진다.
- **결정**
  1. **금액은 서버가 정한다.** 요청에는 신청 번호와 사유만 받고 금액을 받으면 400이다(DV25). 반환 기준액은 개강일(한국 날짜) 전이면 원결제액 전액이다. 개강 후에는 `원결제액 − 월 수강료 × 경과 개월(당월 포함)`이고 월 수강료는 `원결제액 ÷ 교육 개월 수`의 몫이다. 교육 기간을 다 보냈으면(경과 ≥ 교육 개월) 0이다. 나눗셈의 나머지 원은 교육 기간 중에는 환불액에 남고(예: 100,000원·3개월 첫 달 66,667원), 기간을 다 보낸 뒤에는 0으로 닫는다. 공식은 PRD Q15 잠정안이며 기관 승인본이 나오면 `calc.py`만 바꾼다. 응답에 산정 근거(`basis`)를 함께 준다.
  2. **접수 가능 조건.** 신청이 `ES.CONFIRM`이고 `PS.PAID` 결제가 있고 기준액이 0보다 크면 접수한다. 같은 결제에 진행 중인 환불(요청·보류·승인·처리 중·실패)이 있으면 새로 받지 않는다(`RFND_NOT_ALLOWED`). 접수 금액은 `기준액 − 잡혀 있는 환불 합계(반려 제외)`이고 0 이하면 `RFND_LIMIT_EXCEEDED`다.
  3. **잠금 순서.** 강좌 → 신청 → 결제 순으로 잠근 뒤 한도를 판정한다(C07, R14). 환불 한도는 결제 행을 잠근 상태에서만 판정한다.
  4. **접수 즉시 취소(사용자 확정).** 환불 행(`RS.REQUEST`)을 넣은 같은 트랜잭션에서 결제창만 발급된 결제를 정리하고 신청을 `ES.CANCEL`(사유 "환불 접수")로 바꾸며 자리를 돌려주고 대기자를 승격한다(개강 전일 때만, ADR-039). 환불이 반려돼도 신청은 되살리지 않는다.
  5. **멱등.** `Idempotency-Key`가 같고 신청이 같으면 이전 환불을 돌려주고, 신청이 다르면 409다. 다른 신청이 같은 키를 동시에 쓰는 경우는 (운영묶음, 멱등키) 유일키가 마지막으로 막는다.
  6. **소유권.** 남의 신청·없는 신청은 404이고 내역은 요청 회원의 것만 보인다. 작업이력은 `RFND_REQUEST`로 남긴다.
  7. **PG 취소는 이 단계에서 부르지 않는다.** 환불 승인·집행(PG 취소 호출)은 관리자 업무(B4-6)에서 한다. 접수는 DB 변경만 한다(트랜잭션 안에서 외부 호출 금지).
- **API**: `GET /me/applications/{id}/refund-preview`(TDD 10.2에 없던 것, 문서에 반영 필요), `POST /me/refunds`, `GET /me/refunds`.
- **남은 일**: 신청 화면의 `canRequestRefund`는 아직 기준액 0을 반영하지 않는다(접수하면 `RFND_NOT_ALLOWED`로 막힌다). 환불 승인·반려·보류·집행과 폐강 환불은 B4-6.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 25건(공식 7건 포함)과 변이 검사 10건으로 확인했고, 진행 중 환불 차단 변이가 한 건 살아남아 시험을 추가해 잡았다. 환불 동시 접수의 서로 다른 DB 연결 시험은 B4-6에서 집행과 함께 추가한다.
### ADR-043
**관리자 권한은 같은 배정 행에서 기능·범위·유효기간을 함께 판정하고, 범위는 대상 레코드의 강좌 동으로 본다** — 승인 (TDD 4.2, 스키마 R19·R20·R28·R29, RQ-SER-NF-003)

- **맥락**: 관리자 라우터에는 세션 쿠키 선언만 있고 판정이 없었다. 역할과 동을 따로 합치면 A동 강좌 권한과 B동 게시판 권한이 곱집합으로 커진다.
- **결정**
  1. **세션.** `require_admin`은 살아 있는 관리자 세션과 사용 중(`USE_YN=Y`)인 계정을 요구한다. 아니면 401이다. 운영묶음은 세션이 아니라 배포 설정에서 해석한다. 활동으로 보는 요청은 유휴 15분을 다시 세고 `X-Background: 1` 요청은 세지 않는다. 상태를 바꾸는 요청(`require_admin_write`)은 CSRF 토큰도 맞아야 한다(403).
  2. **판정 단위.** `scope_for`는 `TB_MNGR_SCP` 배정 행마다 (역할이 이 권한을 가짐 + 배정·역할 사용 중 + 유효기간 안 + 이 운영묶음)을 함께 보고, 맞는 행의 범위만 합친다. 서로 다른 행의 역할과 동을 섞지 않는다. 유효 시작은 포함, 종료는 포함하지 않는다.
  3. **범위 종류.** `SK.GROUP`은 묶음 전체, `SK.DONG`은 그 동만이다. `SK.SYSTEM`은 운영구조·역할배정 권한(GRP_R·GRP_W·DONG_W·MNGR_W·ROLE_W·GRANT_W)에만 효력이 있고 회원·결제·환불 같은 업무 권한에는 효력이 없다(R20·R29).
  4. **대상 판정.** 범위 판정 값은 요청 파라미터가 아니라 대상 레코드에서 읽는다. 환불은 결제 → 신청 → 강좌의 `DONG_SN`이다. 동이 없는 강좌(묶음 공통)는 묶음 범위만 다룬다. 동 범위 담당자는 동이 없는 대상을 볼 수 없다.
  5. **응답.** 권한이 하나도 없으면 403이다. 권한은 있으나 대상이 범위 밖이거나 없으면 같은 404다(존재 여부를 알리지 않는다). 목록은 범위 안의 것만 SQL에서 거른다.
- **API 권한 매핑**: 화면설계서 5절(ADM-PAY-004·004P)에 따라 환불 목록은 `AU.RFND_A`만, 상세는 `AU.RFND_A` 또는 `AU.RFND_X`(범위 합)다. 대리 접수·보류·해제·승인·반려는 `AU.RFND_A`, 집행·이체 확인은 `AU.RFND_X`다. 집행 권한만 가진 담당자는 목록이 아니라 상세 링크로 들어온다.
- **남은 일**: 나머지 관리자 라우터에 같은 의존성을 붙이는 일(B4-6 이후 단계), 위임·자기 권한 상승 제한(R28).
- **결과**: 새 테이블·컬럼 없이 구현했다. 권한 판정 단위 시험 17건과 환불 API 시험으로 확인했다.

### ADR-044
**환불 승인은 승인 시점의 반환 기준액까지, 집행은 승인자와 다른 담당자가 PG 취소 멱등키로 한다** — 승인 (TDD 5.6, ADR-006·042·043, RQ-FUN-FN-043~046, R14·R15)

- **맥락**: 환불은 돈이 나가는 일이라 한도 초과, 이중 집행, 결과 불명이 가장 위험하다. 승인·집행을 한 사람이 하면 견제가 없다.
- **결정**
  1. **승인.** `RS.REQUEST`에서만 `RS.APPROVE`로 간다(보류 건은 먼저 해제한다). 결제와 환불 행을 이 순서로 잠근 채 검사한다. 승인액은 요청액 이하이고, `다른 환불이 차지한 금액 + 승인액`이 승인 시점의 반환 기준액을 넘으면 `RFND_LIMIT_EXCEEDED`다(사용자 확정: 기준액까지). 다른 환불이 차지하는 상태는 승인·처리 중·완료·실패다. 접수·보류·반려는 차지하지 않는다. 한 건의 `RFND_AMT`만 있어 요청액과 승인액을 따로 저장하지 못한다. 요청액은 감사이력에 남기고 이 한계는 스키마 개정 요청 후보로 둔다.
  2. **대리 접수.** 회원 접수와 같이 접수 즉시 신청을 취소하고 자리를 돌려준다(사용자 확정, ADR-042). 금액은 담당자가 정하고 접수 때도 `기존 환불 합 + 접수액 ≤ 원결제액`을 본다. 같은 키·같은 신청은 이전 결과, 다른 신청은 409다.
  3. **집행 권한.** 승인한 담당자는 집행도 이체 확인도 할 수 없다(PRD Q22 임시 기준, 422). 집행·재처리는 `RS.APPROVE`·`RS.FAIL`에서만 가능하고 재처리도 한도를 다시 검사한다.
  4. **집행 흐름(PG 취소).** (1) 결제·환불을 잠그고 검사한 뒤 `RS.PENDING`과 집행자·요청 시각을 커밋한다. (2) 트랜잭션 밖에서 PG 취소를 부른다. 멱등키는 `RFND-{운영묶음}-{환불번호}`로 고정이고 재처리도 같다. (3) 다시 잠그고 결과를 반영한다. 응답이 없거나 오류면 같은 키로 취소 조회를 해서 확인한다. 취소 완료는 `RS.DONE`(완료 시각·PG 취소 번호), 거절은 `RS.FAIL`, 끝내 모르면 `RS.PENDING`으로 두고 재집행을 막는다(워커가 재조회, B5). PG가 알려 준 취소 금액이 요청과 다르면 완료도 실패도 아닌 채 확인 필요 사건(`EP.FAIL`)만 남긴다. 사건은 `TB_STLM_EVENT`에 환불 번호와 함께 남고 원결제는 바꾸지 않는다.
  5. **수동 계좌환불.** 은행·계좌·예금주가 모두 있을 때만 수동이다(R15). 집행은 `RS.PENDING`으로만 바꾸고 PG를 부르지 않으며, 이체 후 이체 확인으로 `RS.DONE`이 된다. 화면에는 계좌·예금주를 가려서만 준다. 입력은 회원이 환불 신청 때 선택 입력한다(사용자 확정). `POST /me/refunds`에 `bankCode`·`accountHolder`·`accountNumber`를 함께 보내면 서버가 AES-256-GCM으로 암호화해 저장하고 응답·감사이력에는 담지 않는다. 일부만 보내거나 형식이 틀리면 400이다. 수동 환불의 판단 기준과 화면의 노출 시점은 기관 확인 전이라 개정 요청서 R27에 적었다.
  6. **버전·상태.** 모든 전이는 `RCRD_VER`로 낙관적 잠금을 하고 현재 상태에서 갈 수 없으면 409(`CONFLICT_STATE`), 버전이 다르면 409(`VERSION_CONFLICT`)다. 작업이력(`RFND_*`)에 남긴다.
  7. **목록·지연.** 접수·보류 건을 오래된 순으로 먼저 보이고 나머지는 최신순이다. 지연은 접수 뒤 3영업일을 넘긴 검토 중 건이며 공휴일 자료가 오기 전까지 주말만 뺀다.
- **PG 포트**: `cancel(order_no, amount, idempotency_key)`와 `lookup_cancel(idempotency_key)`를 추가했다. 실제 대행사의 취소 API는 계약 후 어댑터가 맡는다.
- **남은 일**: PS.PENDING처럼 RS.PENDING 환불의 재조회·대사는 B5 워커가 `settle_cancel`로 한다. 폐강 환불(일괄), 환불 CSV 내보내기, 증빙 첨부 경로.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 52건과 서로 다른 DB 연결의 동시성 시험 4건(같은 건 4명 동시 집행 시 PG 취소 한 번, 같은 결제 두 건 동시 승인 시 한도 준수, 같은 건 동시 승인, 회원·담당자 접수 경쟁)으로 확인했고 6회 연속 안정적이었다.
### ADR-045
**관리자 신청·대기 조회는 강좌의 운영 동으로 범위를 가르고, 이력은 작업이력에서 읽는다** — 승인 (TDD 4.2·10, 화면설계서 ADM-APL, RQ-FUN-FN-025·035·036, ADR-043)

- **맥락**: 관리자 신청 화면은 조회 전용이고(관리자가 신청 상태를 직접 바꾸지 않는다) 신청·결제·환불을 한 화면에서 본다. 범위는 신청자 거주지가 아니라 강좌의 운영 동이다.
- **결정**
  1. **권한·범위.** 목록·상세·대기 현황은 모두 `AU.APLY_R`이다. 범위는 신청이 걸린 강좌의 `DONG_SN`이며 동 담당자는 자기 동 강좌만, 묶음 담당자는 전체를 본다. 범위 밖이거나 없는 대상은 같은 404다. 동이 없는 강좌(묶음 공통)는 묶음 담당자만 본다.
  2. **목록.** 신청자 이름은 가려서 준다. 표시 상태는 회원 화면과 같은 판정(`flags`)을 쓰고 결제·환불 상태는 가장 최근 결제와 그 결제의 마지막 환불이다. 검색어는 신청번호(숫자) 또는 이름 일부이고 와일드카드 문자는 글자로만 찾는다. 기간은 한국 날짜 기준이다(시작일 00:00 포함, 종료일 다음 날 00:00 미포함). 최신순이다.
  3. **상세 이력.** 새 테이블 없이 작업이력(`APLY_CREATE·APLY_PROMOTE·APLY_EXPIRE·APLY_CANCEL`, 성공만)에서 읽는다. 이전·이후 상태는 작업 메모의 상태 코드에서 읽으므로 승격 작업 메모에 `(ES.HOLD)`·`(ES.CONFIRM)`을 넣도록 바꿨다. 환불 접수로 취소된 신청은 환불 이력(`RFND_REQUEST`)이 따로 있다.
  4. **멱등 재요청 기록.** 재요청은 이전 결과를 돌려줄 뿐 저장하지 않는다(새 테이블 없음). 응답의 `replays`는 항상 빈 목록이다. 계약 필드는 유지한다.
  5. **대기 현황.** 대기 신청이 있는 강좌만 목록에 나온다. 점유는 결제대기와 수강확정 신청 수(ADR-028), 다음 대기 순번은 대기가 있으면 1이다. 대기자는 대기 순서·신청 번호 순이고, 최근 승격 시각은 승격 작업의 최신 시각이다. 승격 이력은 최신 순이며 문자 결과는 아웃박스(`TB_SMS_TRGT`) 상태로 정한다(대기·요청 중·결과확인 중은 대기, 발송 확인은 발송 완료, 실패·제외는 실패). 수신번호가 없어 문자를 쌓지 않은 승격은 실패로 보인다.
  6. **조인 주의.** 작업이력의 대상 키는 문자열이라 숫자 키와 문자열 변환으로 조인하면 정렬 규칙 충돌이 날 수 있다. 신청 번호를 먼저 구해 `IN`으로 찾는다.
- **남은 일**: 신청 CSV 내보내기(B4-7).
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 24건과 변이 검사 약 30건으로 확인했고 생존 변이 8건은 시험을 추가해 모두 잡았다.
### ADR-046
**결제 대사는 PG 재조회와 수동 대사 모두 승인 확인과 같은 반영 규칙을 쓰고, 확인되지 않은 상태를 임의로 정하지 않는다** — 승인 (TDD 5.4, ADR-006·040·041, RQ-FUN-FN-041·042, R12·R13, 화면설계서 ADM-PAY-003)

- **맥락**: 결과를 모르는 결제(`PS.PENDING`)는 자리를 지킨 채 대사로 올라온다. 담당자가 잘못 정하면 돈을 받고 신청이 사라지거나 그 반대가 된다.
- **결정**
  1. **권한·범위.** 목록·상세는 `AU.STLM_R` 또는 `AU.STLM_W`, 재조회·수동 대사는 `AU.STLM_W`다. 범위는 거래가 걸린 신청의 강좌 동이고 범위 밖·없음은 같은 404다. 상세의 재조회·대사 가능 여부는 결과 확인 중이고 쓰기 권한이 범위 안일 때만 참이다.
  2. **목록.** 결과 확인 중인 거래를 먼저, 그 안에서는 최근 요청순이다. 검색어는 주문번호 일부 또는 신청번호(숫자)이고 기간은 한국 날짜 기준이다. 충돌만 보기는 충돌 통보로 격리된 거래만 보인다. 재조회 횟수는 `RECHECK:` 접두 재조회 사건 수이고 수동 대사 사건(`MANUAL:`)은 세지 않는다. 자동 재조회 한도 표시는 3회다(관리자 재조회는 한도를 세지 않는다).
  3. **상세.** 통보 이력은 저장된 통보(해시 앞 8자만)와 충돌로 격리한 통보다. 중복 통보는 저장하지 않으므로 이력에 나오지 않고, 충돌 통보는 해시를 남기지 않아 해시 앞부분이 빈 값이다. 조치 이력은 `PAY_RECHECK`·`PAY_RECONCILE` 작업이력(성공만)이다.
  4. **PG 재조회.** 결과 확인 중인 거래만 가능하다(아니면 409, PG를 부르지 않는다). 요청 세션의 잠금을 풀기 위해 먼저 커밋하고 트랜잭션 밖에서 거래를 조회한다. 그 뒤 강좌 → 신청 → 결제를 잠그고, 그 사이 통보·워커가 먼저 끝냈으면 다시 반영하지 않고 그 결과를 따른다. 반영은 승인 확인·통보와 같은 규칙(`settle_payment`)이다. 승인이면 결제완료·수강확정, 거절이면 결제실패(기한이 지났으면 신청 만료·자리 반환·승격), 결과 불명·조회 실패는 그대로 두고, 응답이 어긋나면(주문번호·금액·가맹점·통화) 확정하지 않고 대사 필요 사건(`EP.FAIL`)으로 남긴다. 모든 경우 `ET.RECON` 사건과 작업이력을 남긴다.
  5. **수동 대사.** PG 관리자 화면에서 확인한 사실만 입력한다. 근거는 5자 이상 필수, 성공이면 승인번호가 필수다(없으면 422). 읽은 버전이 다르면 409, 결과 확인 중이 아니면 409다. 성공은 우리 값과 같은 승인으로, 실패는 거절로 같은 반영 규칙에 넣는다. 근거는 사건 내용에 담고 작업이력에는 담지 않는다. PG를 부르지 않으며 재조회 횟수에 세지 않는다.
- **남은 일**: 거래 CSV 내보내기(B4-7), 근거 파일 첨부(첨부 설계 뒤), 자동 재조회 워커(B5)는 같은 사건 접두(`RECHECK:`)를 쓴다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 34건과 동시성 시험 2건(4명 동시 재조회, 재조회·수동 대사 경쟁)으로 확인했고 변이 검사 약 25건이 모두 잡혔다.
### ADR-047
**교육기수·강좌 관리는 공개 전 재검사와 폐강 시 신청 취소·전액 환불 접수를 한 트랜잭션으로 한다** — 승인 (TDD 4.2·5·10, 화면설계서 ADM-EDU-001·002, RQ-FUN-FN-047·048·057, ADR-006·028·042·043)

- **맥락**: 강좌는 신청·결제·환불의 뿌리다. 정원을 점유보다 줄이거나, 승인 안 된 강사로 공개하거나, 폐강하면서 돈과 신청이 어긋나면 되돌리기 어렵다.
- **결정**
  1. **권한·범위.** 기수는 묶음 공통 설정이라 `AU.CONF_W`를 묶음 전체 범위로 가진 담당자만 다룬다(동 담당자는 403, R28). 강좌 조회는 `AU.CORS_R` 또는 `AU.CORS_W`, 변경은 `AU.CORS_W`이며 범위는 강좌의 운영 동이다. 범위 밖·없음은 404이고 자기 범위 밖의 동에는 강좌를 만들거나 옮길 수 없다(403). 선택지는 `AU.CORS_R·CORS_W·CONF_W·ATND_R·APLY_R·STAT_R·SMS_SEND` 중 하나면 받고 강좌 선택지는 범위 안만 담는다.
  2. **기수.** 연도·차수는 같은 묶음에서 유일하다(422). 모집기간은 한국 날짜이고 종료일은 그날 끝까지 포함하도록 다음 날 00:00(미포함)으로 저장한다. 상태는 사용중만 `USE_YN=Y`이고 나머지는 N이며, 읽을 때 연결 강좌가 없으면 작성중, 있으면 사용중지다(사용자 확정, 개정 요청 R29). 등록은 묶음 행을 잠근 채 멱등 표식(키·내용 해시를 작업이력 메모에 기록, R28)을 조회한다. 같은 키·같은 내용은 이전 결과, 다른 내용은 409다.
  3. **강좌 등록·수정.** 틀린 입력은 필드별 사유로 한 번에 422로 알린다(기수·동·분류 존재, 승인 강사, 접수 순서, 관외 접수 시작은 접수 시작 이상 종료 미만, 교육기간은 기수 안). 정원은 강좌 행을 잠근 뒤 센 현재 점유(`ES.HOLD`+`ES.CONFIRM`)보다 작게 줄일 수 없다. 폐강한 강좌는 고칠 수 없고(409) 읽은 버전이 다르면 409다. 등록은 작성중으로 시작하고 결제 대기 분은 10분, 분류 코드 컬럼은 기본값으로 채운다. 온라인·방문 정원 배분 입력은 없다. 공고 모집정원은 항상 null이다(R29).
  4. **공개·접수마감.** 공개 요청은 그 시점에 승인 강사, 일정 1건 이상, 기수 안의 교육기간, 아직 끝나지 않은 접수기간을 다시 검사한다. 접수마감은 접수 중인 공개 강좌만 가능하다.
  5. **폐강.** 사유가 필수이고 공개·접수마감·운영중 강좌만 폐강한다. 강좌 행을 잠근 채 유효한 신청(대기·결제대기·수강확정)을 모두 취소하고(사유 "폐강", 결제창만 발급된 결제는 취소), 결제완료 건마다 원결제액에서 이미 잡힌 환불을 뺀 금액의 환불 요청(`RS.REQUEST`, 요청자는 폐강한 담당자)을 접수한다(사용자 확정: 전액 접수, 기관 사유라 반환 기준액 공식을 쓰지 않는다). 환불의 승인·집행은 환불 검토에서 사람이 한다. 폐강은 환불 완료가 아니다(FN-057). 결제 결과를 확인 중(`PS.PENDING`)인 신청이 있으면 자리를 지켜야 하므로 409로 막고 아무것도 바꾸지 않는다(사용자 확정, ADR-006). 폐강한 강좌는 대기자를 승격하지 않고 문자도 쌓지 않는다.
  6. **미리보기.** 폐강 전 모달에 유효한 신청 수와 결제완료 수를 보인다.
- **남은 일**: 기수·강좌 CSV 내보내기(B4-7), 일정·휴보강·시설·강사 심사·분류는 각 라우터에서 구현한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 44건과 동시성 시험 2건(폐강과 신청 경쟁, 같은 강좌 동시 폐강)으로 확인했다.
### ADR-048
**워커는 API와 같은 코드를 쓰는 별도 프로세스이며, 대상을 DB 상태로 찾아 항목마다 커밋하고 기존 반영 규칙을 그대로 재사용한다** — 승인 (TDD 7, ADR-004·006·027·040·041·044·046, RQ-FUN-FN-036·042·046)

- **맥락**: 결제기한이 지난 신청과 결과를 모르는 결제·환불은 사람이 누르기 전에도 정리돼야 한다. API 요청이 없으면 만료가 일어나지 않고 자리가 묶인다.
- **결정**
  1. **배치.** 워커 코드는 `app/worker/`(작업 `jobs.py`, 실행기 `runner.py`, 상태 파일 `status.py`, 진입점 `__main__.py`)에 두고 `python -m app.worker`로 자치회마다 한 프로세스만 띄운다. ADR-021의 `apps/worker` 별도 패키지 대신 도메인 코드를 경로 의존 없이 그대로 쓰도록 API 패키지 안에 둔 것이며, 프로세스는 분리된다(배포 구성은 계약 후 확정). 스케줄러는 APScheduler(`max_instances=1`, `coalesce`)다.
  2. **공통 규칙.** 대상은 DB 상태로 찾고 항목마다 새 트랜잭션에서 잠그고 다시 확인한 뒤 커밋한다. 그 사이 다른 경로가 먼저 끝냈으면 건드리지 않는다. 외부 호출(PG)은 트랜잭션 밖이다. 모든 상태 변경은 `AK.SYSTEM` 작업이력이고 회원·관리자는 비운다(R21). 한 번에 50건까지 집고 나머지는 다음 주기가 잇는다.
  3. **`expire_payments`(10초, TDD 7.1).** 기한(`STLM_DDLN_DT`) 정각 이후의 결제대기 신청을 `expire_application`(결제창 취소, 신청 만료, 대기자 승격)으로 처리한다. 결제 결과 확인 중(`PS.PENDING`) 신청은 건너뛴다(ADR-006). 강좌 행은 `FOR UPDATE SKIP LOCKED`로 잡아 다른 처리가 쥐고 있으면 기다리지 않고 건너뛴다. 기한이 오래된 것부터 처리한다.
  4. **`recheck_payments`(30초, TDD 7.2).** 결과 확인 중인 결제를 요청 30초 뒤부터, 1분 간격으로 최대 3회 PG에 조회해 승인 확인과 같은 규칙(`settle_payment`)으로 반영한다. 재조회 횟수는 `RECHECK:` 접두 재조회 사건 수이며 수동 대사 사건(`MANUAL:`)은 세지 않는다. 3회 뒤에는 자동 조회를 멈추고 담당자의 수동 대사에 맡긴다(결제 상태는 `PS.PENDING` 유지). 조회 실패는 결과 불명으로 보고 사건만 남긴다.
  5. **`recheck_refunds`(30초, TDD 7.2).** PG 취소를 요청한 뒤 결과를 모르는 환불(`RS.PENDING`)을 요청 30초 뒤부터 같은 멱등키로 조회해 `settle_cancel`로 확정한다. 수동 계좌환불은 대상이 아니다. 자동 횟수 한도는 두지 않는다(문서가 정하지 않았다).
  6. **상태 파일.** 작업마다 마지막 실행 시각·성공 여부·오류 종류를 JSON 파일(`JORI_WORKER_STATUS_FILE`, 기본 `/var/run/jori/worker-status.json`)에 임시 파일로 쓴 뒤 바꿔 쓴다. 오류 내용은 담지 않는다. 5분 넘게 아무 작업도 돌지 않았거나 파일이 없으면 정지로 본다(`is_stale`). 작업 하나의 오류는 삼켜서 기록하고 다른 작업과 워커는 계속 돈다.
- **남은 일**: `sms_dispatch`(5초, 아웃박스 발송과 `SS.UNKNOWN` 조회), `file_scan`, `consistency_check`(03:00), `retention`(04:00)은 이어서 만든다. `/api/health`가 상태 파일을 읽는 연결과 웹훅 재시도 사건(`EP.FAIL`)의 재조회, 실제 배포(systemd 단위·watchdog)도 남았다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 36건과 동시성 시험 2건(4개 워커 동시 실행, 강좌가 잠긴 동안 건너뛰기)으로 확인했다.
### ADR-049
**문자 발송은 시도를 먼저 확정한 뒤 보내고, 결과를 모르는 문자는 다시 보내지 않고 조회한다** — 승인 (TDD 7.3·8.2, SMS-01~04, RQ-FUN-FN-028·059, ADR-048)

- **맥락**: 승격 안내 같은 자동 문자는 아웃박스에만 쌓이고 실제로 나가지 않았다. 문자는 한 번 나가면 되돌릴 수 없어 중복 발송이 가장 나쁘다.
- **결정**
  1. **대상.** 수신대상 상태가 `SS.WAIT`인 문자를 5초 주기로 한 번에 50건까지, 오래된 순으로 보낸다. 요청의 `SRC_EVENT_ID`가 `CERT:`로 시작하는 OTP 문자는 건드리지 않는다(인증번호 원문은 API만 안다, TDD 8.1).
  2. **발송 순서.** 수신대상을 `FOR UPDATE SKIP LOCKED`로 잡고 (1) 시도 행(`TB_SMS_SNDNG_HSTRY`, 순번 1, 멱등키 `sms-{수신대상}-{순번}`)과 `SS.UNKNOWN`을 먼저 커밋한 뒤 (2) 트랜잭션 밖에서 어댑터를 부르고 (3) 결과를 반영한다. 호출 직후 죽어도 같은 문자를 새로 보내지 않고 조회로 확인한다.
  3. **결과.** 접수는 `SS.SENDING`, 거절 확인은 `SS.FAIL`(결과 확인 시각·사유 기록), 시간 초과·예외는 `SS.UNKNOWN`이다. 거절과 결과 불명은 자동으로 다시 보내지 않는다. 확인된 실패의 재발송은 승인된 사람 요청으로만 새 순번을 만든다(SMS-04, 관리자 문자 발송 기능에서).
  4. **조회.** 접수(`SS.SENDING`)한 문자의 최종 전달과 결과를 모르는(`SS.UNKNOWN`) 문자의 실제 발송 여부를 같은 멱등키·메시지 번호로 공급자에 묻는다. 시도 30초 뒤부터 매 주기 조회한다. 전달 확인은 `SS.SENT`, 실패 확인은 `SS.FAIL`로 바꾸고, 접수 중이거나 모르면 그대로 둔다. 조회 중 다른 처리가 먼저 정한 상태는 덮어쓰지 않는다.
  5. **어댑터 규약.** `SmsSender`에 `lookup(idempotency_key, message_id)`와 전달 상태(`DELIVERED`·`FAILED`·`PENDING`·`UNKNOWN`)를 더하고 `send`가 멱등키를 선택으로 받는다. 키를 받는 공급자에는 같은 키로 한 번만 발송하게 한다. 실제 공급자 연동은 계약 후 어댑터가 한다(PRD Q2~Q4).
  6. **개인정보.** 수신번호는 암호문을 풀어 어댑터에만 넘기고 시도 이력·작업이력·로그에는 남기지 않는다.
- **알아둘 점**: 보내기 전 커밋과 발송 사이에 죽으면 그 문자는 `SS.UNKNOWN`으로 남고 공급자에 기록이 없어 계속 `UNKNOWN`으로 조회된다. 자동으로 다시 보내지 않으므로 일일 정합성 점검(7.5)이 오래된 `SS.UNKNOWN`을 운영 업무로 올려야 한다.
- **남은 일**: 정합성 점검, 관리자 문자 발송 화면의 승인된 재발송, 실제 공급자 어댑터.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 22건과 동시성 시험 3건(4개 워커 동시 발송, 호출 중 다른 연결에서 시도 확인, 잠긴 대상 건너뛰기)으로 확인했고 변이 검사 약 25건이 모두 잡히거나 동등 변이로 분류됐다.
### ADR-050
**정합성 점검은 원자료를 조회해 오래 확정되지 않은 항목을 찾고, 건강 확인은 DB와 워커 상태 파일로 판정한다** — 승인 (TDD 7.5·7, PRD FN-066, ADR-027·048·049)

- **맥락**: 결제·환불·문자는 자동 재조회 뒤에도 확정되지 않을 수 있고, 워커가 멈추면 만료·발송이 조용히 사라진다. 대시보드의 "확인할 업무"는 저장하지 않고 원자료에서 집계한다(FN-066).
- **결정**
  1. **점검 함수.** `find_stale`은 읽기 전용이며 (1) `PS.PENDING` 결제(마지막 수정 시각, 없으면 요청 시각 기준) 24시간 이상, (2) `RS.PENDING` 환불(집행 요청 시각) 24시간 이상, (3) `SS.UNKNOWN` 문자(OTP 제외) 1시간 이상, (4) `FS.PENDING` 파일 1시간 이상을 찾는다. 기준 시각은 정각을 포함한다. 종류마다 오래된 순으로 200건까지 목록에 담고, 건수는 잘려도 정확히 센다. 대시보드가 같은 함수를 쓰도록 워커와 분리했다. 기준 값은 문서가 정하지 않은 보수적 값이라 개정 요청서 R30에 적는다.
  2. **일일 작업.** `consistency_check`는 매일 03:00(한국 시각)에 점검하고 이상이 있으면 종류별 건수만 로그 경고로 남긴다(식별자·개인정보는 담지 않는다). 상태 파일에는 처리 건수(`handled`)로 남는다. 아무것도 바꾸지 않는다.
  3. **상태 파일.** 작업 기록에 `handled`(처리 건수)를 더했다. 크론 작업은 실행기의 `cron=(시, 분)`으로 한국 시각에 돈다.
  4. **`GET /api/health`.** 인증 없이 부르고 계약 문서에는 싣지 않는다. DB에 `SELECT 1`이 닿고, 상태 파일의 마지막 실행이 5분 이내(정확히 5분은 정상)이며, 모든 작업의 마지막 실행이 성공이면 200이다. 하나라도 어긋나면 503이고 본문은 `status`·`database`·`worker.running`과 작업별 마지막 실행·성공 여부만 담는다. 오류 내용과 처리 대상은 담지 않는다. 상태 파일 경로는 `JORI_WORKER_STATUS_FILE`(기본 `/var/run/jori/worker-status.json`)이며 로컬에서 워커 없이 띄우면 503이다.
- **남은 일**: 대시보드의 "확인할 업무"(`/dashboard`)가 `find_stale`을 읽는 연결, `retention`(04:00), `file_scan`, 웹훅 재시도 사건(`EP.FAIL`)의 재조회, systemd 단위·watchdog 배포.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 20건과 변이 검사 약 25건으로 확인했다.
### ADR-051
**목록 CSV는 목록과 같은 조회에서 페이지 제한만 풀어 만들고, 수식 주입을 막으며, 만든 사실을 기록한다** — 승인 (TDD 8.6, TRD 4.6, RQ-FUN-FN-068, ADR-043)

- **맥락**: CSV는 화면과 다른 값을 내보내거나 범위를 벗어나는 가장 흔한 경로이고, 스프레드시트가 셀을 수식으로 실행할 수 있다.
- **결정**
  1. **같은 조회.** 목록 서비스를 필터 조회(`_filtered`)와 쪽 나누기로 나누고 CSV는 같은 필터 조회를 쓴다. 권한·범위·조건·정렬·가림이 목록과 한 곳에서 정해져 서로 어긋날 수 없다. 환불 CSV도 목록과 같은 권한(`AU.RFND_A`)이다.
  2. **형식.** UTF-8 BOM, 쉼표 구분, RFC 4180(따옴표·줄바꿈 이스케이프, CRLF). 시각은 한국 시각(`YYYY-MM-DD HH:MM:SS`), 날짜는 `YYYY-MM-DD`다. `=` `+` `-` `@` 탭 `\r`로 시작하는 글자는 앞에 작은따옴표를 붙이고 머리글도 같다. 숫자는 글자가 아니라 값이라 음수 부호를 막지 않는다. 응답은 `Cache-Control: no-store`이고 한글 파일명은 RFC 5987(`filename*`)로 주며 영문 대체 이름은 안전한 문자만 남긴다.
  3. **한도.** 5만 행(계약)을 넘으면 만들지 않고 `RULE_REJECTED`로 조건을 좁히라고 안내한다. 한도 정확히는 만든다. 한 건 더 읽어 넘침을 판정하므로 전체를 메모리에 올리지 않고도 알 수 있다. 결제·환불 같은 조인 조회는 번호 목록을 1000건씩 나눠 읽는다.
  4. **담는 값.** 신청자 이름은 목록과 같이 가린 값이고 환불 계좌·증빙·원문 개인정보는 담지 않는다. 확인 중인 결제 금액은 상태 열로 구분한다. 비식별 목록이라 `AU.EXPORT`가 필요 없다(개인식별 명단은 별도, ADR-026).
  5. **기록.** 만들 때마다 작업이력(`CSV_EXPORT`, 대상 테이블)에 건수와 쓰인 조건의 이름만 남긴다. 검색어 같은 입력값은 남기지 않는다. 한도로 거절한 요청은 만든 것이 아니라 기록하지 않는다.
- **범위**: 신청·환불·결제·기수·강좌 5종을 구현했다. 나머지 `export.csv`(회원·게시물·통계 등)는 각 목록을 구현할 때 같은 방식으로 붙인다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 24건과 변이 검사 약 45건으로 확인했다.
### ADR-052
**첨부파일은 검증해 검사 대기로 저장하고, 검사를 통과한 것만 소유 업무의 권한으로 내려주며, 모든 접근을 기록한다** — 승인 (TRD 4.5, 스키마 FILE-10·R18, RQ-SER-NF-002, ADR-043·048·049)

- **맥락**: 업로드는 서버를 공격하는 가장 흔한 입구이고, 환불 증빙·계획서는 비공개일 수 있다. 파일의 접근 권한은 소유 업무의 접근 권한이다.
- **결정**
  1. **검증.** 서버가 확장자(pdf·hwp·hwpx·doc·docx·xls·xlsx·jpg·jpeg·png), 크기(0 초과 20MB 이하, 정확히 20MB는 받는다), 내용의 시작 바이트가 확장자의 형식인지를 검사한다. 클라이언트가 보낸 MIME은 믿지 않고 서버가 확장자로 정한다. 틀리면 422이고 저장소와 DB에 아무것도 남기지 않는다. 업로드는 한도보다 한 바이트만 더 읽어 큰 파일을 통째로 메모리에 올리지 않는다.
  2. **파일명.** 경로 구분자·제어·특수 문자를 없애고 NFC로 맞추며 앞의 점을 정리한다(`.pdf`는 `file.pdf`). 줄기는 200자로 줄이고 확장자는 남긴다. 원본 이름은 DB에만 두고 저장소 키에는 담지 않는다.
  3. **저장.** 키는 `b{묶음}/{난수 2자}/{난수 32자}`이고 임시 파일에 쓴 뒤 바꿔 놓으며 같은 키를 덮어쓰지 않는다. 저장소 밖을 가리키는 키는 읽고 쓰지 않는다. DB 기록이 실패하면 저장한 파일을 치운다. 파일은 `FS.PENDING`으로 저장하며 검사를 통과해야 내려갈 수 있다.
  4. **소유 업무.** 이번에 구현한 소유 업무는 강좌(강의계획서, `FP.PLAN`, 한 개)와 환불(증빙, `FP.PROOF`, 다섯 개)이다. 한도는 문서에 없어 둔 값이며 개정 요청 R31에 적는다. 강좌는 고칠 수 있는 담당자(`AU.CORS_W`, 동 범위)만 보고 올리며 폐강·종료 강좌는 잠긴다(409). 환불은 승인·집행 담당자가 보고 승인 담당자(`AU.RFND_A`)만 접수·보류 상태에서 올리고 뺀다. 권한이 전혀 없거나 범위 밖이면 404, 볼 수는 있는데 올릴 권한이 없으면 403이다. 게시물·콘텐츠·강사 지원 증빙 등 나머지 소유 업무는 각 기능을 구현할 때 같은 방식으로 더한다.
  5. **멱등.** 파일 테이블에 멱등키 컬럼이 없어 키와 (소유 업무, 내용 해시, 이름)을 작업이력 메모에 남긴다(개정 요청 R28). 같은 키·같은 파일은 이전 결과, 다른 파일은 409다. 소유 업무 행을 잠근 채 확인해 동시 올리기가 개수 한도를 넘지 못한다.
  6. **검사 워커(`file_scan`, 10초, TDD 7.4).** `FS.PENDING`을 오래된 순으로 50건씩 집어 읽고 검사한 뒤 잠그고 다시 확인해 `FS.SAFE`·`FS.BLOCK`으로 바꾸고 시스템 이력을 남긴다. 저장된 내용의 해시가 올릴 때와 다르면 검사하지 않고 차단한다. 검사기에 닿지 못하거나 파일을 읽지 못하면 통과로 보지 않고 대기로 두어 다음 주기에 다시 한다. 탐지 이름은 로그·이력·화면에 남기지 않는다. 검사기는 포트(`FileScanner`)이고 지금은 모의 어댑터만 있다. 실제 ClamAV(clamd) 어댑터는 배포 환경이 정해진 뒤 더한다.
  7. **관리자 접근.** 전체 목록은 소유 업무를 볼 수 있는 파일만 보이고(삭제한 파일은 상태로 고를 때만) 파일명 검색은 와일드카드를 글자로 다룬다. 상세는 용도·MIME·해시 앞 8자·내려받기 기록을 준다. 삭제는 논리삭제(`FS.DELETE`)이고 저장소 파일은 보존기간 뒤에 치운다. 내려받기는 `FS.SAFE`만 가능하며 `attachment`, `nosniff`, `Cache-Control: private, no-store`로 준다. 권한 없는 시도와 검사 전·차단 파일 요청은 404이고 허용·거절을 모두 작업이력(`FILE_DOWNLOAD`)에 남긴다(거절은 오류 응답에 되돌려지지 않도록 먼저 커밋한다).
- **알아둘 점**: 차단 사유를 담을 컬럼이 없어 화면의 차단 사유는 항상 비어 있다(탐지 이름은 어차피 노출하지 않는다, R31).
- **남은 일**: 게시물·콘텐츠·강사 지원·감면·집계자료 소유 업무의 업로드, 보존기간 뒤 물리 삭제(`retention`), 실제 clamd 어댑터.
- **결과**: 새 테이블·컬럼 없이 구현했다. 검증·저장소 단위 시험 50건, 관리자 파일 API 시험 33건, 검사 워커 시험 11건으로 확인했다.

### ADR-053
**개인식별 명단은 `AU.EXPORT`로 AES-256 ZIP을 즉시 만들어 암호를 응답 헤더로 한 번만 주고, 파일과 암호는 남기지 않는다** — 승인 (RQ-FUN-FN-068, ADR-026·051, DV195~198, 개정 요청 R25·R28)

- **맥락**: 목록과 CSV에는 가려진 값만 나가므로 실제 이름·연락처는 별도 경로가 필요하다. 이 경로가 유출되면 피해가 크므로 권한·범위·상한·감사를 가장 엄격하게 둔다.
- **결정**
  1. **요청.** `POST /exports/pii`(멱등키, CSRF). 대상은 수강신청 목록과 회원 목록이며(ADR-054로 회원 명단을 열었다) 본문은 목록의 조회 조건을 그대로 받는다. 잘못된 상태·날짜 값은 400이다.
  2. **권한·범위.** `AU.EXPORT`가 먼저 필요하고(없으면 목록 권한이 있어도 403), 대상 목록의 조회 권한(수강신청은 `AU.APLY_R`, 회원은 `AU.MBR_R`)도 있어야 한다. 범위는 두 권한의 범위를 모두 만족하는 행만 나간다. 강좌의 운영 동으로 판정한다.
  3. **상한.** 5천 행을 넘으면 만들지 않고 422로 조건을 좁히게 한다. 정확히 5천 행은 만든다.
  4. **파일.** AES-256(WinZip AE-2) 암호화 ZIP 안에 `applicants.csv`(UTF-8 BOM, 수식 주입 방지는 ADR-051 규칙 그대로)를 담는다. 열은 신청번호·강좌·신청자(가리지 않은 이름)·휴대전화·신청 상태·결제 상태·신청일시다. 환불 계좌·증빙은 담지 않는다. 암호는 요청마다 새로 만드는 20자(헷갈리는 글자를 뺀 영숫자)이고 `X-Export-Password` 헤더로 이 응답에서만 준다. 응답은 `no-store`다. 의존성은 `pyzipper`(+`pycryptodomex`)이다.
  5. **멱등.** 같은 담당자가 같은 멱등키로 다시 보내면 내용과 상관없이 409다(암호를 다시 줄 수 없고 새 파일도 만들지 않는다). 멱등키 표식은 작업이력 메모에 남기고(R28) 담당자 행을 잠가 동시 재전송이 한 번만 통과한다. 거절·실패한 요청은 기록하지 않아 같은 키를 다시 쓸 수 있다.
  6. **감사.** 만든 사실(누가·`TB_ATNLC_APLY`·몇 건·조건 이름)만 `PII_EXPORT` 작업이력에 남긴다. 암호·내용·검색어 값은 남기지 않는다.
- **알아둘 점**: 담당자의 세션 갱신이 이미 요청을 한 줄로 세우기 때문에 같은 세션의 동시 재전송 시험은 담당자 행 잠금이 없어도 통과한다. 잠금은 서로 다른 세션을 쓰는 같은 담당자의 겹침을 막는 이중 안전장치다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 16건과 동시성 시험 1건, 변이 검사 10건으로 확인했다.

### ADR-054
**회원 조회는 회원 레코드의 거주 동으로 범위를 정하고, 연락처 원문은 사유를 남겨야 열며, 검토 기록은 작업이력으로 남긴다** — 승인 (RQ-FUN-FN-025·065, ADR-043·053, DV127·128·131, 개정 요청 R12·R13·R33)

- **맥락**: 회원 정보는 가장 민감하고, 담당자는 회원 정보를 고치지 못한다(FN-065). 그러나 거주지 확인 결과와 이용제한·탈퇴·이름 변경 검토 사유는 업무상 남겨야 한다.
- **결정**
  1. **권한·범위.** 모든 API가 `AU.MBR_R`다(없으면 403). 회원의 범위는 신청·결제와 달리 회원 레코드의 거주 동(`TB_MBR.DONG_SN`)이고 동이 없는 회원은 묶음 전체 범위만 본다. 범위 밖·다른 묶음·없는 회원은 같은 404다. 쓰기는 회원 행을 잠가 같은 회원의 요청을 한 줄로 세운다.
  2. **목록·상세.** 이름은 가리고(예 홍\*동) 연락처는 `010-****-5678`, 이메일은 `h***@도메인`으로 준다. 연령·생년·주소는 응답 모델에 없다(PRD Q7). 목록은 최근 가입순이고 검색어(아이디·이름, 와일드카드는 글자로)·상태 조건을 받는다. 상세의 신청·건수·결제완료 합계는 담당자의 회원 범위가 아니라 강좌의 운영 동이 담당자 범위 안인 것만 센다. 신청은 최근 50건만 보이고 전체 건수는 따로 준다. 회원이 입력한 거주 구분은 담을 컬럼이 없어 비운다(R33).
  3. **연락처 열람.** 사유(5자 이상)를 적어야 원문을 주고 열람할 때마다 누가·누구의·왜를 `MBR_REVEAL`로 남긴다. 연락처 값은 남기지 않는다. 연락처가 없는 회원은 빈 값을 주고 그래도 기록한다.
  4. **검토 기록(R12).** 이용제한·탈퇴·이름 변경 사유를 `MBR_REVIEW`로, 처리 완료를 `MBR_REVIEW_CLOSE`로 작업이력에 남기고 회원 상태는 바꾸지 않는다. 검토 번호는 작업이력 번호이고 상태(검토 중·처리 완료)는 닫은 기록의 유무로 정한다. 같은 종류가 검토 중이면 409, 이미 닫은 검토를 다시 닫으면 409, 다른 회원의 검토는 404다. 생성은 멱등키(표식은 R28 방식)를 받아 같은 키·같은 내용은 처음 결과, 다른 내용은 409다. 탈퇴한 회원에는 검토·거주지 기록을 남기지 않는다(409).
  5. **거주지 확인(R13).** `AU.MBR_R`로 기록한다. **확인 완료는 조리읍 거주(`RA.JORI`)로 본다**(사용자 확정 2026-11-12). 확인 완료는 `RV.OK`·확인 일시·수단 `RM.MANUAL`·확인 담당자·근거(요청 식별자)를 채우고, 미확인은 `RV.NONE`·`RA.UNKNOWN`으로 돌리며 확인 정보를 비운다. 회원 행의 다른 값은 바꾸지 않고 기록 버전을 올린다. 파주시 내 조리읍 외(`RA.PAJU_ETC`) 확인은 열지 않았다.
  6. **개인식별 명단.** 같은 목록 조회(`_filtered`)를 재사용해 회원 명단 ZIP(`members.zip`)을 연다. 권한은 `AU.EXPORT`와 `AU.MBR_R`이고 범위는 두 권한이 함께 좁힌다.
- **알아둘 점**: 담당자 이름(`recordedBy`)은 담당자 테이블의 이름 그대로다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 회원 API 시험 26건, 회원 명단 시험 4건, 변이 검사 약 21건으로 확인했다.

### ADR-055
**게시판 설정은 묶음 전체 범위의 담당자만 바꾸고, 게시물은 글의 동 범위로 관리하며, 본문은 허용 태그만 남겨 저장하고, 삭제는 논리삭제로 한다** — 승인 (RQ-FUN-FN-052, DV129·130·131, ADR-043·051, 개정 요청 R11·R28)

- **맥락**: 게시판은 센터 전체가 쓰는 정의이고 게시물은 동 담당자도 올린다. 본문은 공개 화면에 나가므로 저장 전에 정리해야 한다.
- **결정**
  1. **권한·범위.** 설정 조회는 `AU.BBS_W` 또는 `AU.POST_W`, 설정 변경은 `AU.BBS_W`이며 묶음 전체 범위여야 한다(동 범위는 403). 게시물은 모두 `AU.POST_W`다. 글의 범위는 글의 동(`TB_PST.DONG_SN`)이고 동이 없는 공통 글은 묶음 전체 담당자만 본다. 범위 밖·없는 글·지운 글·답변·다른 묶음의 글은 같은 404다.
  2. **설정.** 회원 작성·답변·첨부·사용 여부 네 가지를 바꾼다. 이름과 키는 바꾸지 않는다. 읽은 버전(`RCRD_VER`)이 다르면 409다. **비공개 허용**은 저장할 컬럼이 없어(R11 대기) 게시판 유형이 질문과 답변(`BT.QNA`)일 때만 참으로 보여 주고, 현재 값과 다른 값으로 바꾸려 하면 422로 거절해 조용히 버려지는 일이 없게 한다.
  3. **등록.** 사용 중이고 회원이 쓰지 않는 게시판에만 올릴 수 있다. 같은 게시판의 올리기를 게시판 행 잠금으로 한 줄로 세워 멱등 확인(키·내용 해시, R28)과 저장 사이의 틈을 막는다. 같은 키·같은 내용은 처음 글을 주고 다른 내용은 409다. 묶음 전체 담당자의 글은 공통 글(동 없음)이고 동 담당자의 글은 자기 동의 글이다. 담당 동이 여럿이면 동을 정할 수 없어 422다.
  4. **본문 정리(`app/domain/board/sanitize.py`).** 문단·줄바꿈·굵게·기울임·밑줄·목록·소제목·인용·링크만 남기고 속성은 링크 주소뿐이다. 주소는 `http`·`https`·`mailto`만 받고 `rel="noopener noreferrer"`를 붙인다. 스크립트·스타일·프레임·객체·SVG는 안의 내용까지 버리고, 허용하지 않는 태그는 글자만 남기며, 닫히지 않은 태그는 닫고 짝 없는 닫는 태그는 버린다. 글자는 모두 이스케이프한다. 정리한 뒤 읽을 글자가 없으면 422다. 제목은 앞뒤 공백을 지운다.
  5. **수정.** 읽은 버전이 다르면 409다. 회원이 쓴 글은 내용을 고치지 못하고(422) 게시판도 바꾸지 못한다.
  6. **삭제.** 삭제여부만 바꾸는 논리 삭제이고 회원이 쓴 글도 지울 수 있다. 행을 잠가 동시 삭제가 한 번만 반영되게 하고 이미 지운 글은 404다. 지우면 공개 목록에서도 사라진다. 수정·삭제·설정 변경은 작업이력에 남기되 본문·제목은 남기지 않는다.
  7. **목록·CSV.** 상단공지가 먼저이고 최근 등록순이다. 제목 검색은 와일드카드를 글자로 다룬다. 회원이 쓴 글의 작성자는 가린다. CSV는 같은 조회를 쓰고 본문·첨부를 담지 않는다(ADR-051 규칙).
- **알아둘 점**: 게시판의 회원 작성을 공개 게시판(공지 등)에서 켤 수 있다. 막지 않았으므로 켜면 회원 글이 공개 목록에 나갈 수 있다. 기관 확인 대상이다.
- **남은 일**: 게시물 첨부 올리기(다음 단계).
- **결과**: 새 테이블·컬럼 없이 구현했다. 본문 정리 시험 33건, 게시판·게시물 API 시험 27건(동시 삭제 1건 포함), 변이 검사 약 35건으로 확인했다.

### ADR-056
**게시물 첨부는 게시판의 첨부 정책과 글의 동 범위를 따르고, 갤러리는 이미지만 받는다** — 승인 (RQ-SER-NF-002, FILE-10, ADR-052·055, 개정 요청 R31)

- **맥락**: ADR-052의 파일 기능에 소유 업무 하나를 더한다. 게시물 첨부는 공개 화면에도 나가므로 첨부 정책과 글의 상태가 접근과 변경을 정해야 한다.
- **결정**
  1. **권한·범위.** 올리기·목록·삭제·내려받기는 게시물 권한(`AU.POST_W`)과 글의 동 범위를 따른다. 권한이 없거나 범위 밖·지운 글·답변·없는 글은 같은 404다. 지운 글의 파일은 전체 목록·상세·내려받기에서 사라진다.
  2. **용도·한도.** 일반 게시판은 첨부(`FP.ATTACH`) 5개, 갤러리 게시판은 이미지(`FP.IMAGE`) 10장이다. 갤러리에는 jpg·jpeg·png만 올릴 수 있다(422). 한도는 문서에 없어 둔 값이다(R31).
  3. **잠김.** 게시판이 첨부를 쓰지 않거나(`ATCH_USE_YN`=N) 회원이 쓴 글(내용을 고칠 수 없다, ADR-055)이면 목록은 보이지만 올리기·삭제는 409다. 첨부를 끄면 이미 올린 파일도 지울 수 없다(켜야 지운다).
  4. **동시성.** 올리기는 글 행을 잠근 채 멱등 표식 확인·개수 검사·저장을 한다. 서로 다른 세션의 동시 올리기가 한도를 넘지 못한다.
  5. **나머지.** 검증·저장·검사 워커·멱등·감사는 ADR-052와 같다. 공개 화면은 검사를 통과한 파일만 보인다(TRD 4.4).
- **남은 일**: 강사 지원서·콘텐츠·감면·집계자료 소유 업무의 업로드.
- **결과**: 새 테이블·컬럼 없이 구현했다. 게시물 첨부 시험 11건(동시 올리기 1건 포함)과 변이 검사 15건으로 확인했다.

### ADR-057
**문의 분류는 공통코드 문자열을 식별자로 쓰고, 답변은 원글 아래 한 단계 답변 글이며, 수정할 때마다 이력을 남긴다** — 승인 (RQ-FUN-FN-053, DV132, ADR-055, 개정 요청 R15·R34)

- **맥락**: 문의 분류(IQ)는 공통코드(`TB_COM_CD.COM_CD`, 12자 문자열)라 일련번호가 없는데 계약은 분류 번호를 숫자 일련번호로 정해 두었다. 분류 초기값은 기관 확인 뒤 입력한다(PRD Q26).
- **결정**
  1. **계약 변경(사용자 확정 2026-11-12).** 분류 식별자 `categoryId`를 코드 문자열(`^IQ\.[A-Z0-9_]{1,9}$`, 예 `IQ.COURSE`)로 바꿨다. 영향은 관리자 분류 목록·조건·주민 문의 분류·문의 상세·문의 작성 요청이다. 화면은 값을 그대로 다루므로 모의 서버의 분류 값만 코드로 바꿨고 api-client 타입은 다시 만들었다.
  2. **권한·범위.** 모두 `AU.POST_W`이고 범위는 문의(질문과 답변 게시판의 원글)의 동이다. 범위 밖·없는 글·답변·지운 글은 같은 404다. 주민 쪽 문의 작성이 구현될 때 글의 동을 정해야 동 담당자가 볼 수 있다(지금은 동이 없는 글은 묶음 전체 담당자만 본다).
  3. **목록.** 상태는 답변 글(`PT.REPLY`, 지우지 않은 것)의 유무로 정한다. 답변 대기가 먼저이고 각각 오래된 순이며, 상태·분류 코드·제목(와일드카드는 글자로) 조건과 쪽 나누기를 받는다. 작성 회원 이름은 가린다. CSV는 같은 조회를 쓰고 본문·답변·첨부를 담지 않는다.
  4. **답변.** 원글당 한 단계이고 삭제·다단계는 없다. 원글을 잠그고 읽은 답변 버전(없으면 0)이 다르면 409다. 작성하면 원글과 같은 게시판·동·분류·공개범위의 답변 글을 만들고, 고치면 같은 글을 갱신해 버전을 올리고 마지막 담당자를 답변자로 한다. 내용은 앞뒤 공백을 지운 일반 글자로 저장한다(비면 422). 작성·수정마다 `INQ_ANSWER`·`INQ_ANSWER_EDIT`를 작업이력에 남기고 이 이력이 화면의 수정 이력(작성·수정, 담당자, 시각)이다. 내용은 이력에 남기지 않는다.
  5. **관련 화면 링크.** 사이트 안 경로(`/`로 시작, `//` 제외)나 `https` 주소만 받는다(422). 답변 글에 링크 컬럼이 없어 본문 끝에 `\n\n관련 화면: 주소` 표식으로 담고 읽을 때 떼어 낸다(R34).
- **알아둘 점**: 주민 쪽 문의 조회·작성은 아직 구현 전이다. 구현할 때 같은 답변 글을 읽어 주민에게 보이면 된다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 24건(동시 답변 1건 포함)과 변이 검사 약 25건으로 확인했다.

### ADR-058
**주민 문의는 본인 글만 고치고 지우며, 다른 회원의 비공개 문의는 가려서 보이고, 원글 잠금으로 답변과 수정이 겹치지 않게 한다** — 승인 (RQ-FUN-FN-053, DV86·87·89, ADR-055·057, 개정 요청 R34)

- **맥락**: 관리자 답변(ADR-057)이 주민에게 보이려면 주민 쪽 문의 조회·작성이 필요하다. 문의 글의 동을 정하지 않으면 동 담당자가 문의를 볼 수 없다는 ADR-057의 숙제도 여기서 푼다.
- **결정**
  1. **API 7개.** `GET /inquiry-categories`, `GET /inquiries`, `GET /inquiries/{id}`, `GET·POST /me/inquiries`, `PUT·DELETE /me/inquiries/{id}`. 모두 로그인한 회원이며 쓰기는 CSRF 토큰도 필요하다. 회원 번호는 세션에서만 온다.
  2. **목록·상세.** 목록은 질문과 답변 게시판의 지우지 않은 원글을 최근 등록순으로 모두 준다. 다른 회원의 비공개 문의는 제목을 `비공개 문의입니다.`로, 작성자를 앞 글자만(`박**`) 남겨 준다. 공개 문의의 작성자는 가린 이름(`박*라`)이다. 다른 회원의 비공개 문의 상세는 404다(답변도 같다). 상태는 지우지 않은 답변 글의 유무로 정한다. 답변은 관련 화면 링크 표식이 붙은 글 그대로 보인다(R34). 분류는 공통코드(IQ)에서 쓰는 것만 준다.
  3. **작성.** 멱등키를 받고 같은 키·같은 내용은 처음 문의를, 다른 내용은 409를 준다. 같은 회원의 올리기를 회원 행 잠금으로 한 줄로 세운다. 분류는 쓰는 IQ 코드여야 하고(없으면 422) 제목·내용은 앞뒤 공백을 지운 일반 글자이며 비면 422다. 게시판이 없거나 사용을 멈췄거나 회원 작성이 꺼져 있으면 422다. **글의 동은 작성 회원의 동이다**(사용자 확정 없이 ADR-057의 숙제를 푸는 안이며, 동이 없는 회원의 글은 묶음 전체 담당자만 본다). 등록은 작업이력(`INQ_CREATE`)에 남기되 내용은 남기지 않는다.
  4. **수정.** 본인 글만이고 남의 글은 공개 글이어도 404다. 답변이 달린 문의는 422다. 원글을 잠근 뒤 답변 여부를 다시 읽으므로 관리자 답변(같은 원글 잠금)과 겹쳐도 답변이 달린 글이 고쳐지지 않는다. 수정은 버전을 올리고 `INQ_UPDATE`를 남긴다.
  5. **삭제.** 본인 글만이고 논리 삭제다. 답변이 달려도 지울 수 있다. 원글을 잠가 동시 삭제가 한 번만 반영되게 하고 이미 지운 글은 404다. `INQ_DELETE`를 남긴다. 지운 문의는 관리자 목록에서도 사라진다.
- **알아둘 점**: 분류가 비어 있는 옛 문의(PST-02 위반 데이터)는 상세를 만들 수 없다. 서비스가 만든 문의는 항상 분류가 있다. 문의 첨부(`/me/inquiries/{id}/files`)는 아직 구현 전이다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 22건과 동시성 시험 3건, 변이 검사 약 28건으로 확인했다.

### ADR-059
**주민 문의 첨부는 본인 문의에만 답변 전까지 올리고 지우며, 본인 파일만 내려받고, 관리자 파일 기능의 저장 절차를 그대로 쓴다** — 승인 (RQ-SER-NF-002, FILE-10, DV179, ADR-052·056·058, 개정 요청 R31)

- **맥락**: 관리자 쪽 파일 기능(ADR-052)에 주민이 올리는 경로를 더한다. 주민 첨부는 관리자도 봐야 하는 자료(문의 증빙)이므로 소유 업무는 같은 게시물(`PST_SN`)이고 접근 판정만 다르다.
- **결정**
  1. **API 4개.** `GET·POST /me/inquiries/{id}/files`, `DELETE·GET /me/files/{id}`. 쓰기는 CSRF 토큰과 올리기는 멱등키가 필요하다. 회원 번호는 세션에서만 온다.
  2. **소유 판정.** 본인의 지우지 않은 질문과 답변 게시판 원글만이다. 남의 문의·지운 문의·답변·다른 게시판의 글·강좌 같은 다른 소유자의 파일은 모두 404다.
  3. **잠김.** 답변이 달렸거나(지운 답변은 답변이 아니다) 게시판이 첨부를 쓰지 않으면 목록은 보이되 올리기·삭제는 409이고 `canEdit`은 false다. 답변이 달린 문의에는 파일을 검증하기도 전에 409다.
  4. **한도·검증·저장.** 파일 5개, 검증·MIME·이름 정리·저장 키·검사 대기·멱등 표식(R28)·개수 검사는 ADR-052와 같다. 공통 절차를 `store_upload`와 `lock_owner`로 뽑아 관리자와 주민이 함께 쓴다(관리자 시험 108건으로 동작이 그대로임을 확인했다).
  5. **동시성.** 올리기·삭제는 원글 행을 잠근 뒤 소유 상태를 다시 읽는다. 관리자 답변이 같은 잠금을 쓰므로 읽은 뒤 잠그기 전에 답변이 확정돼도 파일이 더해지거나 지워지지 않는다.
  6. **내려받기.** 본인 파일 중 `FS.SAFE`만 준다. `attachment`, `nosniff`, `Cache-Control: private, no-store`는 관리자와 같다. 남의 파일·검사 전·차단 파일을 열려 한 시도는 `JR.DENY`로 먼저 확정해 남기고 404다. 허용된 내려받기도 `FILE_DOWNLOAD`로 남기며 행위자는 주민(`AK.MEMBER`)이다.
  7. **삭제.** 논리삭제(`FS.DELETE`)이고 수정 일시를 남긴다. 물리 삭제는 보존기간 뒤다.
- **남은 일**: 강사 지원서·감면 사전심사 증빙의 주민 파일 API는 주민 쪽 해당 기능이 구현될 때 같은 방식으로 더한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 22건과 동시성 시험 2건, 변이 검사 약 25건으로 확인했다.

### ADR-060
**홈·센터 콘텐츠는 스키마에 코드가 있는 유형만 제자리에서 고치고, 약관은 검토·확정·게시 버전으로 개정하며, 확정한 문안은 해시로 고정한다** — 승인 (RQ-FUN-FN-011·055, DV133~136, 스키마 R17, 개정 요청 R9·R14·R16·Q23)

- **맥락**: 두 기능 모두 `TB_SITE_CONTS` 한 테이블을 쓰고 주민 공개 화면이 이 행을 바로 읽는다. 약관은 이미 동의한 문안을 사후에 바꾸면 안 된다.
- **결정**
  1. **권한·범위.** 모두 `AU.SITE_W`다. 콘텐츠는 콘텐츠의 동으로 범위를 정하고(동 담당자가 올리면 자기 동, 담당 동이 여럿이면 422), 약관·동의문은 동 미지정 묶음 공통(R17)이라 묶음 전체 범위의 담당자만 다룬다(동 범위는 403).
  2. **콘텐츠 유형.** 저장할 수 있는 유형은 스키마에 코드가 있는 배너·팝업·연혁·센터소개(`CT.BANNER·POPUP·HISTORY·INTRO`)뿐이다. 비주얼·연락처·수강·환불 안내·시설안내는 코드가 없어 422로 거절하고 이유를 알린다(R9·R14·Q23 대기). 연락처 구조 입력도 저장하지 않는다. 약관 계열과 운영기준 콘텐츠는 콘텐츠 목록에 나오지 않는다.
  3. **콘텐츠 저장.** 제자리에서 고친다(버전 이름 `v1` 고정, 읽은 버전 `RCRD_VER`이 다르면 409, 유형은 못 바꾼다). 본문은 허용 서식만 남겨 정리한다(ADR-055). 링크는 사이트 안 경로(`/`로 시작, `//` 제외)나 `https`만 받고, 게시 종료는 시작보다 뒤여야 한다. 멱등 등록(R28)은 같은 유형을 잠근 채 확인한다.
  4. **연혁.** 공개 화면(`/contents/center-history`)이 본문을 `{subtitle, sections}` JSON으로 읽으므로 연혁 본문은 그 모양이어야 하고(아니면 422) 정리 없이 그대로 저장한다. 식별자는 `center-history` 고정이라 하나만 둘 수 있다. 게시를 끄면 공개 화면에서 사라진다.
  5. **약관 상태(컬럼 없이 도출).** 해시가 없으면 검토, 해시가 있고 게시 여부가 N이면 확정, 게시 중이면 게시, 게시 종료 시각이 지금 이전이면 종료다. 시행일은 게시 시작 일시(한국 날짜의 0시)에 둔다. 게시일은 `TERM_PUBLISH` 작업이력에서 읽고, 동의 수는 동의 이력(`AA.AGREE`)의 서로 다른 회원 수다.
  6. **약관 흐름.** 새 버전은 검토로 만든다(종류당 버전 이름 유일, 이전 버전 복제는 같은 종류만, 본문·원본 둘 다 없으면 422). 수정은 검토만(아니면 409), 확정은 검토만이며 정리한 본문의 SHA-256을 고정한다. 게시는 확정만이고 같은 종류의 열린 게시 버전을 새 버전의 시행 시각에 종료한다. 시행일이 지금 게시 중인 버전의 시행일보다 앞서거나 같으면 422다. 시행일이 미래이면 그날까지 이전 버전이 보인다. 같은 종류 행을 잠근 채 상태·버전을 다시 확인한다. 이미 종료된 버전은 다시 건드리지 않는다. 확정·게시된 문안은 덮어쓰지 않고 삭제 API는 없다.
  7. **저장 코드가 없는 약관 종류**(개인정보처리방침·이메일 무단수집 거부, R16)는 새 버전을 422로 거절하고 목록은 비어 있다.
  8. **감사.** 등록·수정·확정·게시를 `CONTENT_*`·`TERM_*` 작업이력에 남기되 본문은 남기지 않는다.
- **알아둘 점**: 사용자 앞 화면이 쓰는 유형 8개 중 4개는 저장되지 않으므로 관리자 화면에서 그 유형으로 올리면 거절 안내가 나온다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 41건(콘텐츠 16건, 약관 25건)과 변이 검사 약 60건으로 확인했다.

### ADR-061
**강좌 운영(센터·강의실, 분류, 일정·휴보강)은 시설별 잠금으로 일정 중복을 막고, 휴강·보강은 원수업일을 두며, 분류는 정규화키와 행 잠금으로 연결 강좌를 지킨다** — 승인 (RQ-FUN-FN-049·050, DV101~109, 스키마 SCH-01~03·CLSF-01~03, 개정 요청 R35)

- **맥락**: 일정·시설·분류는 강좌 공개와 신청 판정이 그대로 읽는 기준 정보다. 일정이 겹치거나 연결 강좌가 있는 분류를 끄면 운영이 깨진다.
- **결정**
  1. **센터·강의실(`AU.FCLT_W`).** 강의실은 센터 아래에만 두고(센터는 상위 없음) 종류와 상위는 바꿀 수 없다. 같은 위치(같은 상위)의 같은 이름은 사용 중지한 시설까지 포함해 거절한다. 범위는 시설의 동이며 강의실은 센터의 동을 따른다. **층은 설명(`FCLT_EXPLN`)에 `층: ` 표식으로 담고 공개 여부는 저장할 컬럼이 없어 항상 공개로 보며, 비공개로 바꾸려 하면 422로 거절한다**(사용자 확정 2026-11-13, 개정 요청 R35). 사용 중지해도 기존 일정은 유지하고 새 일정에는 배정하지 못한다.
  2. **분류(조회 `AU.CORS_R`, 변경 `AU.CORS_W`·묶음 전체 범위).** 이름은 표시용(공백 정리)과 정규화키(NFKC·공백 정리·소문자)로 나눠 서버가 만들고, 삭제한 분류까지 포함해 키가 같으면 거절한다(삭제한 이름은 다시 쓸 수 없다). 100자를 넘으면 절단하지 않고 거절한다. 연결 강좌(폐강한 강좌 포함)가 있으면 비활성·삭제를 거절하고 수를 확인하지 못해 0으로 속이는 일이 없다. 분류 행을 잠근 채 같은 트랜잭션에서 세며, 강좌 등록·수정이 분류를 확인할 때 같은 행을 공유 잠금으로 잡아 둘이 겹치지 못한다(CLSF-02). 변경 전후 값은 작업이력(JSON)에 항목별로 남긴다(등록·명칭·순서·비활성·재활성·삭제, CLSF-03). 분류가 하나도 없을 때도 동시 등록을 막으려고 묶음 행을 잠근다.
  3. **일정(`AU.CORS_W`, 범위는 강좌의 동).** 폐강·종료한 강좌는 409다. 사용 중인 강의실만 고를 수 있고 시설 행을 잠가 같은 시설의 저장을 한 줄로 세운다(SCH-03). 같은 시설·요일에 **시간과 기간이 겹치는 다른 강좌**의 일정(또는 보강)이 있으면 "{시설} {요일} {기존 시간}에 {강좌}이(가) 있습니다."를 시설 항목에 돌려준다. 종료와 다음 시작이 같은 것은 겹침이 아니고 같은 강좌의 일정끼리는 거절하지 않는다. 똑같은 일정(시설·요일·시작·적용 시작일)은 저장소 유일 규칙 전에 422로 알린다. 적용 기간은 강좌 교육기간 안이어야 한다. 휴강·보강이 걸린 일정은 요일·적용 기간을 바꾸거나 지울 수 없고(지우기는 409), 출석 기록이 있어도 지울 수 없다. 공개한 강좌의 마지막 일정은 지울 수 없다(422).
  4. **휴강·보강(계약 변경, 사용자 확정 2026-11-13).** 계약에 `originalDate`(원수업일)를 더했다. 휴강은 `classDate`가 원수업일이고 시설·시간을 받지 않는다. 보강은 `classDate`가 보강일이고 `originalDate`·시설·시간이 모두 필수다. 원수업일은 그 강좌의 정규 일정(요일·적용 기간)에 맞아야 하고(SCH-01), 같은 정규 일정·원수업일에는 변경 한 건만 둘 수 있다(SCH-02). 보강 날짜의 점유는 정규 수업과 다른 보강을 모두 보되 휴강·대체된 원수업은 뺀다(SCH-03). 휴보강은 수정하지 않고 삭제 뒤 다시 등록하며, 삭제는 행을 지우되 지우기 전의 값을 작업이력에 보존한다(SCH-02). 출석 기록이 걸린 보강은 지울 수 없다. 응답에는 `originalDate`를 항상 담는다. 관리자 화면에 원수업일 입력을 더했다.
  5. **멱등.** 시설·분류·일정·휴보강 등록은 멱등키(표식, R28)를 받고 일정·휴보강은 강좌 번호까지 표식에 담는다.
- **알아둘 점**: 일정이 바뀌어도 이미 접수된 신청에는 영향을 주지 않는다. 일정 변경이 신청자에게 알림으로 이어지는 것은 문자 발송 기능에서 다룬다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 시설 13건, 분류 24건, 일정·휴보강 32건과 동시성 시험 4건, 변이 검사 약 100건으로 확인했다.

### ADR-062
**출석 현황은 조회 전용으로 가린 명단만 보이고, 강사 심사는 지원서 행 잠금 아래 상태 전이표로 승인·반려·활동중지를 다루며 승인은 회원과 연결된 지원서만 강사로 만든다** — 승인 (RQ-FUN-FN-051, 스키마 TB_CORS_ATND·TB_INSTR_APLY·TB_INSTR, 개정 요청 R36)

- **맥락**: 출석은 일정·휴보강 위에 놓이는 기록이고, 강사 심사 결과는 강좌 등록의 대표강사 조건(승인 강사)과 이어진다.
- **결정**
  1. **출석 현황(`AU.ATND_R`, 범위는 강좌의 동).** 수정·삭제·CSV는 만들지 않는다. 지운 출석부(`DEL_YN='Y'`)는 목록·상세에서 뺀다. 수업일 최신순이고 기수·강좌·수업일·입력상태(완료 여부)로 거른다. 상세 명단은 가린 이름·신청번호·회원 상태 표시·출석 상태만 담고 연락처·생년·결제는 담지 않으며, 체크하지 않은 사람을 결석으로 바꾸지 않는다.
  2. **강사 심사(`AU.INSTR_W`, 묶음 전체 범위).** 동 범위 담당자는 조회도 403이다. 상태는 지원서(`SRNG_STTS_CD`)와 강사(`INSTR_STTS_CD`)에서 도출한다(심사대기·승인·활동중지·반려). 전이표는 대기→승인·반려, 승인↔활동중지이며 **반려는 끝**(409, 새 지원서를 받는다)이고 대기로 되돌리거나 대기에서 바로 활동중지하는 것도 409다. 지원서 행을 `FOR UPDATE`로 잠그고 다시 읽은 뒤 읽은 버전을 확인해(409) 두 담당자가 겹쳐도 한 번만 반영한다. 반려·활동중지는 사유가 필수(422)이고 공개는 승인 상태에서만 켤 수 있다(422).
  3. **승인(사용자 확정 2026-11-13).** 회원과 연결된 지원서만 승인한다(연결이 없으면 422로 회원 가입 후 연결을 안내하며 반려는 가능). 승인하면 그 회원의 강사 행을 만들고(이미 있으면 다시 승인해 재사용) 승인자·승인일을 남기고 지원서에 잇는다. 강좌 배정과 관리자 권한은 자동으로 주지 않는다(FN-051). 활동중지는 공개를 끄고 사유를 남기며 다시 승인하면 승인자·일시를 새로 남긴다.
  4. **접수 등록(사용자 확정 2026-11-13).** 방문·외부 접수만 등록한다(온라인은 422). 계약에 모집 공고 번호(`recruitmentId`, 스키마상 필수)·휴대전화(`phone`, 숫자만)·선택 회원 아이디(`memberLoginId`)를 더했다. 전화번호는 암호화해 저장하고 응답·목록·작업이력 어디에도 담지 않는다. 멱등키(`admin-` 접두)로 같은 요청은 같은 접수를, 내용이 다르면 409를 돌려준다. 관리자 화면에 입력란을 더했다.
  5. **검토 메모.** 컬럼이 없어 작업이력에 담는다(R36).
- **알아둘 점**: 비회원 지원서의 회원 연결을 나중에 하는 수단은 아직 없다(회원 연결 기능이 정해지면 다룬다).
- **결과**: 새 테이블·컬럼 없이 구현했다. 출석 10건, 강사 심사 22건과 동시성 시험 1건, 변이 검사로 확인했다.

### ADR-063
**감면 사전심사는 회원·기수 단위의 접수 건을 한 번만 승인·반려하고, 재심사는 이전 심사를 그대로 둔 새 접수건이며, 범위는 회원의 거주 동으로 판정한다** — 승인 (RQ-FUN-FN-038, 스키마 TB_RDCT_BFHD_SRNG·TB_RDCT_HSTRY, 개정 요청 R19)

- **맥락**: 감면은 결제 금액에 바로 영향을 주고(수강료 50%), 신청 쪽 산정(`find_usable_approval`)이 이 심사의 승인·유효기간을 읽는다. 승인은 되돌리거나 덮어쓰면 안 된다.
- **결정**
  1. **권한(R19).** 목록·상세·판정 이력은 `AU.APLY_R`, 증빙 열람·승인·반려·재심사는 `AU.APLY_W`다. 조회 권한만 있으면 상세의 증빙 목록·열람 기록을 비워 주고 `canDecide`·`canReReview`·`canViewEvidence`는 false다.
  2. **범위(사용자 확정 2026-11-13).** 심사는 강좌가 아니라 회원·기수 단위라 강좌의 동이 없다. **대상 회원 행의 거주 동(`TB_MBR.DONG_SN`)으로 범위를 판정한다**(회원 조회와 같은 방식). 동이 없는 회원은 묶음 전체 담당자만 본다. 범위 밖은 404다. 판정 이력은 신청한 강좌의 동으로 판정한다(신청 쪽 규칙과 같다).
  3. **결정(승인·반려).** 접수 상태만 결정할 수 있고(아니면 409), 읽은 버전이 다르면 409다. 승인은 유효 종료일이 필수이고 오늘 이후여야 하며(오늘 포함) 반려 사유를 받지 않는다. **조리읍 거주가 확인되지 않은 회원(`RA.JORI`·`RV.OK`가 아닌 회원)은 승인할 수 없다**(422, 반려는 가능). 반려는 사유가 필수이고 유효 종료일을 받지 않는다. 결정한 뒤에는 내용·증빙을 고치지 않는다.
  4. **유효 종료일.** 입력은 날짜이고 DB에는 그날 한국 시각 23:59:59(UTC로 변환)를 넣는다. 신청 쪽 산정이 `유효 종료 > 지금`으로 읽으므로 그날 끝까지 쓸 수 있고 다음 날부터 못 쓴다. 읽을 때는 한국 날짜로 되돌린다.
  5. **재심사.** 승인·반려된 심사만 대상이며 이전 심사는 그대로 두고 같은 회원·기수·유형의 새 접수건(버전 1, 증빙 없음)을 만든다. 같은 회원·기수에 접수 중인 건이 있으면 409다. 멱등키는 표식(R28)에 원 심사 번호를 묶어 작업이력에 남기며, 같은 키로 다시 보내면 같은 건을, 다른 심사에 쓰면 409를 돌려준다. 이전 승인은 재심사해도 유효기간 안에서 계속 쓸 수 있다(새 심사가 승인되기 전에는 바뀌지 않는다).
  6. **잠금.** 회원 행을 먼저, 심사 행을 다음에 잠그고 다시 읽는다. 재심사와 결정이 같은 순서라 교착이 없고, 같은 회원의 두 재심사가 겹쳐도 접수건은 하나만 생긴다.
  7. **증빙 열람 기록.** 증빙을 내려받을 때 쓸 `record_evidence_view`를 작업이력(`RDCT_EVIDENCE_VIEW`, 대상은 심사 번호, 변경 내용은 파일 번호만)에 남기도록 두었고 상세가 이를 읽는다. 파일 번호만 남겨 파일 이름이 기록에 퍼지지 않는다.
  8. **판정 이력.** 신청에 적용된 감면 판정(`TB_RDCT_HSTRY`)을 읽기만 한다. 최근 순, 결과·기간(한국 날짜)으로 거르고 이름은 가린다.
- **알아둘 점**: 증빙 파일을 올리고 내려받는 API(관리자 `reduction` 소유자, 주민 쪽 신청·증빙)는 주민 쪽 사전심사 기능과 함께 더한다. 이번에는 그 기록 함수만 먼저 둔다. 증빙이 한 건도 없는 심사의 승인을 막는 규칙은 문서에 없어 만들지 않았다(기관 확인 필요).
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 20건과 동시성 시험 2건, 변이 검사로 확인했다.

### ADR-064
**주민 쪽 감면 사전심사는 거주 확인 회원이 기수별로 신청·철회하고 결과만 보며, 증빙은 접수 상태일 때만 올리고 지우고, 관리자의 증빙 내려받기는 열람 기록을 남긴다** — 승인 (RQ-FUN-FN-038, 스키마 TB_RDCT_BFHD_SRNG·TB_FILE, 개정 요청 R23·R31)

- **맥락**: 관리자 심사(ADR-063)가 읽을 접수 건과 증빙은 주민 쪽에서 만들어진다. 주민에게는 심사 내용·처리자·거주 확인 결과를 주지 않는다(R23).
- **결정**
  1. **신청 가능 여부(`/me/reduction-options`).** 조리읍 거주가 확인된(`RA.JORI`·`RV.OK`) 회원만 신청할 수 있고, 아니면 이유와 함께 빈 기수 목록을 준다. **고를 수 있는 기수는 사용 중(`USE_YN=Y`)이고 교육 종료일이 오늘(한국) 이후인 기수**다(문서에 기준이 없어 둔 값이다).
  2. **신청.** 회원 행을 잠근 뒤(관리자 결정·재심사와 같은 순서) 거주·기수·중복을 검사하고 접수 건(버전 1)을 만든다. 금액·비율은 받지 않는다. **같은 기수에 접수 중이거나 아직 유효한(기간이 끝나지 않은) 승인이 있으면 422**이며 반려·철회·기간이 끝난 승인은 막지 않는다(끝난 승인이 새 신청을 영영 막지 않게 한다). 멱등키는 표식(R28)에 회원·키·(기수·유형)을 묶어 남기고 같은 키는 같은 건을, 내용이 다르면 409를 돌려준다.
  3. **조회.** 내 심사만(남의 것은 404) 최근 신청 순으로 준다. 승인이면 유효 종료일, 반려이면 사유만 보이고 심사 메모·처리자는 담지 않는다.
  4. **철회.** 접수 상태만 가능하고(아니면 409) 상태를 `DS.REVOKED`로 바꾼다. 철회해도 증빙은 보존기간 규칙대로 남기며 지우지 않는다. 철회 뒤에는 같은 기수에 새로 신청할 수 있다.
  5. **증빙(주민).** 본인의 접수 상태 심사에만 올리고 지운다. 결정(승인·반려)·철회된 뒤에는 잠긴다(올리기·지우기 409). 목적은 `FP.PROOF`, 한도는 5개다(문서에 없어 문의·환불과 같게 둔 값, R31). 올릴 때 심사 행을 잠근 뒤 상태를 다시 읽어 철회·관리자 결정과 겹쳐도 잠긴 심사에는 파일이 남지 않는다. 검증·멱등·검사 대기 저장은 관리자 올리기와 같은 코드를 쓴다. 내려받기·삭제 라우터(`/me/files/{id}`)는 문의 첨부와 감면 증빙을 함께 다루고 남의 파일은 404와 거절 기록이다.
  6. **증빙(관리자).** 관리자가 `/files/{id}/download`로 내려받는 것은 심사 권한(`AU.APLY_W`)이 회원의 거주 동을 덮을 때만이고, 아니면 같은 404다. 올리기·지우기는 관리자에게 없다. **내려받기가 성공하면 `RDCT_EVIDENCE_VIEW`를 남기고**(대상은 심사 번호, 내용은 파일 번호만) 관리자 심사 상세의 열람 기록이 이를 읽는다(ADR-063 7항을 닫는다).
- **알아둘 점**: 강사 지원서 증빙의 주민 파일 API와 수강후기는 아직 없다. 증빙이 한 건도 없는 심사의 승인을 막는 규칙은 문서에 없어 만들지 않았다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 21건과 동시성 시험 3건, 변이 검사로 확인했다.

### ADR-065
**강사 모집공고는 게시된 공고글과 모집 기간으로 상태를 서버가 정하고, 회원의 강사 지원은 공고당 한 번·서류 검토중일 때만 고치며 증빙은 같은 주민 파일 경로로 다룬다** — 승인 (RQ-FUN-FN-019·027, 스키마 TB_INSTR_RCRT·TB_INSTR_APLY·TB_FILE, 개정 요청 R37)

- **맥락**: 관리자 강사 심사(ADR-062)가 읽는 온라인 접수 건은 주민 쪽 지원에서 만들어진다. 계약과 스키마에 어긋나는 곳이 있어 사용자와 정했다.
- **결정**
  1. **계약 변경(사용자 확정 2026-11-16).** 희망 분야는 번호를 저장할 곳이 없어(`HOPE_FLD_NM` 문자열뿐) 요청·응답을 `categoryName`(사용 중인 강좌 분류의 이름)으로 바꿨다. 이름은 분류 목록에 있는 것만 받고 분류의 표시 이름으로 저장한다. 이전의 `categoryId`는 없앴다. 모집공고 상세의 `field`는 저장 위치가 없어 null을 허용하고 항상 null이다. 화면·모의 서버·시험을 함께 바꿨다.
  2. **모집공고(공개).** 공고는 게시된(삭제·비공개·게시 기간 밖이 아니고 게시판이 쓰이는) 공고글에 이어진 모집 정보이며 모집 시작·종료가 모두 있는 것만 공개한다. 상태는 서버가 정한다(시작 전 예정, 시작~종료 모집중, 종료 후 마감). 목록은 게시일 최근 순이고 제목은 글 제목, 안내(`guide`)는 글 본문에서 태그를 걷어 낸 글자다. 공고 상세의 `canApply`는 모집중이고 로그인한 회원이 아직 지원하지 않았을 때 true다(로그인하지 않았으면 모집중인 것만 보고 true를 주며, 중복 지원은 지원할 때 서버가 다시 판정한다).
  3. **지원(회원).** 이름과 휴대전화는 회원정보를 쓴다(휴대전화는 암호화해 저장하고 응답·작업이력에 담지 않으며 회원정보에 휴대전화가 없으면 422). 모집중이고 보이는 공고만, 같은 공고에는 결과와 상관없이 한 번만 지원할 수 있다(422). 회원 행을 잠근 뒤 같은 키의 이전 지원을 먼저 찾아(멱등키 컬럼, 회원 번호를 키에 묶는다) 같은 내용이면 같은 건을, 다르면 409를 돌려주고, 없을 때만 공고·분류·중복을 검사해 접수한다.
  4. **수정.** 서류 검토중(`IA.WAIT`)인 내 지원서만 고친다(아니면 422). 지원한 공고는 바꿀 수 없다. 회원 행 → 지원서 행 순서로 잠그고 잠근 뒤 상태를 다시 읽어, 관리자 승인과 겹쳐도 승인 뒤에는 바뀌지 않는다.
  5. **상태 대응(R37).** 지원 상태는 대기→검토중, 승인→선정, 반려→미선정이다. 계약의 보완요청·심사중은 대응하는 코드가 없어 나오지 않는다.
  6. **증빙.** 주민은 서류 검토중인 내 지원서에만 올리고 지우며 심사가 끝나면 잠긴다(409). 한도는 5개다(R31과 같게 둔 값). 주민 파일 라우터(`/me/files/{id}`)가 문의·감면·지원 증빙을 함께 다룬다. 관리자는 묶음 전체 범위의 `AU.INSTR_W` 담당자만 목록·올리기·내려받기를 할 수 있고(범위가 좁으면 보이지 않음) 서류 검토중일 때만 더한다.
- **알아둘 점**: 공개 강사 목록·상세와 수강후기는 아직 없다. 온라인 지원은 회원과 연결되어 있어 관리자가 승인할 수 있다(비회원 지원서 문제는 방문·외부 접수에만 남는다).
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 18건과 동시성 시험 3건, 변이 검사로 확인했다.

### ADR-066
**공개 강사 목록·상세는 승인되고 공개로 정한 강사만 보이고, 분야와 강좌는 그 강사의 공개 강좌에서 읽으며, 심사 정보·연락처는 어떤 응답에도 담지 않는다** — 승인 (RQ-FUN-FN-018, 스키마 TB_INSTR·TB_CORS·TB_CORS_CLSF)

- **맥락**: 관리자 강사 심사(ADR-062)가 승인·공개한 강사가 주민에게 보이는 마지막 연결이다. 공개 강좌 목록이 이미 같은 조건(`IS.APPROVE`·`RLS_YN=Y`)으로 강사 이름을 보여 주므로 같은 기준을 쓴다.
- **결정**
  1. **공개 조건.** 강사 상태가 승인이고 공개 여부가 Y인 강사만이다. 활동중지·신청·반려·비공개는 목록에 없고 상세는 404다(없는 것과 같다). 공개로 정했다가 활동중지하면 관리자 쪽이 공개를 끄므로(ADR-062) 바로 사라진다.
  2. **항목.** 이름은 회원정보의 이름이다(공개 강좌 목록과 같다). `courseNames`는 그 강사의 공개 중인 강좌(`CS.OPEN·RUN·CLOSE`, 초안·폐강 제외)의 이름을 중복 없이 가나다순으로 준다. **분야(`categoryName`)는 따로 저장하지 않아 가장 최근 공개 강좌의 분류 이름**을 쓰고, 분류를 지웠거나 공개 강좌가 없으면 null이다. 경력·자격은 `CRR_CN`과 `QLFC_CN`을 줄바꿈으로 이어 주고 둘 다 비면 null이다. 소개(`INSTR_INTRO_CN`)는 계약에 없어 내놓지 않는다.
  3. **검색.** 이름 또는 공개 강좌 이름의 일부로 찾는다(`%`·`_`는 문자 그대로). 공개하지 않는 강좌 이름으로는 찾지 못한다. 정렬은 이름 가나다순이다.
  4. **비공개 정보.** 승인자·승인일·반려 사유·공개 여부·연락처는 응답에 없다.
- **알아둘 점**: 같은 이름의 회원 두 명이 강사이면 목록에서 이름만으로 구분되지 않는다(번호로 구분). 분야를 강좌 분류에서 읽으므로 강좌를 배정하기 전의 강사는 분야가 비어 있다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 8건과 변이 검사로 확인했다. 화면·계약은 바뀌지 않았다.

### ADR-067
**수강후기는 `review` 게시판의 후기 원글이며, 수강확정 이후의 내 강좌에 한 번만 쓰고 본인 글만 고치며, 공개 목록은 이름을 가려 누구나 본다** — 승인 (RQ-FUN-FN-020·052, PRD Q19, 스키마 TB_PST·TB_BBS)

- **맥락**: 후기는 "실제 수강 이력 회원만" 쓴다(FN-020). 문의(ADR-058)와 같은 게시물 행을 쓰되 공개이고 강좌에 이어진다.
- **결정**
  1. **저장.** `BBS_ID=review` 게시판의 원글(`PT.POST`, 공개, `CORS_SN`=강좌)이다. 글의 동은 강좌의 동이라 그 동의 담당자가 관리자 게시물 관리에서 본다. 게시판이 꺼져 있거나(`USE_YN`) 회원 작성을 받지 않으면(`MBR_WRT_YN`) 작성은 422다.
  2. **작성 자격(PRD Q19 가정).** 내 신청이 **수강확정(`ES.CONFIRM`) 또는 수강종료(`ES.COMPLETE`)** 인 강좌만이다. 대기·결제대기·취소·만료는 자격이 없다. 직접 요청도 같은 검사를 한다(422, 필드 `courseId`). 후기를 쓸 수 있는 강좌 목록(`/me/reviewable-courses`)은 같은 조건에서 이미 쓴 강좌를 뺀 것이다.
  3. **강좌마다 한 번(문서에 없어 둔 규칙).** 같은 회원이 같은 강좌에 지우지 않은 후기를 둘 이상 쓸 수 없다(422). 지우면 다시 쓸 수 있다. 회원 행을 잠근 뒤 자격·중복을 확인해 동시에 써도 한 건만 생긴다.
  4. **멱등.** 같은 키·같은 내용은 처음 글을, 다른 내용은 409를 돌려준다(작업이력 표식, R28).
  5. **수정·삭제.** 본인 글만이고 남의 글·지운 글은 404다. 수정은 제목·내용만이고 강좌는 바꿀 수 없다(422). 삭제는 논리 삭제다.
  6. **공개 조회.** 로그인 없이 목록·상세를 볼 수 있다(게시판이 쓰이고 지우지도 비공개도 답글도 아닌 후기). 작성자는 가린 이름이고 로그인한 회원에게만 내 글 표시와 수정·삭제 가능 값이 켜진다. 제목으로 찾을 수 있고 최근 순이다. 선택 로그인을 위해 `optional_member` 의존성을 공통(`auth/deps.py`)에 두었다(강사 모집공고 상세도 같이 쓴다).
- **알아둘 점**: 후기에는 첨부가 없다(계약에 없음). 관리자가 부적절한 후기를 숨기는 일은 관리자 게시물 관리의 삭제로 한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 14건과 동시성 시험 1건, 변이 검사로 확인했다.

### ADR-068
**권한 배정은 수정하지 않고 새로 만들거나 회수하며, 부여자가 가진 권한·범위·기간을 넘는 배정과 자기 배정을 막고, 범위 유형은 역할이 담은 권한으로 제한한다** — 승인 (RQ-FUN-FN-056, RQ-SER-NF-003·004, TDD 4.4, 스키마 TB_MNGR_SCP·TB_MNGR_ROLE·TB_ROLE_AUTHRT)

- **맥락**: 지금까지 만든 모든 관리자 기능은 배정 행의 권한·범위·유효기간을 읽는다(ADR-035). 그 행을 만드는 일이 이 기능이고, 여기서 위임 제한이 깨지면 다른 모든 범위 검사가 무의미해진다.
- **결정**
  1. **권한.** 조회·배정·회수 모두 `AU.GRANT_W`다. 목록·상세는 **내 부여 범위 안의 배정**만이다. 묶음 전체 부여자는 운영묶음과 전체 운영구조 배정을, 동 범위 부여자는 자기 동의 동 배정만 본다(범위 밖은 404). 배정은 고치지 않는다.
  2. **범위 유형은 역할의 권한으로 정한다.** 전체 운영구조(`SYSTEM`)는 역할의 권한이 모두 구조 권한(GRP_*·DONG_W·MNGR_W·ROLE_W·GRANT_W)일 때만, 동(`DONG`)은 구조 권한과 묶음 공통 권한(강사 승인 INSTR_W·교육기수 CONF_W·게시판 정의 BBS_W)이 없을 때만 줄 수 있다(R29, TDD 4.4). 묶음(`GROUP`)은 항상 가능하다.
  3. **위임 한도.** 역할의 **모든 권한**을 내가 그 범위로 줄 수 있어야 한다. 전체 운영구조 배정은 구조 권한만 주고, 묶음 배정은 묶음·동 범위로, 동 배정은 같은 동으로만 준다. 전체 운영구조 범위는 전체 운영구조 부여자만 준다. **기간도** 내가 그 권한을 계속 가진 기간(이어진 여러 배정을 합친 기간) 안이어야 한다. GRANT_W의 범위도 맞아야 한다. 어긋나면 422(필드 `roleId`)다.
  4. **자기 배정 금지(R18).** 자기 자신에게는 줄 수 없고(422) 자기 배정은 회수할 수 없다(422). 다른 권한 관리자가 대신 한다.
  5. **기간.** 시작일은 오늘(한국) 이후, 종료일은 시작일 이후다(문서에 없어 둔 규칙으로 과거 시점 소급 부여를 막는다). 종료일은 그날 끝까지이고 저장은 다음 날 시작이다(`> 지금`으로 읽는 판정과 맞춘다). 상태는 사용 여부와 기간으로 서버가 정한다(유효·시작 전·기간 종료·회수).
  6. **중복·동시성.** 같은 대상·역할·범위(·동)의 사용 중 배정과 기간이 겹치면 422다. 대상 관리자 행을 잠가 같은 대상의 배정을 한 줄로 세워 동시에 줘도 한 건만 생긴다. 사용 중지·없는 관리자와 꺼진·권한 없는 역할은 422다.
  7. **멱등.** 같은 키·같은 내용은 처음 배정을, 다른 내용은 409를 돌려준다(작업이력 표식, 부여자별).
  8. **회수.** 행을 지우지 않고 `USE_YN=N`으로 바꾸며(읽은 버전 확인, 409) 유효하거나 시작 전인 배정만 가능하다(끝난·회수한 배정은 409). 판정 함수가 요청마다 배정을 다시 읽으므로 회수는 대상의 세션이 살아 있어도 바로 효력이 난다(AUTH-05).
  9. **기록.** 배정·회수는 작업이력(`ROLE_GRANT`·`ROLE_REVOKE`)에 대상·역할·범위·동·기간(회수는 전후 상태)을 번호로 남긴다.
  10. **선택지.** 내가 줄 수 있는 역할(과 줄 수 있는 범위 유형)만, 자기와 사용 중지 계정을 뺀 관리자, 내 부여 범위의 동을 준다.
- **알아둘 점**: 역할 정의 자체(권한 구성)를 만들고 고치는 일은 `AU.ROLE_W`의 별도 기능이다. 마지막 `GRANT_W` 보유자를 회수해 아무도 배정하지 못하게 되는 일은 막지 않는다(다른 배정자가 있어야 하는 규칙으로 막고 있다). 동 담당자가 시스템 관리자에게 보이지 않는 업무 본문은 이 응답에 없다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 25건과 동시성 시험 1건, 변이 검사로 확인했다.

### ADR-069
**대시보드와 수요·정산·출석 통계는 원자료에서 그때그때 집계하고, 범위는 강좌의 운영 동이며, 자료 없음과 0을 구분하고, CSV는 첫 줄에 집계 조건을 담는다** — 승인 (RQ-FUN-FN-066·067·068, TDD 4.3, 스키마 TB_ATNLC_APLY·TB_STLM·TB_RFND·TB_CORS_ATND)

- **맥락**: 통계는 요구사항이 정의한 식(좌석점유·유효수요·순수납·출석률)대로 실제 원자료에서만 계산한다. 별도 집계 테이블은 두지 않는다. 연령·성별과 만족도(기관 제공 집계자료)는 자료를 올리고 승인하는 기능이 먼저 있어야 해서 다음 단계로 둔다(스텁 유지).
- **결정**
  1. **권한·범위(사용자 확정 2026-11-16).** 조회와 CSV는 `AU.STAT_R`이다. 범위는 **강좌의 운영 동**이라 동 담당자는 자기 동 강좌만 집계되고 동이 없는 강좌는 묶음 전체 담당자만 본다. 정산도 신청한 강좌의 동으로 거른다.
  2. **정의.** 신청 상태로 센다. 등록완료=`ES.CONFIRM`+`ES.COMPLETE`, 결제대기=`ES.HOLD`이면서 확인 중 결제(`PS.PENDING`)가 없는 것, 승인확인중=`ES.HOLD`이면서 `PS.PENDING`이 있는 것, 대기=`ES.WAIT`, 취소=`ES.CANCEL`+`ES.EXPIRE`. **좌석점유=등록완료+결제대기+승인확인중, 유효수요=좌석점유+대기**, 수요율=유효수요÷정원(정원이 0이면 null)이다. 고유 신청자는 회원 수다.
  3. **수요.** 강좌마다 한 줄이고 신청이 없는 강좌도 0으로 나온다(자료 없음과 0을 구분하려고 강좌는 남긴다). 기수·분야·신청일(한국 날짜)로 거르고 유효수요가 큰 강좌가 먼저다. 분류가 없으면 `미분류`다.
  4. **정산.** 승인액(`PS.PAID`, 승인일 기준)에서 **완료된 환불액**(`RS.DONE`, 환불일 기준)을 뺀 것이 순수납이고, 결과를 모르는 금액(`PS.PENDING`)은 순수납에 넣지 않고 따로 준다. 결제수단별(카드·계좌이체)로도 나눈다. 실패·취소 결제와 접수·보류·반려 환불은 넣지 않는다.
  5. **출석.** 체크한 건(출석+결석)만 분모로 하고 미체크는 뺀다. 지운 출석부는 뺀다. 출석부가 하나도 없는 강좌는 나오지 않고, 체크한 건이 없으면 출석률은 null이다. 강사는 강좌에 배정된 강사다. CSV로 내보내지 않는다(FN-068).
  6. **대시보드.** 기수를 주지 않으면 사용 중인 가장 최근 기수를 본다(문서에 없어 둔 기준). 신청 자료가 없으면 요약은 null이다. 강좌별 수요는 열 개까지다. **확인할 업무는 권한이 있는 종류만**이고 개수는 그 권한의 범위 안에서 센다(승인 결과 확인=`STLM_W`, 환불 검토=`RFND_A`, 강사 심사=`INSTR_W` 묶음 전체, 문의 답변=`POST_W`, 문자 실패=`SMS_SEND` 묶음 전체). **최근 작업은 묶음 전체 범위의 `AU.LOG_R`이 있을 때만** 나오고 담당자와 시스템의 작업만 담으며 회원 작업은 담지 않는다(작업 대상은 표와 번호만, 개인정보 없음).
  7. **CSV.** 수요·정산을 내려받는다. 첫 줄에 집계 조건(기간·기수·분야·집계 기준·생성 시각)을 주석 행으로 넣고, UTF-8 BOM·RFC 4180·수식 주입 방지를 지키며, 만들 때마다 작업이력(`CSV_EXPORT`)을 남긴다. 정산 CSV는 확인 중 금액을 순수납과 따로 둔 열의 합계 줄에 둔다. 기간 순서가 틀리면 422다.
- **알아둘 점**: 연령·성별·만족도 통계와 그 CSV는 기관 제공 집계자료(`TB_MBR_STATS_*`·`TB_CORS_DGSTFN_*`) 등록·승인 기능과 함께 한다. 강좌별 시간대 수요(FN-067의 시간대)는 계약에 없어 만들지 않았다. 큰 기간·전 강좌 집계는 요청마다 계산하므로 느려지면 색인을 본다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 17건과 변이 검사로 확인했다.

### ADR-070
**관리자 문자 발송은 서버가 대상을 산정해 미리보기로 보여 주고, 최종 확인과 수신자 수 확인을 거쳐 요청·강좌 연결·수신명단을 한 트랜잭션으로 저장하며, 발송은 워커가 한다** — 승인 (RQ-FUN-FN-059, TDD 8.2, SMS-01~06, 개정 요청 R17)

- **맥락**: 발송 처리(`sms_dispatch`)와 결과 조회는 ADR-048·049로 이미 있다. 이 기능은 관리자가 대상을 정하고 요청을 아웃박스에 쌓는 쪽이다. 문자는 한 번 나가면 되돌릴 수 없어 대상·문안·중복 방지를 서버가 최종 판정한다.
- **결정**
  1. **권한·범위.** 모두 `AU.SMS_SEND`다. **센터 전체는 묶음 전체 범위만** 쓰고(403), 선택 강좌는 강좌의 운영 동이 내 범위 안인 것만 고를 수 있다(아니면 422, 필드 `courseIds`). `EVENT` 범위는 자동 알림 전용이라 고를 수 없다(422).
  2. **대상 산정.** 선택한 신청 상태(수강확정=`ES.CONFIRM`, 결제대기=`ES.HOLD`, 대기=`ES.WAIT`)인 신청자의 **회원 한 명당 한 번**이다. 사용 중(`MS.ACTIVE`)이고 휴대전화가 있는 회원만이다. 서로 다른 회원의 같은 번호는 합치지 않는다(SMS-03). 중복 제거 수는 (회원, 강좌) 쌍 수에서 최종 수신자 수를 뺀 값이다. 선택 조건은 요청에 저장하지 않고 수신 명단만 남긴다(R17).
  3. **문안.** 앞뒤 공백을 뺀 뒤 한글 2바이트(cp949) 기준 90바이트까지이고 공급자가 표현할 수 없는 글자가 있으면 거절한다(422, 필드 `content`).
  4. **미리보기.** 저장하지 않고 수신자 수·중복 제거 수·강좌 수·센터 이름·바이트 길이·가린 수신자(최대 50명)를 준다.
  5. **발송 요청.** `confirmed`가 true여야 하고(422), 서버가 다시 산정한 수가 사용자가 확인한 수(`expectedRecipientCount`)와 다르면 **409**이며 지금 수를 알린다. 수신자가 없으면 422다. 통과하면 요청(`SM.MANUAL`)·강좌 연결·수신명단(암호화한 번호, `SS.WAIT`)을 한 트랜잭션으로 저장하고 작업이력(`SMS_SEND`, 건수만)을 남긴다. 발송은 커밋 뒤 워커가 한다(공급자 호출은 트랜잭션 밖). 발신번호는 설정값(`sms_sender_number`, 계약 전에는 TBD)이다.
  6. **멱등(SMS-02).** 키는 담당자별로 구분하고(`a{담당자}-{키}`) 같은 키·같은 내용(해시)은 처음 요청을 돌려준다. 대상이 바뀐 뒤에 같은 키로 다시 보내도 처음 요청을 돌려준다. 같은 키에 다른 내용은 409(IDEMPOTENCY_CONFLICT)다. 두 요청이 동시에 와도 (묶음, 키) 유일 제약이 한 번만 저장하게 한다.
  7. **이력·상세.** 자동 알림과 관리자 발송을 종류로 나눠 최근 순으로 보여 준다. 인증번호 문자(`CERT:` 사건)는 업무 알림이 아니라 뺀다. 결과 수는 성공(`SS.SENT`)·실패(`SS.FAIL`)·확인 중(`SS.SENDING`·`SS.UNKNOWN`)이다. **묶음 전체 담당자는 모든 요청을, 동 담당자는 자기가 보낸 관리자 문자만** 본다(문서에 없어 둔 범위). 상세는 처음 200건의 수신자를 가린 이름·번호, 시도 횟수, 마지막 시도의 실패 코드·사유와 함께 준다. 복호화할 수 없는 번호도 응답은 나온다(`****`).
- **알아둘 점**: 확인된 실패를 사람이 승인해 다시 보내는 재발송(ADR-049, 새 순번)은 계약에 없어 만들지 않았다. 연결 강좌가 폐강돼도 이력은 남는다. 수신자가 많을 때(수천 명)는 저장을 한 트랜잭션으로 하므로 시간이 걸릴 수 있다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 14건과 동시성 시험 1건, 변이 검사로 확인했다.

### ADR-071
**운영 설정은 읽기 전용으로 항목마다 최근 버전을 보여 주고, 공통 코드는 표시명·순서를 모든 그룹에서, 사용 여부는 기관이 정하는 목록에서만 한 번에 고치며 코드값은 바꾸지 않는다** — 승인 (RQ-FUN-FN-058·069, PRD Q21, 개정 요청 R20)

- **맥락**: 운영 기준(검토 상태 포함)과 공통 코드의 표시명은 기관 확인이 필요한 값이라 관리자가 읽고 고친다. 코드값(`ES.CONFIRM` 등)은 서버 업무 규칙이 직접 쓰므로 어떤 경우에도 바꾸지 않는다.
- **결정**
  1. **운영 설정(읽기 전용).** `AU.SITE_W` 묶음 전체 범위만(동 범위는 403)이다. 운영 기준은 콘텐츠 유형 `CT.OPER_RULE` 행이고, **항목(`CONTS_ID`)마다 가장 최근 버전만** 목록에 나온다. 상태는 `RVW_STTS_CD`(검토중·확정·보류, 비어 있으면 검토중)이고 확정은 실제 기능에 적용되었다는 뜻이 아니다(FN-069). 요약은 본문 첫 줄 80자까지(넘으면 말줄임), 상세의 버전은 같은 항목에서 그 행까지 몇 번째 기준인지다. 상태·항목명으로 거르고 `SORT_SEQ` 순이다. 이 화면에서는 고치지 않는다.
  2. **공통 코드 권한(R20 가정).** 조회와 수정 모두 `AU.GRANT_W` 묶음 전체 범위다(코드는 사이트 전체의 값이라 동 범위는 403). 코드 그룹 이름은 스키마 코드집합 이름과 코드 값의 뜻에서 옮긴 표를 쓰고 이름이 없는 그룹은 그룹 번호를 이름으로 쓴다.
  3. **조회.** 그룹은 코드가 있는 것만, 코드는 `SORT_SEQ`·코드 순이다. 코드·표시명 검색과 사용 여부 거르기가 있다. **업무 건수(`refCount`)**는 코드를 쓰는 표와 컬럼을 아는 그룹(신청·결제·환불·회원·강좌·게시물·강사·감면·파일·문자 등)에서만 세고, 알 수 없는 그룹은 0이 아니라 null이다.
  4. **수정(사용자 확정 2026-11-16).** 한 그룹의 표시명·순서·사용 여부를 한 번에 저장하고 **하나라도 거절되면 아무것도 저장하지 않는다**. **표시명·순서는 모든 그룹에서, 사용 여부는 기관이 정하는 목록(문의 분류 `IQ`, 강좌 분야 예시 `CC`)에서만** 바꿀 수 있다. 업무 규칙이 쓰는 그룹은 사용 여부를 바꾸려 하면 422다. 없는 그룹·없는 코드·다른 그룹의 코드가 섞이면 404, 같은 코드가 두 번이거나 표시명이 비면 422다. 코드를 더하거나 지우지 않는다.
  5. **기록.** 바뀐 코드의 전후 값(표시명·순서·사용 여부)을 작업이력(`CODE_UPDATE`, 대상은 그룹)에 남기고 바뀐 것이 없으면 남기지 않는다. 동시 저장은 그룹 행 잠금 아래에서 나중 저장이 덮어쓴다(레코드 버전 컬럼이 없다, R20).
- **알아둘 점**: 운영 기준을 새 버전으로 만들거나 검토 상태를 바꾸는 쓰기는 이 화면에 없다(TDD의 `PUT /settings/{id}/review-status`는 계약에 없어 만들지 않았다). 사용 여부를 끈 문의 분류는 문의 작성 화면(`USE_YN='Y'`만 보임)에서 빠진다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 14건과 변이 검사로 확인했다.

### ADR-072
**연령·성별과 만족도 통계는 승인된 기관 집계자료의 가장 나중에 승인한 한 버전만 그대로 보이고, 버전을 합산하지 않으며, 자료가 없으면 0이 아니라 미제공이다** — 승인 (RQ-FUN-FN-060·067·068, STAT-01~04, DGSTFN-01~03, 개정 요청 R38)

- **맥락**: 회원 개인의 생년·성별은 저장하지 않으므로(STAT-01) 연령·성별은 기관이 제공한 집계자료만 쓴다. 만족도도 주민 응답을 받지 않고 기관 제공 자료의 승인 버전만 읽는다.
- **결정(사용자 확정 2026-11-16: 조회와 CSV만)**
  1. **권한·범위.** `AU.STAT_R`이다. 연령·성별 자료에 동이 정해져 있으면 그 동을 다루는 담당자만, 만족도 자료는 그 강좌의 운영 동을 다루는 담당자만 본다(동이 없는 자료는 묶음 전체 담당자만).
  2. **승인된 최신 한 버전.** 연령·성별은 `SA.APPROVE`, 만족도는 `SA.APPROVED`이면서 **승인자와 승인일시가 모두 있는** 자료 중 가장 나중에 승인한 한 건이다. 대기·검증 전·반려와 승인 기록이 없는 자료는 없는 것이다. 이전 버전은 보이지도 합산하지도 않는다(STAT-03). 자료가 없으면 `source`가 null이고 행은 비며 0으로 대신하지 않는다.
  3. **연령·성별.** 연령 구간 이름과 순서는 자료 그대로이고, 성별 분류는 남·여·미상 세 열로 옮기되 합계·전체·계·소계 분류는 열에 넣지도 합산하지도 않는다(개정 요청 R38). 0명은 0으로 보인다. 자료 버전(번호)·출처·집계 기간·연령 기준일을 함께 준다.
  4. **만족도.** 응답자 수, 문항별 유효응답자 수와 선택 항목별 응답 수(자료 순서 그대로)를 준다. 평균은 **점수 문항에서만** `SUM(점수×응답수) ÷ SUM(점수 있는 응답수)`이고 분모가 0이면 산출하지 않으며 빈 점수를 0점으로 바꾸지 않는다(DGSTFN-03). 만족도 CSV·XLSX 내보내기는 없다.
  5. **연령·성별 CSV.** 첫 줄에 자료 버전·출처·집계 기간·연령 기준일·생성 시각을 주석 행으로 넣고 `연령구간,남,여,미상`을 담는다. 수식 주입을 막고 만들 때마다 작업이력(`CSV_EXPORT`)을 남긴다. 승인된 자료가 없으면 만들지 않고 422다.
- **알아둘 점**: 자료를 올리고 검증·승인·반려하는 관리자 기능은 계약에 없고 권한·화면 위치(PRD Q21, 화면설계서 S11)가 기관 확인 사항이라 만들지 않았다. 그래서 지금은 자료가 DB에 직접 들어가야 보인다. 만족도는 강좌 하나의 자료이고 조회 계약에 강좌를 나타낼 곳이 없어 강좌 이름이 보이지 않는다(R38). 자료 버전은 번호(`SRC_VER`)다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 11건과 변이 검사로 확인했다.

### ADR-073
**관리자 권한·메뉴 응답은 로그인한 관리자의 현재 유효 배정에서만 만들고, 메뉴는 노출용일 뿐 모든 요청은 서버가 다시 판정한다** — 승인 (RQ-FUN-FN-056, RQ-SER-NF-003, C06, 개정 요청 R19·R20)

- **맥락**: 관리자 화면은 서버가 준 메뉴만 그린다. 숨김은 편의이고 접근 통제는 각 API가 대상 레코드로 다시 한다.
- **결정**
  1. **유효 배정.** 배정 행마다 사용 중, 역할 사용 중, 유효 시작 이전이 아님, 종료 시각 전, 이 운영묶음 또는 묶음 공통인 행만 본다. 만료·예정·중지된 행과 다른 묶음의 행은 권한도 역할 이름도 주지 않는다.
  2. **시스템 배정.** `SK.SYSTEM` 배정은 구조 권한(`STRUCTURE_AUTHORITIES`)만 준다. 업무 권한은 `scope_for`와 같은 규칙으로 뺀다.
  3. **내용.** 역할 이름은 중복 없이 배정 순서대로, 묶음 이름, 권한 코드는 코드 정의 순서대로 준다. 기능을 켜지 않는 코드(`AU.MBR_W`)는 내보내지 않는다.
  4. **메뉴.** 서버가 가진 메뉴표(화면설계서 2.2·3.2, TDD 9.3 경로)에서 항목마다 하나라도 가진 권한이 있을 때만 넣고, 보이는 항목이 없는 묶음은 뺀다. 권한이 없으면 빈 메뉴로 200이다.
- **알아둘 점**: 메뉴표의 권한 후보는 화면 모의 서버와 같다. 항목을 부르는 API의 실제 권한과 어긋나면 메뉴표를 고친다. 기관이 권한을 확정하면(PRD Q21) 바뀔 수 있다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 7건과 변이 검사 11건으로 확인했다.

### ADR-074
**보존·파기 검토는 목록·상세 조회만 구현하고, 되돌릴 수 없는 파기 실행은 탈퇴 처리와 보존기간 확정 뒤로 미룬다** — 승인 (RQ-SER-NF-006, FN-032, SMS-06, AUTH-06, PRD Q21·Q30)

- **맥락**: 파기·비식별은 되돌릴 수 없다. 회원 탈퇴 처리가 아직 없어 탈퇴 회원 대상이 비어 있고, 환불계좌·문자기록의 보존기간은 정해지지 않았다(사용자 확정 2026-11-16: 조회만).
- **결정**
  1. **권한.** `AU.LOG_R`이고 묶음 전체 범위의 담당자만 본다. 동 담당자는 403이다(자료가 묶음 공통).
  2. **항목 번호.** 보존 항목을 담는 테이블이 없어 대상 종류마다 고정 번호 1~5(탈퇴 회원, 인증 기록, 감사이력, 환불계좌, 문자기록)다. 그 밖의 번호는 404다.
  3. **건수·날짜.** 건수는 기준 시각이 지난 것만 센다(탈퇴 30일, 인증번호 요청 30일[가정값], 감사이력 3년). 기준일은 가장 오래된 자료의 한국 날짜이고 예정일은 거기에 보존기간을 더한 날이다. 예정일이 오늘 이하이고 건수가 있으면 `DUE`, 아니면 `WAITING`이다. 감사이력은 `REVIEW_ONLY`, 환불계좌·문자기록은 `PERIOD_TBD`로 예정일을 만들지 않는다.
  4. **인증 기록.** 인증번호 요청(TB_CERT_DMND)만 센다. 세션·로그인 실패 이력은 기간이 정해지지 않아(Q30) 세지 않고 규칙 설명에 밝힌다.
  5. **제외.** 정산자료(결제·환불 원장, 5년)와 보안 접속로그(인프라 1년)는 목록에서 빼고 이유를 준다.
  6. **환불계좌.** 계좌가 있고 환불 집행일이 있는 환불만 센다.
  7. **실행.** `can_execute`는 항상 false이고 `executions`는 비어 있다. 실행 API는 계속 501이다.
- **알아둘 점**: 탈퇴 회원 건수는 아직 비식별하지 않은 회원과 구분할 표식이 없어 탈퇴 상태의 회원 전체를 센다. 실행을 만들 때 표식(스키마 개정)이 필요한지 정한다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 9건과 변이 검사 15건으로 확인했다(동치 변이 1건 제외).

### ADR-075
**회원 본인 정보는 세션의 회원만 다루고, 이메일만 저장하며, 비밀번호 변경과 탈퇴는 현재 비밀번호를 다시 확인한다. 탈퇴는 대기·결제대기 신청, 결과 불명 결제, 처리 중 환불이 있으면 거절한다** — 승인 (RQ-FUN-FN-031·032, AUTH-05, 개정 요청 R10·R33)

- **맥락**: 회원 `/me` 4건(프로필 조회·수정, 비밀번호 변경, 탈퇴)이 골격이었다. 탈퇴 처리가 없어 보존·파기 실행(ADR-074)의 전제도 비어 있었다(사용자 확정 2026-11-16).
- **결정**
  1. **조회·수정.** 회원 번호는 세션에서만 온다. 전화번호는 가려 보이고 센터 확인 상태는 `RV.OK`일 때만 `VERIFIED`다. 이메일만 저장하고 본인 입력 거주지역은 검증만 한 뒤 버리며 응답은 항상 null이다(저장할 컬럼 없음, R10·R33). 작업이력(`PROFILE_UPDATE`)에는 값이 아니라 바뀐 항목만 남긴다.
  2. **비밀번호 변경.** 회원 행을 잠그고 현재 비밀번호가 틀리면 400(`fields.currentPassword`)이다. 성공하면 이 세션만 남기고 같은 회원의 다른 세션은 끊는다. 값은 기록하지 않는다.
  3. **탈퇴.** 비밀번호를 다시 확인하고(틀리면 400 `fields.password`), 회원 행 잠금 아래에서 진행 중인 일이 없을 때만 `MS.WITHDRAW`와 탈퇴일시를 정한다. 진행 중이란 신청 `ES.WAIT`·`ES.HOLD`, 결제 `PS.PENDING`, 환불 `RS.REQUEST·HOLD·APPROVE·PENDING`이다. 있으면 422(`RULE_REJECTED`)다. 수강확정·수강종료 신청과 끝난 환불은 막지 않는다.
  4. **세션.** 탈퇴하면 현재 세션을 끊고 쿠키를 지운다. 다른 세션 행은 건드리지 않는다. 탈퇴 회원은 `active_member` 검사로 모든 세션이 이미 거절되고, 다른 세션 행을 갱신하면 그 행을 쥐고 회원 행을 기다리는 요청과 교착한다(동시 탈퇴 시험에서 확인).
  5. **중복 탈퇴.** 잠금을 얻은 뒤 상태가 `MS.ACTIVE`가 아니면 401이다. 그래서 두 번째 요청이 탈퇴일을 다시 쓰지 못한다(보존 30일이 늘어나는 것을 막는다).
- **알아둘 점**: 개인정보 파기는 이 단계에서 하지 않는다(보존·파기 실행은 ADR-074에서 미룸). 서로 다른 세션의 비밀번호 변경이 동시에 오면 교착이 날 수 있으나 드물어 따로 다루지 않았다. 현재 비밀번호를 연속으로 틀리는 시도의 횟수 제한은 두지 않았다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 17건과 동시성 시험 1건, 변이 검사 19건(동치 1건 제외)으로 확인했다.

### ADR-076
**홈 배너·팝업의 이미지는 콘텐츠를 소유 업무로 삼아 한 장만 올리고, 권한과 범위는 콘텐츠를 다루는 담당자(AU.SITE_W)와 콘텐츠의 동을 따른다** — 승인 (RQ-FUN-FN-011, FILE-10, 개정 요청 R9·R14)

- **맥락**: 관리자 파일 라우터의 콘텐츠 이미지 2건(목록·올리기)이 골격이었다. 공개 쪽은 배너·팝업의 이미지를 이미 내려준다(`FP.IMAGE`, 게시 기간 안).
- **결정**
  1. **소유 업무.** 홈·센터 콘텐츠(`CT.BANNER·POPUP·HISTORY·INTRO`)만 대상이다. 약관·운영 기준 같은 다른 콘텐츠 행과 다른 묶음의 콘텐츠는 404다. 권한이 없으면 존재를 숨기려고 404다(다른 소유 업무와 같다).
  2. **범위.** 콘텐츠의 동이 담당자의 `AU.SITE_W` 범위 안일 때만 보고 올리고 지운다. 동이 없는 공통 콘텐츠는 묶음 전체 담당자만 다룬다.
  3. **한 장.** 배너와 팝업만 이미지를 쓰고 한 장이다. 이미 있으면 422이고 한 장을 바꾸려면 먼저 제거한다. 연혁·소개는 이미지를 쓰지 않아 올리기가 422이고 목록은 `canEdit=false`다(계약의 `maxFiles`는 1 이상이라 0으로 알리지 않는다). 형식은 jpg·jpeg·png만이고 서버가 검사 대기(`FS.PENDING`)로 저장한다.
  3. **동시성.** 올리기 전에 콘텐츠 행을 잠가 서로 다른 키의 동시 올리기가 두 장이 되지 않게 한다.
  4. **전체 목록·상세·내려받기·삭제.** 콘텐츠 이미지도 같은 경로로 다루고 범위는 위와 같다.
- **함께 고친 것**: 전체 파일 상세가 감면 증빙·강사 지원서 파일에서 환불로 가정해 500이 나던 것을 소유 업무별 이름으로 고쳤다(`_summary`).
- **알아둘 점**: 홈 비주얼은 저장 코드가 없어(R9) 대상이 아니다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 10건과 동시성 시험 1건, 변이 검사 20건으로 확인했다.

### ADR-077
**세션이 필요한 모든 쓰기 경로의 CSRF 검증은 경로마다 붙이지 않고 세션 의존성이 요청 메서드로 한다** — 승인 (DV17, RQ-SER-NF-008, ADR-008)

- **맥락**: 관리자 쓰기 63건 중 22건만 `require_admin_write`로 CSRF를 강제하고 41건은 로그인만 확인했다. 경로를 만들 때마다 쓰기 의존성을 골라야 해서 빠뜨리기 쉬웠다. 회원 쪽은 22건이 모두 강제하고 있었다.
- **결정**
  1. **메서드로 판정한다.** `require_admin`과 `require_member`가 `GET·HEAD·OPTIONS`가 아닌 요청에서 `X-CSRF-Token`을 세션에서 파생한 값과 비교한다. 다르면 403(`FORBIDDEN`)이다. 관리자 라우터 전체와 회원 세션 경로가 이 의존성을 쓰므로 새로 만드는 쓰기 경로도 자동으로 포함된다.
  2. **순서.** 세션 확인(401) 다음에 CSRF를 보고, 그다음에 활동 시각을 갱신한다. 틀린 요청은 오류로 끝나 트랜잭션이 되돌려지므로 유휴 시간이 늘지 않는다.
  3. **스스로 검증하는 경로.** 로그인 전 경로(관리자 `login`, 회원 `join`·`otp`·`find-id`·`password-reset`·`login`)는 세션이 없어 시드 쿠키로, `logout`·`extend`는 직접 검증한다. 이 경로는 변하지 않았다.
  4. **`require_*_write`는 표시용으로 남긴다.** 이미 붙은 경로를 건드리지 않으려고 이름은 두고 검증은 하지 않는다(중복 검증 없음).
  5. **자동 점검.** 시험이 관리자·회원 라우터에서 쓰기 경로를 모아 토큰 없음·틀린 토큰이 모두 403인지 확인한다. 새 쓰기 경로가 검증을 빠뜨리면 이 시험이 실패한다.
- **알아둘 점**: 프런트 두 앱은 이미 모든 쓰기 도우미가 토큰을 싣는다(`http.ts`). CSV·파일 내려받기는 GET이라 토큰이 필요 없다. 조회에 `X-Background` 헤더를 붙이면 유휴 시간을 늘리지 않는 기존 규칙은 그대로다.
- **결과**: 기존 시험 1720건은 수정 없이 통과했다. 새 시험 6건과 변이 검사 5건(동치 1건 제외)으로 확인했다.

### ADR-078
**보존·파기 실행은 관리자가 확인 건수를 넣어 실행하는 방식으로, 탈퇴 30일이 지난 회원의 비식별과 30일이 지난 인증번호 요청의 삭제만 한다** — 승인 (RQ-SER-NF-006, FN-032, AUTH-06, ADR-074 후속, PRD Q21·Q30)

- **맥락**: ADR-074는 조회만 구현하고 되돌릴 수 없는 실행을 미뤘다. 탈퇴 처리(ADR-075)가 생겨 전제가 갖춰졌다(사용자 확정 2026-11-17: 비식별 방식, 관리자 실행만, 권한).
- **결정**
  1. **권한.** `AU.GRANT_W` 묶음 전체 범위만 실행한다. 조회 권한(`AU.LOG_R`)만 있거나 동 담당자는 403이다(PRD Q21 후보, 확정되면 바뀔 수 있다). 상세의 `canExecute`는 이 권한과 실행 가능한 대상, 예정일이 지난 건수가 모두 있을 때만 true다.
  2. **실행 대상.** 탈퇴 회원(1번)과 인증 기록(2번)뿐이다. 감사이력(3번)은 검토만이라 422, 환불계좌(4번)·문자기록(5번)은 보존기간이 정해지지 않아 422다. 없는 번호는 404다.
  3. **확인 건수.** 대상 행을 `FOR UPDATE`로 잠근 뒤에 다시 세어 확인한 건수와 다르면 409(`CONFLICT_STATE`)다. 그 전에 아무것도 바꾸지 않는다. 동시에 같은 항목을 실행하면 하나만 처리하고 나머지는 대상이 줄어 409다.
  4. **멱등.** `Idempotency-Key`와 (항목, 확인 건수) 해시를 작업이력 메모에 남긴다(R28). 같은 키·같은 내용은 이전 결과를 돌려주고 다시 처리하지 않으며, 같은 키에 다른 내용은 409(`IDEMPOTENCY_CONFLICT`)다. 표식은 잠금을 얻은 뒤에 본다.
  5. **탈퇴 회원 비식별.** 탈퇴 후 30일이 지난 회원의 이름은 `탈퇴회원`, 전화번호·이메일은 NULL, 로그인 아이디는 `withdrawn-회원번호`로 바꾼다. 같은 아이디가 이미 있거나 20자를 넘으면 해시 아이디(`w-` + 18자)를 쓴다. 회원 번호와 결제·환불 원장은 그대로다. 처리한 회원의 표식은 별도 컬럼이 아니라 "이름이 `탈퇴회원`이고 전화번호가 없는 탈퇴 회원"이다.
  6. **인증 기록 삭제.** 30일(가정값)이 지난 인증번호 요청(`TB_CERT_DMND`)을 지운다. 문자 기록(`TB_SMS_TRGT`)이 가리키는 요청은 문자 기록의 보존기간이 정해질 때까지 남기고(FK RESTRICT) 목록 건수에서도 뺀다. 세션·로그인 실패 이력은 ADR-074대로 세지 않는다.
  7. **기록.** 실행마다 작업이력(`RETENTION_EXECUTE`)에 실행자와 처리 건수만 남기고 개인정보 값은 적지 않는다. 상세의 `executions`는 이 기록을 최근 것부터 20건 보인다.
- **알아둘 점**: 이름이 `탈퇴회원`인 실제 회원이 전화번호 없이 탈퇴하면 처리한 것으로 보고 건너뛴다(전화번호는 가입 때 필수라 사실상 없다). 워커의 자동 실행은 만들지 않았다. 기관이 보존기간(Q30)을 확정한 뒤에 더한다. 탈퇴 회원의 다른 개인정보(강사 지원서의 이름·연락처 등)는 이번 범위가 아니다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 9건과 동시성 시험 1건, 변이 검사 19건으로 확인했다.

### ADR-079
**파일 검사는 ClamAV(clamd) 어댑터를 `FileScanner` 포트의 구현으로 더하고, 닿지 못하거나 결과를 알 수 없으면 통과로 보지 않는다** — 승인 (TRD 4.5, NF-SER-002, PRD Q9, ADR-049 후속)

- **맥락**: ADR-049는 검사기를 포트로 두고 모의 어댑터만 만들었다. 실제 검사기는 배포 환경이 정해진 뒤로 미뤘다(사용자 확정 2026-11-17: 이번에는 clamd 어댑터만).
- **결정**
  1. **프로토콜.** clamd의 `zINSTREAM`으로 TCP 연결을 열어 64KB 덩어리마다 4바이트 빅엔디안 길이를 앞에 붙여 보내고, 길이 0으로 끝낸다. 응답은 한 줄이다.
  2. **결과 해석.** `… OK`는 통과, `… FOUND`는 차단이다. 탐지 이름은 결과 객체에만 담고 로그·이력·화면에 내보내지 않는다(ADR-049 6). 그 밖의 응답(`… ERROR`, 빈 응답, 알 수 없는 문자열)과 연결 거절·시간 초과·응답 전 끊김은 모두 `ScanUnavailable`이다. 워커는 이 경우 파일을 검사 대기로 두고 다음 주기에 다시 한다.
  3. **설정.** `JORI_FILE_SCANNER=clamd`이면 쓰고, 주소는 `JORI_CLAMD_HOST`(기본 `127.0.0.1`), `JORI_CLAMD_PORT`(기본 `3310`)다. 둘은 clamd의 기본 TCP 값이고 배포 환경이 정하면 환경변수로 바꾼다. 시간 제한은 30초다.
  4. **모의 검사기는 그대로 둔다.** 기본값은 계속 `mock`이라 개발·시험은 영향이 없다.
- **알아둘 점**: Unix 소켓 접속은 만들지 않았다(배포가 같은 호스트의 소켓을 쓰기로 정하면 더한다). clamd의 `StreamMaxLength`(기본 25MB)는 업로드 한도(20MB)보다 커야 한다. 작으면 큰 파일이 `ERROR`로 검사 대기에 머문다. 실제 ClamAV로는 시험하지 않았고 프로토콜을 따르는 가짜 서버로 확인했다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 12건과 워커 흐름 시험 2건, 변이 검사 15건으로 확인했다.

### ADR-080
**조회가 실패해 남은 PG 통보는 워커가 1분 간격으로 최대 3회까지 다시 조회해 반영하고, 사람이 대사해야 하는 사건은 건드리지 않는다** — 승인 (TDD 5.4.2, FN-041, R23·R30, ADR-040 후속)

- **맥락**: 통보를 받았는데 PG 거래 조회가 실패하면 결제를 바꾸지 않고 사건을 `EP.FAIL`(재시도 1회)로 남긴다. 이때 결제는 `PS.READY`로 남아 있어 결제 재조회 작업(`PS.PENDING`만 본다)이 보지 못한다. 재시도 작업이 없으면 이 결제는 담당자가 알아차릴 때까지 확정되지 않았다.
- **결정**
  1. **대상.** 웹훅 사건(`ET.WEBHOOK`) 중 `EP.FAIL`이고 재시도 횟수가 1 이상 3 미만이며 마지막 처리가 1분 이상 지난 것이다. 최초 통보가 1회째라 재시도는 최대 2번이다. 불일치·보상환불로 `EP.FAIL`이 된 사건은 재시도 횟수가 0이라 대상이 아니다.
  2. **처리.** 통보 처리와 같은 규칙(`settle_payment`)으로 강좌→신청→결제를 잠그고 반영한다. 다시 조회해도 모르면 횟수만 늘리고 `EP.FAIL`로 둔다. 알게 되면 결과(`EP.DONE`, 불일치면 `EP.FAIL`)로 사건을 닫고 횟수를 0으로 되돌려 다시 집히지 않게 한다. 조회가 예외를 내도 결과 불명으로 본다.
  3. **경합.** 사건 갱신은 읽은 상태(`EP.FAIL`, 같은 횟수)일 때만 되고 아니면 결제 반영까지 함께 되돌린다. 다른 처리가 먼저 사건을 끝낸 경우다.
  4. **주기·기록.** 30초마다 돈다(`retry_webhooks`). 처리마다 작업이력(`PAY_WEBHOOK_RETRY`, 시스템)을 남기고 항목마다 커밋한다. 한도(3회)에 닿은 사건은 `EP.FAIL`로 남아 담당자가 대사한다.
- **알아둘 점**: 결제 재조회 작업(`PS.PENDING`, `ET.RECON`)과 대상이 다르다. 한 결제가 둘 다에 걸려도 `settle_payment`가 이미 확정된 결제를 `EP.DONE`으로 닫으므로 이중 반영은 없다.
- **결과**: 새 테이블·컬럼 없이 구현했다. 기능 시험 7건과 변이 검사 14건으로 확인했다.
