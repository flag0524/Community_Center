# 홈페이지 글 유형(CT) 코드 추가 요청서

> **회신 반영(2026-11-19):** 3.1은 (가) 12자 이내로 줄임(`CT.PRVPOLICY`, `CT.EMAILREFU`), 3.2~3.5는 제안대로 회신받아 구현했습니다. 이 문서는 발송 당시 내용이며 구현 결과는 ADR-092에 있습니다.

- 요청 대상: 스키마 설계 담당자(스키마 설계안 v0.5 소유자)
- 요청처: 조리읍 주민자치센터 수강시스템 구축 개발팀
- 관련 번호: 스키마 개정 요청서 R3, R4, R9, R14, R16 / 요구사항 RQ-FUN-FN-006, FN-011, FN-055, FN-072
- 회신 기한 희망: 구현 착수 전(코드가 정해져야 콘텐츠 저장 화면을 연결할 수 있습니다)

## 1. 요청 요약

콘텐츠 유형(CT) 코드집합에 **4종을 추가**하고, 아래 **5가지를 정해 주십시오.** 가장 먼저 정해야 할 것은 **코드 이름의 길이**입니다. 기관과 합의한 이름 두 개가 코드 칸(CHAR(12))에 들어가지 않습니다.

## 2. 배경

기관(조리읍 주민자치회)이 2026-11-17 2차 회신에서 아래 4종의 추가에 동의했습니다. 현재 CT는 8종뿐이라 이 글들을 저장할 수 없고, 해당 화면(푸터 링크, 수강·환불 안내, 연락처)은 시안 문서로만 동작합니다.

현재 CT 코드(설계안 코드표, 마이그레이션 0001 시드):

| 코드 | 이름 | 글자 수 |
|---|---|---|
| `CT.INTRO` | 소개 | 8 |
| `CT.HISTORY` | 연혁 | 10 |
| `CT.POPUP` | 팝업 | 8 |
| `CT.BANNER` | 배너 | 9 |
| `CT.TERMS` | 이용약관 | 8 |
| `CT.PRIVACY` | 개인정보동의문 | 10 |
| `CT.MARKET` | 마케팅동의문 | 9 |
| `CT.OPER_RULE` | 운영기준·결정검토 | 12 |

관련 제약: `TB_COM_CD.COM_CD`와 `TB_SITE_CONTS.CONTS_TYPE_CD`는 CHAR(12)이고, `CK_CD_SITE_CONTS_CONTS_TYPE_CD`가 `CT.%` 접두부를 검사하며, `FK_SITE_CONTS_03`이 코드표 존재를 검사합니다.

## 3. 추가를 요청하는 코드

| 순서 제안 | 코드(기관 합의 이름) | 코드명 | 쓰임 | 기관 답 |
|---|---|---|---|---|
| 9 | `CT.GUIDE` | 수강·환불 안내 | 수강신청·환불 안내 글 | 동의 |
| 10 | `CT.CONTACT` | 연락처 | 수강문의·센터 대표·행정복지센터 대표 전화, 운영시간, 주차, 주소 | 동의 |
| 11 | `CT.PRIVACY_POLICY` | 개인정보처리방침 | 푸터와 방침 화면에 게시하는 문안 | 동의, 버전 관리를 함 |
| 12 | `CT.EMAIL_REFUSAL` | 이메일 무단수집 거부 | 푸터 링크의 안내 문안 | 동의, 버전 관리를 함 |

**추가하지 않는 것:** `CT.FACILITY`(시설안내)는 기관이 추가하지 않기로 했습니다. `CT.VISUAL`(홈 비주얼)은 기관 답이 없어 이번 요청에서 뺍니다.

## 4. 정해 주실 것

### 4.1 코드 이름의 길이 (가장 먼저)

`CT.PRIVACY_POLICY`는 17자, `CT.EMAIL_REFUSAL`은 16자라 12자를 넘습니다. (`CT.GUIDE` 8자, `CT.CONTACT` 10자는 들어갑니다.)

| 선택 | 내용 | 영향 |
|---|---|---|
| (가) **12자 이내로 줄임 — 개발팀 추천** | `CT.PRVPOLICY`(12자), `CT.EMAILREFU`(12자) | 컬럼·FK 변경 없음. 기관 문서의 긴 이름은 줄임 이름과 같은 뜻으로 읽는다고 기록 |
| (나) 코드 칸을 넓힘 | CHAR(12)를 더 길게 | 코드를 참조하는 모든 CHAR(12) 컬럼과 FK가 연쇄로 바뀌어 영향이 큼 |

회신 칸: ☐ (가) 그대로 / ☐ (가)에서 이름을 이렇게 바꿈: `__________`, `__________` / ☐ (나)

### 4.2 두 문안(방침·이메일 거부)을 약관과 같은 버전 관리 규칙(R17)에 포함할지

기관은 두 문안의 버전 관리를 하겠다고 답했습니다. 제안은 다음과 같습니다.

- 설계안 R17(게시된 버전은 본문 수정 금지, 새 버전 생성, SHA-256 문안 고정)을 두 유형에도 적용합니다.
- 두 문안은 회원이 동의하는 문서가 아니라 고지 문서이므로 **동의 이력(`TB_MBR_AGRE_HSTRY`, R22)의 동의 대상에는 넣지 않습니다.**

회신 칸: ☐ 제안대로 / ☐ 다르게: `__________`

### 4.3 묶음 공통(동 미지정)인지

약관은 `DONG_SN`이 NULL인 묶음 공통입니다. 네 유형도 같은지 확인해 주십시오. 개발팀은 **묶음 공통**을 제안합니다(센터는 하나의 운영묶음).

회신 칸: ☐ 제안대로 / ☐ 동별로 둘 수 있음

### 4.4 연락처의 저장 위치

연락처는 항목이 여럿입니다(전화 3종, 운영시간, 주차, 주소). 새 컬럼 없이 **`CONTS_CN`(CLOB)에 항목 구조(JSON)로 저장**하는 것을 제안합니다. 이 경우 설계안에 "`CT.CONTACT`의 본문은 구조화 값"이라는 규칙을 한 줄 적어 주시면 됩니다.

회신 칸: ☐ 제안대로 / ☐ 별도 컬럼·테이블이 필요함: `__________`

### 4.5 게시 기간

네 유형의 게시 여부(`PSTG_YN`)와 게시 기간은 기존 규칙(게시 시작 이상·종료 미만)을 그대로 씁니다. (홈 배너만 기간과 무관하게 노출하도록 이미 별도로 정했습니다.)

## 5. 승인되면 개발팀이 하는 일

1. 스키마 설계안 코드표와 마이그레이션 0001 시드에 코드 4종을 넣고, 5개 운영묶음의 코드집합 체크섬을 맞춥니다(설계안 R24).
2. 콘텐츠 API의 유형 목록과 유형 매핑, 관리자 콘텐츠 화면의 유형 탭, 공개 화면(푸터·안내·연락처)을 서버 콘텐츠로 연결합니다. 지금은 시안 문서로만 동작합니다.
3. 4.2가 승인되면 약관 서비스의 버전·해시 규칙을 두 유형에도 적용합니다.
4. 각 단계는 실제 DB 시험과 변이 검사로 확인합니다.

## 6. 승인이 늦어질 때의 영향

- 푸터의 개인정보처리방침·이메일 무단수집 거부는 계속 "검토 중" 문구로 게시됩니다.
- 수강·환불 안내와 연락처는 센터 전화·주소(운영묶음 값)만 표시하고, 운영시간·주차·수강문의 번호는 표시하지 못합니다.
- 코드 이름이 정해지기 전에는 시드를 만들지 않으므로 나중에 이름이 바뀌어도 저장된 데이터를 옮길 필요가 없습니다.
